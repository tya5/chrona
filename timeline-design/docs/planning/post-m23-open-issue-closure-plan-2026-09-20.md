# Post-M23 Open-Issue Closure Plan — 2026-09-20

**Status:** Design complete; implementation begins only after this design is published
**Scope:** GitHub issues #14, #16, and #17; Gregorian leap-year contract clarification
**Milestone effect:** M23 remains complete. This is corrective work against accepted

## 1. Purpose

The M23 release closes the planned roadmap, but three presentation issues remain open.
This program closes those gaps and records the already-general Gregorian rule without
changing Project, Schedule, Actual, or Review meaning.

The order is mandatory: publish this design and the owning specification corrections,
then implement, regenerate the affected examples, run the complete evidence set,
publish the implementation, and close only issues whose published evidence passes.
GitHub writes are strictly serial and non-force.

## 2. Closed design decisions

### 2.1 Gregorian Date arithmetic

Every accepted ISO Date uses the proleptic Gregorian leap-year rule across the
implementation's supported Date range: a year divisible by 4 is a leap year, except a
year divisible by 100 is not, unless it is also divisible by 400. Month/year
CalendarPeriod arithmetic derives the target month's final valid day from that rule and
then applies the existing clamp policy. No year-specific exception is permitted.

The existing representative leap-year conformance cases remain sufficient because the
implementation delegates target-month validity to a general calendar operation rather
than branching on named years. No exhaustive year-by-year or century-case fixture set
is required. Advancing a February 29 date by one year continues to clamp to February 28
when the target year is common.

### 2.2 Theme paint and opacity ownership

Scene owns the resolved paint value for every emitted mark. A `row-shade` Rect carries
both `theme.paints.rowShade.color` and `opacity`; the SVG adapter serializes that Scene
opacity without replacing or dropping it.

A planned or baseline point mark is a milestone visually while retaining its planned or
baseline semantic facet. It therefore resolves `theme.paints.milestone`, emits the
distinct output purpose `milestone`, and matches the milestone legend swatch. Actual
point observations retain the Actual paint and purpose. Span plan bars continue to use
the planned paint and purpose. Adapters do not infer point paint from sample IDs.

### 2.3 Table/timeline label ownership

On a `table-timeline` surface, direct timeline labels exist only when an explicit
`detail.labelRules` entry requests them. Scene must not synthesize a title-label rule.
A table title column and an explicit timeline title rule may coexist only when the
settings author intentionally requests both.

The shipped Aster table/timeline settings remove the redundant title rule because their
table already carries `source: title`. Non-table surfaces retain their existing title
default so the change does not remove the only row identification on minimal or review
surfaces.

### 2.4 Text collision boundary

Label placement treats previously accepted emitted text associated with a row,
including variance and date labels, as obstacles in addition to comparison marks and
previous item labels. Candidate search remains finite and deterministic. Optional text
may be omitted under `clip-optional`; required text diagnoses
`E_PRESENTATION_LABEL_UNPLACEABLE`. No renderer-specific coordinate correction is
allowed.

### 2.5 Example and reproducibility closure

All five Aster SVGs are regenerated from their manifests. The overview acceptance test
must prove row-shade opacity, planned-gate paint/purpose equality with the legend,
absence of duplicate timeline titles, and non-overlap of emitted text bounds. The
Controller Z executive artifact is regenerated by its documented command and must
remain byte-deterministic. The M23 Controller Z review-detail SVG/PNG is also
regenerated because it consumes the same Scene row-shade and point-mark contracts; its
existing detail-content acceptance remains unchanged.

The Aster README documents both complete SVG+PNG verification and the SVG-only
`--no-raster` path. It states that raster verification requires Node, `sharp`, and the
runtime module path, so an unavailable optional raster dependency is not confused with
an SVG-generation failure.

## 4. Stop conditions

Implementation stops if it discovers a semantic choice not closed above, a required
label that cannot be placed, a mismatch between regenerated and tested output, or a
regression outside this scope. The owning design is corrected and published before
implementation resumes.
