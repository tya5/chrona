# Design — Reproducible Example Evidence and Reachability (#441)

**Design plan:**
`issue-441-reproducible-example-evidence-design-plan-2026-09-26.md`.

## Decision

An example directory is a declared corpus closure, not a general asset folder.
The authoritative roots are tracked `examples/*/manifest.yaml` documents. A
manifest reaches its declared Contexts and generated `expectedSvg` /
`expectedScene` evidence; each Context reaches its typed local resource
references and recursively declared local source assets. A tracked file under
`examples/` is valid only when it is reachable from that graph or has a
recorded, finite reason in an explicit reachability declaration.

The graph walker is a repository-quality tool. It neither materializes content
nor uses renderer logic. It recognizes only typed references already used by
the materializer/closure contract: manifest Context and evidence paths; local
Context references; snapshot-project references; and local icon/source assets.
Package resources are recorded as external closure dependencies and are not
mistaken for missing example files. All paths are normalized beneath their
example root, and an undeclared traversal, missing node, duplicate evidence
owner, or unclassified tracked file is an error.

## README evidence contract

A Markdown image in the root README whose target is below `examples/` must
point directly at a manifest's declared generated SVG evidence. The check
matches the normalized repository-relative target to exactly one
`expectedSvg`; its path is therefore the exact committed materializer artifact,
not a copied byte replica. Non-example images remain outside this contract.
The README will use `examples/aster-ssd/generated/overview.svg` as its hero.

SVG is selected deliberately: it is the immutable public materializer output
already declared by the ASTER manifest, displays in GitHub Markdown, and needs
no separate preview/raster lifecycle. The caption will identify it as
materialized corpus evidence rather than imply an unpublished gallery.

## Test population

View schema validation will derive its paths from reachable manifest Context
references, not a filesystem glob. Each selected View must have the current
schema version and validate. A tracked but unreachable View is rejected by
the reachability gate; it cannot become an old-version skipped fixture. This
keeps syntax validation and materialization coverage over the same public
population without making schema tests own repository topology.

## ASTER migration

The atomic cleanup removes `slides/`, `gallery.html`, and Views 02–05. The
remaining `overview` source, Context, generated SVG/Scene, and README are
all one closure. Historical documentation under `docs/archive/` is not
rewritten: it records past artifacts and is outside the live README/evidence
contract.

## Exclusions

- No gallery product feature, PNG rendering policy, or new example packaging
  mechanism.
- No generic filesystem-reference heuristic or automatic deletion of an
  unclassified file.
- No renderer changes; materialization remains the owner of generated bytes.
