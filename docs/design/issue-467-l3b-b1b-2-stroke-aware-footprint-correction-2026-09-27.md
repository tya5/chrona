# Design Correction — B1b-2 Stroke-Aware Candidate Footprints (#467, #494)

**Design plan:** [B1b-2 stroke-aware footprint plan](../planning/active/issue-467-l3b-b1b-2-stroke-aware-footprint-design-plan-2026-09-27.md). **Extends:** [atomic bundle and row translation correction](issue-467-l3b-candidate-footprint-correction-2026-09-27.md) and [L3b preflight and route evidence correction](issue-467-494-l3b-prelayout-route-evidence-correction-2026-09-27.md). **Architecture review:** [whole-architecture review](../reviews/current/issue-467-l3b-b1b-2-stroke-aware-footprint-architecture-review-2026-09-27.md). **Normative homes:** [Specification 38 §3.1](../specification/38-review-row-composition.md) and [Specification 46 §7](../specification/46-completed-scene-paint.md).

## Problem and boundary

B1b-1 accepts `ObstacleGeometry` footprints and documents that callers provide stroke-expanded bounds or segments. It intentionally has no ReviewProjection, Theme, mark, or icon mapping. The source trace also found a responsibility gap: `surface_composer` creates mark bounds/ports, but `scene/v05_builder.py` calls `ThemeTokenView.variant_symbol` and `scene/mark_geometry.py`'s `symbol_geometry`/`glyph_parts` to create point-symbol path geometry; Scene `_complete_icon_paths` transforms normalized icon commands and applies `stroke_scale`; and `_glyph_part_paint` modifies a `ScenePaint` after the resolver returns it. These operations can change geometry or appearance after Layout has made collision decisions. Without closing both that ownership gap and the role-by-role footprint mapping, B1b-2 could reserve only fill geometry, apply stroke twice, or put paint conversion outside the declared resolver.

This correction closes the mapper's geometry contract and selects a structural ownership correction: Layout must return complete mark-symbol and icon path geometry, including transformed coordinates and scaled stroke widths, before Scene construction. This applies to ordinary point marks and point legend swatches. Scene may select primitive identity/order and ask `ScenePaintResolver` to convert a typed paint intent for each primitive/path part. All glyph-part and icon-path color/channel treatment is resolved there; post-resolution paint mutation is removed. Layout derives visible extents from the same resolved Theme geometry metrics and normalized icon closure used to produce those completed paths. It does not choose colors, paint families, opacity, dash, or a replacement stroke treatment. Scene and adapters receive completed placements and paint; neither repairs candidate geometry.

## Geometry authority and one-expansion rule

For each mark role, Layout uses the same canonical Theme geometry role, mark shape/glyph selection, bounds, and selected temporal scale for both the candidate footprint and final placement. Numeric Theme geometry inputs include the role's `markGeometry` height/offset/order/corner-radius values and, when that role declares a stroke, its resolved `strokeWidth` and explicit line-cap/join values. Layout may read these geometry-bearing values through the existing validated Theme token view and normalized icon closure; it MUST NOT call `resolve_scene_paint`, construct `ScenePaint`, interpret a color channel, or select a paint family. The completed Layout result carries selected geometry/path commands and non-paint path metadata needed by Scene. For a Theme glyph part, it carries geometry plus a typed paint intent (mode and any Theme-authored color) for the resolver; for an icon path, it carries transformed commands, scaled width, cap/join metadata, and a typed paint intent. Those intents are not completed paint.

`ScenePaintResolver` is extended as the only Theme/Scheme-to-paint conversion point to consume those typed part intents and return completed paint for each emitted primitive/path. The builder MUST NOT patch a returned paint value in `_glyph_part_paint` or complete icon stroke paint outside the resolver. This change preserves paint resolution after geometry while making Layout the sole geometry authority. It adds no serialized Scene field or resource schema; any required internal request/result type belongs to the implementation plan and must be immutable.

The ownership move preserves the existing geometry contract exactly: use contain-and-center fitting for Theme glyphs; ignore a built-in Layout outline when the selected shape is a glyph, but keep using the nonempty Layout-completed outline for the built-in diamond path; omit `paint: none` parts; preserve part order, `partN` identity and paint order; close glyph paths with the same start point and deterministic float arithmetic; and use each normalized vector icon's path commands, per-path cap/join, and Theme-scaled stroke width. Legend point swatches use the same Layout shape/glyph path closure as their source/variant, with their current source and stable Scene identities. These are compatibility requirements, not new shape or paint choices.

Each source primitive is converted exactly once into a collision footprint:

- A stroked `Rect` uses the emitted rectangle bounds expanded by half its resolved stroke width on each side. A fill-only rectangle uses the bounds as-is.
- A stroked `Symbol` uses its Layout-completed path geometry and stroke width. Straight paths retain segment geometry with `stroke_width` carried by `ObstacleSegment`; the obstacle index performs the half-width expansion. A closed path's conservative rectangular envelope expands its path-control-point bounds by `2 × stroke_width` on every side, covering square/round/butt caps and a miter join limited to four stroke radii. Fill-only paths use their unexpanded path bounds.
- A path whose curves cannot be represented by the obstacle primitives uses the convex control-point envelope, not a chord-only or endpoint-only box. This may conservatively reject a lane placement but cannot silently understate the emitted path extent.
- An `Icon` is treated as one visual slot footprint plus any stroke overhang. A raster icon reserves its complete placed viewport: alpha transparency does not create unmeasured holes. A vector icon reserves the union of its normalized path control-point bounds, transformed by the same contain/center scale and offsets that Layout places in its completed result. Each stroked path uses the normalized asset width multiplied by the same Layout `stroke_scale`; its own normalized cap/join is considered in the overhang. A vector path outside its viewport remains represented by its transformed geometry, not clipped by assumption. Scene does not transform path commands or scale widths.
- A hosted progress-fill rectangle is clipped to its planned/actual host in Scene. Its candidate footprint is the clipped visible rectangle, with its own stroke expansion only if the emitted progress primitive is actually stroked. It is not expanded again by the host mark's stroke.

For a segment, `ObstacleSegment.stroke_width` is the sole stroke carrier and coordinates remain the unexpanded centerline. For rectangular and compound envelopes, geometry constructors return already stroke-expanded bounds and use stroke-free `ObstacleRect` values. A footprint must never both inflate its coordinates and set a nonzero segment stroke width for the same emitted stroke. `SurfaceObstacle.clearance` remains separate collision policy; it is not folded into visible stroke bounds. A named mark-pair overlay may relax only the existing within-bundle mark collision rule; it does not erase either footprint, alter label geometry, or exempt later candidates/routes.

The `2 × stroke_width` path-envelope bound is deliberately conservative, not a claim that every rendered join has that shape. It is safe for the currently supported SVG miter limit of four when the adapter uses that limit; round/bevel joins and square/round/butt caps fit inside it. **Unverified compatibility gate:** the published Scene paint type carries cap/join but no explicit miter-limit value, and the current SVG serializer relies on the SVG default. Before B1b-2 implementation is accepted, architecture review and adapter evidence must establish that every admitted materializer has an effective miter limit no greater than four (or the envelope must be amended to bound the actual target). No larger or unknown miter limit may be assumed safe. The lane footprint cannot silently add a renderer-specific miter-limit paint choice.

## Mark-class matrix

| Semantic class | Final Scene geometry and style source | B1b-2 candidate footprint | Identity/overlay treatment |
| --- | --- | --- | --- |
| Planned task span | `Rect` from planned bounds; role from `planned` binding | Bounds plus one expansion for that role's stroke, if present | Primary item identity; no implied overlay |
| Planned point / unattached milestone | Layout-completed built-in `Symbol` or Theme glyph-part `Symbol` siblings; planned role | Union of every emitted part's footprint; built-ins use their actual symbol bounds/path, glyph parts use Layout-transformed path envelopes; each stroke included once | One semantic member with per-primitive identities; no duplicate lane candidate per glyph part |
| Point legend swatch | Same Layout-completed built-in or glyph-part `Symbol` geometry as its source/variant member mark | Same stroke-aware union, computed from the legend's own placed bounds and resolved variant | Preserve legend source, part order, `partN` identities, and paint order; never build a second geometry algorithm in Scene |
| Snapshot/scenario span or point | Same `Rect`/`Symbol` shapes using the baseline/snapshot semantic role and shape variant | Same rules as planned geometry using that concrete role and variant | Comparison facet of its source candidate according to the approved bundle contract |
| Closed Actual span or Actual point | `Rect` for a span or Theme-selected `Symbol` for a point using the `actual` role | Same shape-specific expansion using actual role metrics | Actual source/member identity; only approved same-object comparison overlay |
| Open Actual span | `Symbol`/path from the open-span geometry with `end_treatment: open` and the `actual` role | Path-control-point envelope plus conservative cap/join overhang, using resolved Theme stroke width once | Actual member identity and existing port identity retained |
| Missing-Actual mark | `Rect` at the existing scheduled anchor using `missingActual` role | Rectangle bounds plus one stroke expansion if that role is stroked | Missing-observation treatment is distinct from an Actual observation |
| Progress fill | `Rect` clipped to its host and styled by `progressFill` | Visible clipped subrectangle; apply only its own declared stroke, if any | Child visual of its host; no independent lane item or double host expansion |
| Attached point | Planned/Actual point class from its selected source and role; emitted as its own member | Same point rule, plus the attached member's own required text footprint | Retain child source/item/port identity and pin it to the host candidate's lane under #486 |
| Selected vector icon leading/trailing a member | Layout-completed `Icon` path primitives from normalized closure; Theme icon role supplies size/gap/scale, asset supplies per-path width/cap/join, ScenePaintResolver supplies paint | Transformed union of normalized control-point bounds plus per-path stroke overhang; include placed slot viewport for the complete icon visual | Keep asset identity and visual request identity; include as a separate required member visual, never flatten its paint into mark style |
| Selected raster icon leading/trailing a member | `Icon` with verified raster payload and placed viewport | Complete viewport rectangle; do not inspect alpha or infer a smaller painted shape | Same identity rule as vector icon |

The matrix is limited to emitted geometry that contributes to a lane candidate. Dependency paths and relation terminals remain in the route geometry/obstacle contract, not in the candidate mark footprint. A summary bar is not introduced by non-hierarchy grouping. Delta/title text remains measured as text, never expanded as mark stroke. The same Layout-completed path geometry must be used by candidate collision checks, final ports/painted primitives, and final obstacle registration; there is no Scene-side geometry re-derivation.

## Failure, determinism, and migration

Missing required Theme geometry, unsupported geometry commands, non-finite scale/width, or a role/primitive pairing that cannot be represented by the matrix fails before allocation with a stable Layout diagnostic (`E_LAYOUT_LANE_FOOTPRINT_UNAVAILABLE`, with source/role context). Invalid Theme values retain their existing Theme diagnostics. No generic `ValueError` catch may turn malformed geometry into “no lane fits,” and no incomplete member may be omitted. The public lane guard remains closed.

The mapping is deterministic from the immutable projection, resolved Theme/FontMetrics/icon closure, seed scale, and normalized source geometry. Theme/Scheme color changes cannot affect the candidate footprints; a geometry-bearing Theme change may alter them and therefore lane membership. Strokes are expanded once by the Layout conversion boundary. The Scene builder consumes the exact Layout-completed paths and identities and invokes `ScenePaintResolver` for paint; it does not rebuild geometry, lane membership, or stroke scale from Scene paint or an SVG scan.

No View, Project, Actual, Scene, serialized Scene, or adapter schema changes are authorized. Existing `automatic` and `explicit` behavior and output bytes remain unchanged across the geometry-ownership migration. Lane-only allocation may change when previously unexpanded strokes are first included; old lane counts, membership, and route diagnostics are not carried forward as acceptance evidence. B1b-2 tests must cover the matrix and byte-characterize automatic/explicit materializers. Subsequent B2/B3/L3c plans must rerender current evidence and attribute membership or route changes before activation.

## Alternatives rejected

- Calling the Scene paint resolver from Layout would make Layout a paint-conversion authority and introduce color policy into geometry.
- Keeping Theme glyph-outline construction or normalized icon path transformation in Scene would leave collision-relevant geometry under Scene ownership after Layout had completed placement.
- Mutating a completed `ScenePaint` in a helper after `ScenePaintResolver` would create a second paint-conversion authority.
- Using a raw `ScenePaint` as mapper input would reverse the current boundary and couple the allocator to Scene internals.
- Expanding both a segment's coordinates and its `stroke_width` would count stroke twice; carrying stroke in neither would understate its visible extent.
- Treating every icon as only a glyph center point would ignore its measured viewport and stroke; treating raster alpha as transparent collision space would require an undeclared image-analysis policy.
- Dropping unrecognized roles or catching generic geometry errors as a rejected lane candidate would permit hidden/incomplete content and unstable membership.

The prior [B1b-2 plan](../planning/active/issue-467-l3b-b1b-2-stroke-aware-footprint-design-plan-2026-09-27.md) remains the discovery record. All six #467 and three #494 literal acceptance criteria are unchanged and remain open; this correction establishes a design contract, not implementation or issue acceptance. The implementation plan must name the internal ownership migration from `scene/mark_geometry.py`/`v05_builder.py` to Layout-produced path placements and the resolver API extension before code begins. It must byte-characterize automatic/explicit materializers, point legend swatches, and material-icon SVG/materializer outputs while preserving glyph contain-center fitting, `paint: none`, part ordering/IDs, close-point conversion, float arithmetic, the built-in diamond outline override/glyph exception, and normalized vector icon cap/join/stroke-scale behavior.
