# Design — PR pytest speed and balance (#657)

**Plan:** [design plan](../planning/active/issue-657-pr-pytest-speed-design-plan-2026-09-30.md) (measurements, acceptance, decisions D1 to D6).
**Review:** [architecture review](../reviews/current/issue-657-pr-pytest-speed-architecture-review-2026-09-30.md).

This design changes the test suite and how CI selects and splits it. It changes no product behaviour, no schema and no public artifact. The living specifications are untouched; the only normative text added is the AGENTS.md paragraph of I657-4.

## 1. Split the monolithic test and give the shards timing data (D5, first half)

- `test_default_draft_and_presets_draw_a_distinct_axis_band` becomes one parametrized test over `["default", *library ids]` (8 ids from `library.yaml`, read at collection time like `test_axis_cells.py` does). The body is the current loop body for one id: render, then the same two assertions on `_band_contrasts(scene)`. No assertion changes and nothing is dropped; an id added to `library.yaml` is covered automatically, as today.
- `.test_durations` is committed at the repository root and consumed by the existing shard command with **no workflow change**, because pytest-split reads `.test_durations` from the rootdir by default. It is generated by `pytest -n 4 --store-durations` on a CI runner (never a loaded developer laptop) so that its numbers describe the machine that consumes them.
- Test ids that do not yet exist in the file fall back to the average, so a new test never breaks the split. Entries for deleted tests are inert. The refresh (section 4) prunes them with `--clean-durations`.
- Timing noise: `least_duration` only needs relative weights. It does not need exact times, so a quarter-refresh cadence is enough once the big tests are split (the largest remaining single test is about 85 s, which is below the 150 s target and below a third of a shard).

## 2. Shared render cache (D1, D2)

A new module `tests/support/render_cache.py` (its own module, so it never collides with `tests/support/synthetic_review.py` of #575) and a root `tests/conftest.py` that only exposes the fixture.

**What is cached.** One CLI render of an *unmodified committed input*: `chrona render <project> [--actual <actual>] [--preset <copied preset>] [extra flags]`, run in-process by calling `chrona.app.cli.main` exactly as the tests do today, with the same `sys.argv` shape. Presets are obtained by `chrona preset copy <id>` once per id into the cache directory and rendered with `--preset <dir>/preset.yaml`, which is what all current consumers do.

**Key** (`RenderKey`, frozen dataclass): repository-relative project path, actual path or `None`, preset id or `None`, sorted extra flags, plus a SHA-256 over the bytes of every input file the key names. The digest makes a modified input a *different key*, so a stale hit is impossible even if a test edits a file it should have copied. `render()` refuses any path outside `examples/`, `src/chrona/resources/` or the starter produced by `initialize_project` in the cache directory: a `tmp_path` file cannot enter the cache by accident.

**Result** (`RenderResult`): `svg: bytes`, `scene_text: str`, `stdout: str`, `stderr_lines: tuple[str, ...]`; properties `scene` (a fresh `json.loads` on every access) and `warnings` (a fresh list of parsed JSON-line diagnostics from stderr, the exact shape the tests parse from `capsys` today). Immutable bytes and strings plus copy-on-read mean one test cannot alter what another test sees. Diagnostics are captured with `contextlib.redirect_stdout/stderr` inside the render, not `capsys`, so a session-scoped fixture can produce them.

**Sharing across xdist workers.** Under `pytest -n 4` each worker is its own process with its own session, so a plain session-scoped fixture would render once *per worker*. The cache therefore lives on disk under `tmp_path_factory.getbasetemp().parent / "chrona-render-cache"` (the directory shared by all workers of one run; identical to `getbasetemp()` without xdist):

- an entry is a directory named by the key digest holding `scene.json`, `out.svg`, `stdout.txt`, `stderr.txt`;
- a worker that misses creates `<digest>.lock` with `os.open(..., O_CREAT | O_EXCL)`, renders into `<digest>.tmp/`, `os.replace`s it into place, appends one line to `renders.log`, and removes the lock; a worker that finds a lock polls until the entry appears (bounded, 300 s, then fails loudly rather than rendering a duplicate);
- `O_EXCL` files and `os.replace` are portable to the Windows leg of the full-matrix job; `fcntl` and the `filelock` package (not a dependency) are not used.

**Render counter.** `renders.log` is the counter: one line per real render, holding the key digest and its readable form. The fixture exposes `render_counts() -> dict[RenderKey, int]` by reading it, so the count is correct across workers. The miss path raises if the log already lists its digest, so the invariant is enforced where renders happen, not only observed afterwards. The acceptance test is `tests/integration/test_render_cache.py::test_each_render_key_renders_at_most_once`: it requests one key from three tests' worth of call sites, asserts `render_counts()[key] == 1`, and asserts `max(render_counts().values()) <= 1` over everything rendered so far in the session. Because the invariant holds at any moment, the assertion is valid regardless of test order and worker.

**Session boundary, stated honestly.** "Session" means one pytest invocation including its xdist workers. The three CI shards are three invocations on three machines. A combination used by tests that pytest-split places in different shards is rendered once per shard that uses it (at most 3 times), not once overall. This is a property of sharding, not of the cache (review, finding 2), and the measured shard totals in the PR bodies show its size.

**Who may use it.** Only tests whose input is a committed, unmodified project and packaged preset. The migration list (I657-2) is exactly the tests that render HALCYON *with actuals* through a copied catalogue preset: the split monolith and `test_axis_cells.py` (8 plus 1 tests). Tests that modify their input (`test_cli` margin sweep, `test_planned_mark_shadow…`), that render without actuals (`test_project_generic_presets`), or that call `render_review` with explicit view/theme/layout/scheme (`test_render.py`), render their own input as today. They do not become cache users just to share a name; converting them is a matter for the corpus/synthetic work of section 3.

## 3. The `corpus` marker and synthetic PR-path tests (D3, D4)

**Definition.** A `corpus` test exercises committed corpus material as a whole (all contexts, all presets on HALCYON) as evidence, or renders a corpus project to check a rule for which a synthetic PR-path test exists. AGENTS.md already states that corpus output is evidence, not an oracle, and that core rules are tested with synthetic fixtures; this section applies that rule to CI time. A test that is the *only* PR-path test of a rule is never marked `corpus`.

**Marker.** Registered in `pyproject.toml` (`markers = ["corpus: whole-corpus sweep; excluded from PR shards, run on main, nightly and manual runs"]`) in I657-3a. Registering it changes nothing at run time, so the marker and the tests can merge before any selection (I657-3a), and selection is a one-line workflow change (I657-3b).

**Selection.**

| Run | Command | Corpus tests |
| --- | --- | --- |
| PR code shards (`pr-pytest`) | `pytest -n 4 --splits 3 --group N --splitting-algorithm least_duration -m "not corpus"` | deselected |
| `reproduction-newest-python` (every code PR) | unchanged, explicit node id, no `-m` | `test_declared_examples_reproduce_by_public_cli` still runs (Python 3.12) |
| `full-matrix` (schedule, dispatch, post-sync dispatch after each push to `main`) | unchanged `pytest -n 4`, no `-m` | run on three OSes |
| Local | unfiltered by default | run; developers may add `-m "not corpus"` |

Because `addopts` is not set, the full-matrix job needs no edit for corpus tests to run there; a guard test (I657-3b) parses `conformance.yml` and fails if a shard command lacks `-m "not corpus"` or the full-matrix command gains any `-m`, so neither side can drift silently.

**Synthetic PR-path tests.** Each `corpus` decision in I657-3a is recorded in a rule table (in the PR body and the implementation plan): rule, what was HALCYON-only, the synthetic PR-path test, and the corpus test that remains. The synthetic project is built with the small builders #575 lands in `tests/support/synthetic_review.py` when they exist; until then, with the `chrona init` starter (already a committed, packaged, small project) and, where a date span matters, a small dictionary-built project written into `tmp_path` by a helper local to this issue (`tests/support/axis_projects.py`). The synthetic project must reproduce the *condition* of the rule (for the margin sweep: a planned span of several months across the same window and each catalogue preset's axis tiers), not just render without error. Each synthetic test records a mutation check in the PR body (re-introduce the #482 defect or its equivalent and see the test fail).

**Initial candidates** (final list decided per test in I657-3a; anything without a defensible synthetic test stays on the PR path and is reported):

| Candidate | Worker s | PR-path replacement |
| --- | --- | --- |
| `test_declared_examples_reproduce_by_public_cli` | 53 | none needed in shards: the same test runs on every code PR in `reproduction-newest-python` |
| `test_cli_margin_days…[*]` HALCYON leg | about 330 | synthetic project across all 7 presets (starter leg already exists) |
| `test_closure_inputs_are_read[*]` context sweep | 86 | to be audited: needs a synthetic closure whose every declared input is read |
| `test_attached_milestones` | 112 | audited against #575 I575-2/4 (data restoration pending) |

## 4. Refreshing `.test_durations` automatically (D5, second half)

A dedicated workflow `.github/workflows/test-durations.yml` (not a job in `conformance.yml`, so a duration-job failure never reddens the release matrix) with `schedule` (weekly, Monday 05:00 UTC) and `workflow_dispatch`:

1. checkout, `pip install -e '.[dev,render]' -e packages/chrona-fonts-noto-cjk`;
2. `pytest -n 4 --store-durations --clean-durations` (unsharded, unfiltered, so corpus tests have entries too);
3. if `.test_durations` changed, push branch `bot/test-durations` and open or update one PR titled `Refresh .test_durations (I657-4)` whose body says `Refs #657`, with `contents: write` and `pull-requests: write` limited to this workflow.

**Token decision for the lead.** A pull request opened with `GITHUB_TOKEN` does not trigger `pull_request` workflows, so the required checks (`derived-ready`, `pr-title`) would never appear and the PR could not merge. The job uses `secrets.DURATIONS_PR_TOKEN || github.token`. With the secret unset the PR is created but needs a maintainer to close and reopen it (or push an empty commit) to start checks. Creating the secret (a fine-grained token limited to this repository, contents and pull requests write) is an owner action and is *not* assumed. The alternative, extending the `derived-sync` route so the bot commits the file to `main` behind the derived gate, couples an unrelated file to the most delicate workflow in the repository and is rejected.

AGENTS.md (I657-4) gains one paragraph under "Publication and CI discipline": what `.test_durations` is, that shards read it, that the weekly job refreshes it, the local command for a manual refresh, and that a stale file only costs balance, never correctness.

## 5. Boundaries

- Tests, one `pyproject.toml` marker, two workflow edits (shard `-m`, refresh workflow) and one AGENTS.md paragraph. No product code. No schema, specification or public artifact.
- The routing hot spot (plan, measurement C) is a product change and stays out. It is the largest single lever on test time and is proposed as a successor issue in the final report.
- `conformance/run_conformance.py` (about 35 s in `pr-conformance`) is not part of this issue.
- Corpus data, `examples/` and generated evidence are not edited.
