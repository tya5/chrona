# Design — Collision-Aware Lane Rows (#467)

**Status:** selected design, subject to the architecture review linked below.
**Plan:** [#467 design plan](../planning/active/issue-467-lane-packing-design-plan-2026-09-26.md).
**Prerequisite:** [#466 shared-obstacle design](issue-466-general-placement-design-2026-09-26.md), obstacle-only stage. This design does not declare #466 complete or authorize its later candidate/tail grammar.
**Target:** the Transit Map research board is inspiration for density, not a table-timeline byte target.

## Use cases and owned facts

`rows.mode: lanes` packs selected primary Review Items inside their View-derived group while preserving every item's semantic identity, baseline/actual placement, name and selected finish delta. A group can require several lanes. `automatic` remains the exact one-object-per-row composition and its old table/label policy is not reinterpreted. Authored `explicit` row membership, order, group and table subject remain View facts; Layout may share a member subtrack when its completed footprints do not collide. Hierarchy grouping retains parent/child row semantics and is not admitted with `lanes` in this version. A hierarchy slide such as HALCYON 06 remains `automatic`; 01, 02 and a non-hierarchy third slide provide the three lane examples.

Project and Schedule own dates and dependency meaning. View owns selection, grouping, authored explicit membership, lane/table/label intent, and immutable source references. Projection keeps stable selected Review Items and group keys; it does not invent packed row geometry or lane ordinals. Layout owns measured footprints, group-local lane assignment, final row and track geometry, labels, ports, routes, and completed table content. Scene projects completed placements; adapters serialize. Theme owns text/mark treatment, not assignment.

## Versioned View contract and migration

Introduce `chrona/view/v0.23`, preserving v0.22 as a frozen accepted contract. In v0.23, `rows.mode` is `automatic | explicit | lanes` and remains required: a schema default is not inferred for an existing immutable View. `lanes` requires selection, grouping, ordering and window like `automatic`, forbids `rows.items`, `rows.points`, hierarchy grouping, `hierarchyColumn`, and item-oriented `tableColumns`, and is table-timeline-only. `explicit` and `automatic` retain their v0.22 validation and exact output for unchanged resources. A v0.23 `lanes` View requires `visibility.labels` with `placement: plot`, `content` containing `title`, and `overflow: visible-overflow`; `finishDelta` is required in label content whenever a table delta column is removed from a migrated View that promises visible deltas. The renderer never silently promotes `suppress` or `table` to a different policy.

`rows.laneTable` is a finite row-summary declaration, required only for `lanes`:

```yaml
rows:
  mode: lanes
  laneTable:
    label: group          # group | lane
    count: true           # optional; default false
```

The lane table has one `Lane` column. `group` prints the resolved group title on the first lane of each group and an empty cell on later lanes; for `grouping.by: none` it prints the View's finite ungrouped label (`Ungrouped` by default). `lane` prints the stable lane representative's item title, not a transient ordinal. `count: true` adds a second `Items` column with the number of selected primary items on that lane. These are aggregate/identity facts, never a table subject's object facts. The left table does not implicitly carry dates, phases, WBS, variance or observation status. Migration of 01/02/third slide must explicitly choose which facts move into plot labels and which are intentionally removed, and record that decision in the release review. The row summary is not a substitute for each plotted item's visible name.

`visibility.labels.content` remains the finite existing vocabulary. For lane mode, a selected `finishDelta` is combined with the item's title in exactly one measured text placement and is not independently repeated. Items without a delta show a title only. `automatic` retains its original label and table semantics; v0.22 bytes are characterized independently. Default Draft and every packaged preset that points to it migrate together to v0.23 lane mode, with explicit `laneTable`, plot title/delta intent and regenerated output. Existing immutable Contexts are not rewritten merely to create a new default.

Invalid combinations fail at schema/normalization ingress (`E_RESOURCE_SCHEMA` for shape, `E_REVIEW_LANE_*` for cross-field rules) before Layout. A required name may never be suppressed by `W_LAYOUT_LABEL_SUPPRESSED`. If no collision-free lane exists, Layout creates a new lane. If no bounded text candidate fits even alone on the finite canvas, Layout emits the name with the declared visible-overflow warning and exact source text; it never drops the item. An invalid measured font or unbounded geometry remains a normal measurement error, not a visible-overflow success.

## Identity, grouping and stable assignment

Each selected item's canonical identity is `(source kind, stable object ID, View item ID)`; lane assignment must not change its source reference, projection-instance identity or primitive IDs. An automatic item instance uses its existing object identity. A generated lane row has a `lane:<group-key>:<representative-item-id>` identity, where the representative is the first item admitted to that lane. The identity does not include an array index, coordinate or lane count. The lane's visible order follows group order, then its representative's stable chronology key. Group-key encoding is collision-free and canonical, including a distinct ungrouped sentinel. A later unrelated item insertion cannot rename or reorder a lane whose members and predecessor closure are unchanged; insertion into the lane can change geometry, and a collision or predecessor-chain interaction can legitimately change its membership. This is the precise stability guarantee tested, rather than an impossible promise of globally fixed ranks under arbitrary insertion.

Within each group, candidates are traversed in `(planned start/at, planned finish/at, object ID, item ID)` order. For each item, Layout first tries the existing lane containing its unique eligible immediate finish-to-start predecessor, if the two marks touch or have nonnegative temporal gap. If several predecessors qualify, use stable relation ID then source item ID; if none qualifies or that lane collides, try existing lanes in representative order, then open a new lane. Dependency preference never overrides collision. No lane crosses a group boundary. Semantic relation routes are completed only after lanes and labels, so a route is not a packable item footprint; its endpoints and route still use the shared obstacle inventory. This finite first-fit rule is deterministic from closed inputs and cannot depend on hash traversal, local fonts or renderer dimensions.

The admitted footprint is the union of all renderer-neutral planned, snapshot/scenario, baseline, actual, progress and point-glyph stroke bounds, plus measured title/delta/icon-leading text and any local label connector. Ports carry clearance but do not block their own host. Two closed strokes may touch only when their effective stroke/clearance interiors do not intersect; calendar-interval equality alone is insufficient. A group may contain a milestone at a span boundary only if their measured mark and label geometries fit. Layout tests actual rectangles/segments through the one #466 `SurfaceObstacleIndex`, with the named host/port exemptions only. Background rows and group bands are not obstacles.

For each candidate lane, measure a small finite label ladder in the lane's local coordinate frame: adjacent-end, adjacent-start, then two staggered block offsets with short orthogonal leaders. Rank by declared order and deterministic distance/tie key. The staggered levels add to that lane's measured required block extent; Layout allocates full natural row height before final marks/labels are emitted. A label may not cover another packed mark or required label. A candidate that spills outside the plot is rejected unless it is the terminal visible-overflow placement; that terminal case records the overlap/overflow rather than hiding it. The accepted lane footprint is translated once when group rows receive final block positions. No 45-degree typography or SVG-only rotation is introduced; finite stagger is the selected solution for this version.

Explicit rows retain their authored `row_id` and member IDs. Their members are assigned to the first collision-free subtrack in authored order, considering the same measured mark/label footprints. A member's source kind or object type does not silently select a different algorithm. Declared `track: shared` means candidate sharing is requested and remains eligible for one subtrack; `stacked` means a dedicated subtrack as before. A primary/snapshot/actual comparison overlay of the *same semantic object* may explicitly share its host mark through the named host exemption; unrelated objects cannot use this exemption. Thus v0.22 explicit output is not changed; v0.23 explicit may opt into the collision algorithm only with a new explicit `rows.trackAllocation: collision` declaration. This avoids silently changing old authored compositions while satisfying the issue's explicit-row successor. If collision allocation cannot fit a shared member, it gets a new subtrack with natural row growth; never a suppressed name. `tableSubject` remains authoritative for explicit row cells.

## Closure order and failure behavior

The shared #466 obstacle stage must publish first. Layout then runs: (1) slot/scale and measured item candidate geometry; (2) group-local lane/explicit collision allocation, final row extents, marks and ports; (3) required plot labels and lane table cells, registering them in the same obstacle index; (4) dependency route and route-label placement around those labels; (5) annotation placement around marks, labels and routes. This order does not let a dependency route retroactively evict an item name. Route-overflow policy remains independently declared. The full #466 nearest-free annotation candidate schema is not a prerequisite for lane text: the bounded lane ladder is an internal Layout algorithm over the shared obstacle index, not a View-authored annotation grammar.

Measured row requirements feed the existing content-coherent host re-solve (#468), so table, timeline and later normal-flow slots grow together. `fill` distribution (#434) is used when available and does not alter lane membership. `rows.points: key-row` (#440) stays separate; no group-header point fold is silently reused. When labels force more than twelve lanes on the target fixture, the selected design's measured footprint or label strategy must be reviewed and amended before loosening acceptance or writing a HALCYON-specific exception.

## Acceptance evidence and adjacent impact

Tests cover neutral interval touching, point-glyph and actual/baseline collisions, label staggering, chain preference, group isolation, explicit collision opt-in, stable insertion, visible overflow, and unmodified automatic bytes. HALCYON 02 must show 26 selected items in at most twelve completed lane rows and the named chain in one lane. At least 01, 02 and one non-hierarchy slide must be committed as v0.23 lanes. Each packed name and applicable delta must be checked in actual SVG/PNG and Scene; generated diffs must explain removed per-item table facts. Public materializers and CI's full matrix gate release.

No Project/Schedule/Actual schema, immutable Context reference, Theme role or adapter-specific coordinate changes. The intended incompatibility is a new v0.23 lane View's row/table composition and default Draft output, not a reinterpretation of an existing `automatic` View.
