# Design — Actionable Unsupported Resource Versions (#489)

**Plan:** [design plan](../planning/active/issue-489-resource-version-diagnostics-design-plan-2026-09-27.md). **Authority:** [Issue #489](https://github.com/tya5/chrona/issues/489), [Specification 56](../specification/56-schema-authoring-and-diagnostics.md) and Specification 34 §8. This changes diagnostics, not supported resource versions or rendering semantics.

## Use cases and behavior

When a resource declares a string `version` unsupported for its known resource kind, ingestion refuses it before constructing any runtime contract or Scene. The stable code is `E_RESOURCE_VERSION_UNSUPPORTED`; `sourceRef` is the resource-local `/version`. The message names the resource kind and id, the found complete version, and the currently supported complete version(s), ordered lexically from the authoritative contract schema registry. Example: `view chrona-preset-mission-light declares chrona/view/v0.22; supported: chrona/view/v0.26`. The complete version, not `dict` or another Python type name, is the problem statement. The diagnostic does not claim an old version can be upgraded in place. The detector applies uniformly to every kind registered in `_SCHEMAS`; public CLI acceptance focuses on View, Theme and Layout Profile.

An unsupported *kind* remains a kind error. Missing and non-string `version` values remain on their existing malformed-envelope path (`E_CLOSURE_KIND` in the current parser); this issue does not rename or improve that path, and must not mislabel it as an older supported version. A supported version with an invalid body keeps the ordinary `E_<KIND>_SCHEMA` explanation at the failing body pointer. No fallback, closest-version parser, or implicit normalization is introduced. A later version-shape diagnostic can be designed separately without weakening this string-version rule.

For a stale member loaded from a local copied builtin preset, the CLI appends: `Run chrona preset copy <id> --output <new-dir>, then re-apply your edits.` The `<id>` is the catalogue id, not the resource id. An explicit user-supplied override that is stale gets the generic version message without a copy-again remedy, even if it is used alongside a builtin preset. A stale independently supplied resource gives the supported version and refers the user to the current resource schema/specification; it does not fabricate a builtin origin. The first three fields (code, versions, pointer) are invariant across all entry points; the remedy is contextual presentation.

## Ownership and transport

1. `contracts/resources.py` owns supported-version lookup and raises a typed version diagnostic carrying resource kind/id, found version, supported versions, and pointer. The single-resource parser and the validation-only collection use this same decision. There is one registry, not a second table of version strings.
2. The presentation collector records the typed version failure as one `PresentationDiagnostic` and continues collecting independent sibling failures. It must not let one stale resource bypass the established multi-resource diagnostic contract. The closure maps a single finding to `ClosureError` and preserves `/version`; the multi-finding path preserves the existing ordered diagnostic list. Snapshot and direct Draft paths preserve the same version code and pointer. Snapshot reference loading currently has early Layout Profile and Review Detail Profile version comparisons; those comparisons must stop masking the typed parser decision for a declared string version after reference identity/framing checks. They must not weaken the id or content-identity checks.
3. The closure knows whether a failure occurred while loading a member declared by a particular preset, and may carry that preset identity as non-rendered error context. It does not know or format CLI commands, does not import the builtin catalogue use case, and does not infer provenance from a resource id. An override is not a copied member.
4. The CLI verifies that the failed declared member belongs to a local preset whose id is `chrona-builtin-<catalogue-id>` and whose catalogue id is currently builtin, then formats the copy-again remedy. It does not rewrite source files and does not change `sourceRef`. The normal JSON diagnostic envelope (`status`, `code`, `component`, `sourceRef`, `message`) stays intact.

## Identity, privacy and migration

The found version comes from the declared YAML scalar; supported versions come from the registered `(kind, version)` pairs. A malformed or extremely long scalar and resource identity are described safely rather than echoed without bound. Resource identity comes from the existing closure identity and is included only when available. The pointer is local to the failing resource, as in Specification 56; no host filesystem path is emitted. For a copied preset, a *new directory* is suggested so edited files are not overwritten. Re-applying edits is explicit because incompatible fields may need manual migration. Existing stale files remain invalid, including historical View v0.22, Theme and Layout Profile copies.

## Architecture and extension boundaries

This is an ingress/CLI change. Project scheduling, View projection, Theme resolution, Layout geometry, Scene primitives, SVG adapter, resource identity hashing and generated art remain unchanged. Adding a future resource version requires registering its schema; the diagnostic automatically reports the new supported set. Adding a future copy/distribution mechanism may supply its own remedy through CLI provenance, without changing the version detector. The same typed diagnostic can be used by snapshot-based consumers without teaching contracts about local files.

## Acceptance evidence

Public CLI tests create a copied builtin preset, replace only its View/Theme/Layout Profile `version` with a stale string, then assert `E_RESOURCE_VERSION_UNSUPPORTED`, found and supported values, `/version`, the copy-again command, and no output artifact. A direct override test proves no misleading builtin remedy. Unit tests check unsupported-kind and malformed-version separation, collector continuation across sibling errors, supported-body schema behavior, and version registry derivation across registered kinds. Focused tests, diagnostic inventory, public materializer byte checks and the repository CI matrix gate release. The final review must copy all three literal issue acceptance criteria.
