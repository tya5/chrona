# Design Correction — Candidate Normalization Ownership (#466)

**Amends:** [candidate placement design](issue-466-candidate-placement-design-2026-09-26.md). **Discovered in:** C1 typed normalization before any C1 product-code publication. **Plan:** [implementation amendment](../planning/active/issue-466-candidate-placement-implementation-amendment-2026-09-26.md).

The original implementation outline placed legacy-rung expansion in `layout/placement_candidates.py`, which made View normalization import a Layout implementation helper. That creates an avoidable inward/outward dependency and blurs responsibility: translating a View spelling to an immutable candidate is not a geometry operation. The typed candidate values and the pure legacy expansion belong in `presentation/model/placement_candidates.py`, the shared contract between Review normalization and Layout. Review invokes the expansion before Layout ingress; Layout consumes only typed candidate values and may insert the already declared preferred legacy candidate using the same pure function for direct lower-level fixture inputs. Geometry, obstacle queries, candidate search and routing remain exclusively in Layout.

This correction changes no resource syntax, search policy, public byte expectation or migration. C1 retains the exact v0.22 order and output; v0.23 declared candidates bypass legacy expansion. A structural test should reject `review/v05_content.py` importing `layout/placement_candidates.py`. The whole-architecture boundary remains Project → View/Review normalization → immutable model intent → Layout geometry → Scene projection → adapter serialization.
