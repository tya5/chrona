# Issue 370 — Resolvability quality gates design

## Decision

Chrona adds a repository-quality policy, not a product-runtime policy.  Four
deterministic tools derive bounded populations from source, public CLI metadata,
documentation, and regression-corpus manifests.  A single checked-in policy
document records the maintainer decisions that cannot be inferred safely.  The
tools report every member of their population and fail only for a missing,
stale, or internally inconsistent decision.  They never execute product input,
change a diagnostic at runtime, or make generated documentation an evaluation
input.

The policy is `conformance/resolvability-quality-policy-v0.1.yaml`.  It is a
quality-control input rather than a public resource schema: it is read solely
by `tools/`, is versioned, and has no import path into `src/chrona/`.

```text
source / CLI parser / corpus manifests
              |
              v
       derived population tools -----> generated Markdown inventories
              |                                  |
              +---- checked policy classifications+
              |
              v
          conformance gate
```

## 1. Diagnostic actionability

`tools/diagnostic_inventory.py` parses every Python file below `src/chrona`
with `ast`.  A diagnostic construction is a call or `raise` containing a
literal string whose first token is an `E_` or `W_` identifier.  The inventory
records its code, stable source location, constructor form, inferred layer,
and whether that construction supplies a non-code detail argument.

The parser deliberately does not attempt symbolic execution.  It recognizes
the repository's diagnostic conventions (`Diagnostic`, `CliFailure`, and
exceptions exposing a code plus optional detail/message) by call shape.  An
unrecognized literal diagnostic is still listed as `unknown-form`; it cannot
silently disappear from the population.

Layer is a source-boundary fact, not an exception-class guess.  The policy
defines the product ingress prefixes (`app`, `usecases`, `operational`,
`storage`, `presentation/model/closure`, and `presentation/contracts`); all
other paths are internal.  For each ingress construction the gate requires a
detail-bearing form.  The only exception is a policy `bareDiagnostic` entry
with the exact code and a reviewable reason establishing that the identifier
itself is the complete user message in every bare ingress use.  The report
retains every source site, so a code-level classification is visible and a
code whose meaning varies by site must gain detail rather than use a generic
allowlist reason.

The non-gating report is committed at
`docs/diagnostics/inventory.md`.  `--check` compares generated bytes, so both
new constructions and changed classifications appear in review.  The report
includes all layers; the gate is deliberately narrow because internal
invariants may validly use an identifier-only exception before a caller adds
context.

## 2. Declared versus computed values

The same tool family provides `tools/declared_value_inventory.py`.  It uses a
conservative intraprocedural AST data-flow rule: a comparison is in scope when
a declared document/reference value reaches an equality comparison with a
value produced by an identity function or a variable whose producer is
`content_identity`, `sha256`, or an `*_identity` computation.  The report
contains both expression anchors, the enclosing function, and the declared
field path where statically recoverable.  It is an inventory rather than a
claim that every comparison should be removed.

Each reported site has exactly one policy record:

| Classification | Meaning | Required evidence |
| --- | --- | --- |
| `pinned-deliberately` | User supplied bytes are immutable evidence and comparison is an assertion. | Exact public CLI producer command for the value. |
| `product-bookkeeping` | The product already knows the value and the author should not reconstruct it manually. | Resolver/refresh command or an explicitly named follow-up issue. |

The source anchor is `path`, enclosing `function`, and declared-field label;
line numbers are report-only and never policy identity.  A missing site, a
stale policy record, an unknown classification, a missing producer, or a
producer that does not exist in the live argparse tree fails the gate.  This
preserves immutable closure and snapshot assertions while exposing the places
where product bookkeeping needs a public resolution path.

## 3. Documentation is executable CLI evidence

`tools/check_documented_commands.py` has two distinct inputs.

1. It extracts shell command blocks and inline `chrona …` invocations from
   `README.md` and `docs/guides/`, joining shell continuations and retaining
   document/line provenance.  It tokenizes with `shlex` and validates each
   command, nested subcommand, option, option value, and parser `choices`
   against the live `_parser()` metadata.  It does not invoke the command.
2. It derives the public argparse command and option population.  Every
   public command/option must have a documentation classification: a matching
   documented invocation or a narrow policy `undocumentedCliSurface` record
   with a reason.  This is the reverse gate that prevents a shipped option
   such as `--viewport …xauto` from becoming invisible.

The policy separately names the one fresh-project sequence published in the
README.  `tools/wheel_smoke.py` executes that sequence from an empty temporary
directory after wheel installation: `chrona init`, then its documented
`chrona materialize` command.  Its paths are constructed only from the
temporary directory and it asserts exit status and output existence.  The
repository documentation remains explanatory input to this test; no runtime
code reads it to decide how to render or materialize.

## 4. Corpus magnitude

`tools/corpus_coverage.py` remains the owner of corpus discovery.  It gains a
per-manifest magnitude table derived from declared Project and Context inputs:

- Project objects;
- projected rows (declared objects, before a renderer-specific layout);
- declared relations;
- scheduled segments, where a segment is a declared dependency or explicit
  schedule interval rather than an SVG primitive.

`resolvability-quality-policy-v0.1.yaml` names each contract limit and the
minimum corpus magnitude expected to exercise it.  The report shows facts and
the threshold that each project satisfies; the gate rejects an absent contract
classification or a declared threshold with no qualifying corpus project.
Feature coverage remains non-gating curation information.  Magnitude limits
are only an acceptance assertion for an already-declared product limit; the
policy cannot invent a rendering limit or turn a corpus fixture into runtime
configuration.

## Architecture and authority review

| Boundary | Owner | Decision |
| --- | --- | --- |
| Product diagnostics | Core/use case/adapter that detects the condition | Tools inspect construction; they do not format or replace diagnostics. |
| Immutable identities | Core identity and closure/store boundaries | Classification protects deliberate assertions; no gate derives or weakens an identity at runtime. |
| CLI grammar | `chrona.app.cli._parser` | Documentation checker reads parser metadata; documentation cannot define commands. |
| User documentation | README and guides | Commands are evidence subject to validation; it is not executable product configuration. |
| Corpus meaning | manifests, Project, Context, and corpus coverage tool | Scale is derived from declared semantic facts, never Scene/SVG geometry. |
| Human policy | checked conformance policy | Explicit classification only; no broad suppressions or inferred exemptions. |
| CI | conformance and installed-wheel smoke | Quality checks run before full tests; fresh sequence runs only after wheel installation. |

This preserves `Project → View → Layout → Scene → renderer`: none of the four
tools gains a route into any presentation layer.  It also preserves the
application/use-case boundary: argparse remains an adapter, and tool policy
does not leak into public schemas or product behavior.

## Migration and acceptance

The first rollout inventories the current tree before enforcing the narrow
gates.  Existing bare ingress constructions and identity comparisons receive
an individual classification; unjustified bare constructions are changed to
emit relevant detail rather than hidden behind an allowlist.  No compatibility
alias or old policy format is retained.

Completion requires committed current inventories, focused negative tests for
every gate, conformance execution, full pytest, public materializer checks,
wheel smoke of the fresh sequence, generated-report diff review, and CI on
the three supported operating systems.
