# Design — Minimal `chrona init` and Explicit Corpus Example (#376)

**Status:** Proposed for architecture review.

## Decision

`chrona init DIRECTORY` creates the smallest editable draft project: exactly
`project.yaml`, `actual.yaml`, and `README.md`.  The Project contains two
fixed-span tasks and one fixed-point gate; the Actual set contains observations
for those same objects.  The README identifies both documents as the user's
source and makes the packaged `chrona-default-draft` preset explicit in the
render command:

```console
chrona render project.yaml --actual actual.yaml --viewport 1600xauto --output plan.svg
```

The command relies on the public #377 no-flag draft-default contract.  It does
not copy View, Theme, Color Scheme, Layout, or a private preset document.  A
user who wants a named or changed appearance can supply `--preset` or an
explicit member as documented by `chrona render --help`; that is draft
selection, not source generated by `init`.

`chrona init DIRECTORY --example halcyon-1` remains the explicit way to create
the complete regression corpus.  `--example` has no default.  This deliberate
CLI break removes the old ambiguity: a caller either asks for an editable
starter or names the corpus it wants.

## Source and runtime authority

The editable starter has no Store and no immutable closure.  It has no
materializer manifest because a draft render is intentionally not reproducible
evidence.

The explicit HALCYON example retains its source tree, manifest, Contexts, and
declared generated evidence.  During initialization, its Context closures are
copied under `.chrona/store/`, and `.chrona/store.yaml` names that directory as
the sole local Store root.  Context references continue to identify the same
opaque revisions and resource addresses; only the local filesystem adapter's
root changes.  Therefore the visible root contains authored corpus source and
evidence, while revision directories are hidden runtime state:

```text
halcyon-1/
  project.yaml, actual.yaml, manifest.yaml, contexts/, generated/, ...
  .chrona/
    store.yaml                 # local Store configuration
    store/revision-example-v1/ # immutable closure
    store/revision-.../        # baseline closure when declared
```

`initialize_project` is the one application-service boundary that selects a
template and prepares any required Store state.  Template lookup remains in
`chrona.resources`; Store snapshot creation remains in
`copy_context_closure`; CLI parsing merely passes the explicitly selected
mode.  No renderer, draft closure resolver, Context schema, or Store reader
learns about an init mode.

## Resource topology

The minimal template is a wheel-owned resource below
`src/chrona/resources/templates/minimal/` and is force-included in the wheel.
It is deliberately not an `examples/` corpus: it has neither manifest nor
generated evidence.  A dedicated minimal-template resource accessor makes
that distinction type-visible instead of weakening `template_resource`, whose
contract remains "a full named example with a manifest."  The existing
HALCYON example lookup remains the named-example accessor.

All template copying remains byte-preserving and non-overwriting.  An existing
non-empty destination rejects before any write; an absent or empty destination
is allowed.  The public diagnostic stays `E_INIT_OUTPUT_EXISTS`.  Unsupported
named examples retain `E_INIT_EXAMPLE`.

## Documentation and evidence

The root README replaces the old default-init materializer example with the
minimal init/render route, explains that `plan.svg` is a Draft, and places the
full corpus materialization command under the explicit `--example halcyon-1`
route.  A focused guide owns the complete three-file listing, the one render
command, and the escalation route to an explicit preset.  The generated CLI
reference reflects an optional `--example` rather than implying HALCYON is the
default.

Tests prove the default tree is exactly readable starter source and renders via
the public CLI; a separate test proves the named full example is
Store-resolvable with all closure directories below `.chrona/store`.  Existing
public materializer checks continue to prove corpus evidence, rather than
turning a starter Draft into evidence.

## Non-goals and migration

This does not introduce theme/view inheritance, a preset registry selector,
package acquisition, mutable-source Store fallback, or terse Project syntax.
It intentionally does not preserve default HALCYON generation: automation
requiring the corpus must pass `--example halcyon-1`.  The ordinary four-member
and `--preset` render forms remain governed by #377 and are unchanged.
