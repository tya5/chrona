# Issue 369 — Guided authoring revision recovery design

## Decision

Guided authoring workspaces use a workspace content identity as a local-file
compare-and-set precondition. That identity is not a Revision Store token and
must not be discovered by intentionally failing a mutation. The public CLI
therefore gains:

```text
chrona workspace revision WORKSPACE
```

It validates and reads the workspace, writes exactly its current
`sha256:<digest>` content identity plus a newline to standard output, and has
no mutation or Store dependency. An author obtains this value before composing
the first authoring command, then chains accepted `resultRevision` values.

## Authoring result contract

Authoring command results become an explicit
`chrona/authoring-command-result/v0.1` contract. They contain:

| Field | Meaning |
| --- | --- |
| `commandBaseRevision` | The precondition supplied in the command. |
| `workspaceRevision` | The identity observed before validation/writing. |
| `resultRevision` | The identity after an accepted write; `null` on rejection. |

`baseRevision` is not emitted in this result. It previously held the observed
workspace identity on rejection, which falsely looked like an echo of the
input. The new names make stale state observable without disguising its
provenance. This is an intentional clean contract correction; no compatibility
alias is retained.

An `E_AUTHORING_BASE_REVISION` diagnostic includes a stable human detail and
machine-readable `expectedRevision` and `receivedRevision` fields. The
expected identity is `workspaceRevision`; the received identity is
`commandBaseRevision`.

## Boundary with general Commands

The generic Command Model continues to use an opaque Revision Store token.
Its `baseRevision` is untouched. Specification 10 is amended to define a
target-specific equivalent precondition, while preserving the Store-token rule
for canonical Store mutations. Specification 51 names the workspace content
identity as that equivalent precondition for `authoring-command/v0.1` and
links to the public revision operation. Specification 35 remains scoped to
`command/v0.2` and is not generalized to workspace files.

## Initialization and materialization

`chrona init` copies Contexts whose local Store identity is
`halcyon-1-example`; its generated `.chrona/store.yaml` must declare exactly
that identity. It also materializes the local immutable snapshot closure named
by those Context references at initialization time. The identity is a selector,
not a per-directory nickname, so the copied Contexts remain valid without
rewriting their immutable references or falling back to mutable source paths.

Materialization remains strict: generated bytes that differ from declared
evidence fail unless the caller explicitly supplies `--write`. The materializer
raises a typed, caller-facing mismatch diagnostic whose detail directs the
author to review the diff and rerun the same materialize command with `--write`
only when refreshing intended evidence. The use case remains free of CLI
formatting; the CLI maps its typed code/detail to the standard diagnostic
envelope.

## Architecture review

| Boundary | Decision | Review result |
| --- | --- | --- |
| Core identity | `content_identity` remains the one canonical codec. | No duplicate hashing policy. |
| Authoring use case | Reads/validates workspace and produces typed authoring result. | Does not inspect CLI or Store configuration. |
| CLI | Exposes revision inspection and emits standardized failure envelopes. | Read-only inspection cannot mutate a workspace. |
| Operational Store | Generic command token semantics remain opaque and unchanged. | No workspace rule leaks into Store commands. |
| Local initialization | Config identity and emitted immutable snapshot closure match copied Context references. | No Context rewriting or mutable-source fallback. |
| Materializer | Byte mismatch stays a failure; remediation is presentation at CLI boundary. | No silent evidence refresh. |

## Acceptance evidence

1. A fresh workspace revision can be read through the public CLI and used for
   an accepted first command.
2. A stale command reports both identities, with no misleading `baseRevision`
   result field.
3. Japanese content continues to use the same canonical identity.
4. `init` output resolves a copied Context through its generated Store config.
5. A changed artifact fails without `--write`, emits refresh guidance, and is
   regenerated only with the explicit flag.
