# Design Correction — C4 Note Contrast Closure (#466)

**Corrects:** C4 contract and review targets in the [design plan](../planning/active/issue-466-c4-contrast-closure-design-plan-2026-09-27.md). **Predecessors:** [candidate placement design](issue-466-candidate-placement-design-2026-09-26.md), [#465 image-container amendment](issue-465-image-annotation-container-design-amendment-2026-09-27.md), and [#478 role-admission rebase correction](issue-478-role-admission-rebase-correction-2026-09-27.md). **Review:** [whole-architecture review](../reviews/current/issue-466-c4-contrast-closure-architecture-review-2026-09-27.md). This document defines the design gate; it does not authorize implementation.

## Decision

The semantic registry classifies `annotation-note-text` as `STATE_TEXT` and `annotation-note-box` as `DECORATION`. For already classified roles, `resolve_theme` checks the declared `contrastTreatment` and compares resolved fill/opacity against the resolved Scheme `surface`; `evaluate_scene_contrast` independently checks completed text paint against its Scene ground. Adding note text to `STATE_TEXT` activates those existing checks for the note role. The authored role declares `contrastTreatment: required`, giving it a 4.5:1 floor at both boundaries. Note prose has no semantic state that justifies `deemphasized`; using that value would weaken the existing state-text guarantee without an authoring meaning. The box classification applies the existing 1.10:1 decoration visibility floor and contributes a new role to the corpus-wide decoration witness.

The effective Theme migration is six authored Theme roots: `src/chrona/resources/presets/bundles/executive-light/theme.yaml`, `examples/halcyon-1/themes/wallboard-image-notes.yaml`, and `examples/controller-z/themes/{progress-track,axis-tiers,capabilities,executive-light}.yaml`. Each directly declares both note roles and resolves their colors through Scheme targets. Add `contrastTreatment: required` to each note-text binding in the same atomic slice that classifies it. Do not add treatment to the note-box role or to Scheme color targets. Base/derived Theme closure must retain declaration provenance and continue checking the declared text treatment while resolving the effective fill.

This migration adds one direct property-admission requirement to #478: `annotation-note-text` must register `contrastTreatment` as a Scene state-text/contrast-policy capability. The current role registry admits that property only for the four existing state-text roles; its current annotation-text family registration admits only text paint. The implementation must update the role capability registry in the same slice as the semantic class and six declarations. The existing Theme-closure treatment and numeric-floor implementation is reused; no second Scheme-surface contrast formula is introduced. The existing exact-pointer rule applies to direct declarations and Scheme target failures; the treatment error points at `/body/roles/annotation-note-text/contrastTreatment`.

## Ground, pair, and paint contract

For each note-text primitive, Scene contrast evaluation uses the topmost prior completed opaque `Rect` or `Symbol` containing the policy sample point, under the existing [#459 ground rule](issue-459-opaque-gradient-ground-correction-2026-09-26.md). In the paired annotation output, this is the note box. Its `fill` is the authoritative declared representative content-area color, including when `annotationContainer.outline` is `image`; the image payload is not sampled. The same resolved representative fill is the paint input to perceptibility. SVG, PNG, and typeset adapters serialize the completed image and fill facts and do not repair contrast.

The representative ground supported by the current contrast kernel is an opaque flat six-digit color. Scene opacity belongs to `paint.opacity`; a host with opacity other than 1 is explicitly unsupported by `_ground_under`. In contrast, a prior Rect with no fill is skipped, after which the current generic search can select a lower host or canvas. C4 therefore adds two explicit guards: after Theme inheritance and Scheme insertion, closure requires the effective `annotation-note-box.fill` to resolve to an opaque color and its effective opacity (defaulting to 1) to equal 1; missing or non-opaque values fail with new `E_SCHEME_ANNOTATION_NOTE_GROUND` at the exact role property pointer. In completed Scene evaluation, every `annotation-note-text` must have a prior `annotation-note-box` with the same `sourceRef`, containing its policy sample point and carrying opaque flat fill. A missing pair/fill must produce `E_SCENE_CONTRAST_GROUND_UNSUPPORTED` instead of falling through to an unrelated host or canvas. These are new C4 validation rules; they close paths that current generic `_ground_under` does not reject. A transparent/partially opaque box cannot be treated as if its raw color were the visible ground: compositing it over its own underlay would require a separately specified, renderer-neutral host-composition rule. The six audited roots currently bind note-box fill to opaque Scheme colors.

Annotation note text and box are paired by the current Layout presentation (`AnnotationPresentation("note", ..., "annotationNoteBox", "annotationNoteText", ...)`) and Scene construction emits the box before its text. The contract is about that completed Scene paint order, not an adapter convention. For classified `annotation-note-text`, C4 replaces generic fallback behavior with the same-source paired-host requirement above; unpaired note text fails explicitly rather than receiving a plausible but incorrect contrast result against another host or the canvas. Tests must prove valid pairing and fail missing pair, missing fill, and non-opaque fill.

## Scope and migration

No View, Project, annotation candidate, geometry, obstacle, route, tail, or placement identity changes. Layout remains the owner of completed annotation geometry; Scene owns the visual-role classification and reports; Theme owns the explicit treatment and representative fill; adapters only serialize completed facts. The public semantic classes change the contrast report and may add SVG paint findings, so regenerated reports, Scene, SVG, and any published PNG are part of one materialization batch. Geometry, candidate choice, connector route, and search provenance must remain unchanged.

The new `DECORATION` class means C4 must add `annotation-note-box` to the corpus witness. It is not enough to classify the role: at least one committed public Scene must visibly emit a note box with enabled paint. The #467 L3 / C3 remeasurement dependency remains binding. If C3 is not yet published and valid, C4 may complete design and planning but cannot claim the issue's visible acceptance or release closure.

## Exact behavior and diagnostics

- At Theme closure, every effective `annotation-note-text` declaration has `contrastTreatment: required`; the existing class-driven closure code checks its resolved fill/opacity against the Scheme surface at 4.5:1. Scheme insertion may change the fill token/value but cannot supply or weaken this treatment.
- Theme/Scheme closure checks text fill and opacity over the resolved Scheme surface using the existing 4.5:1 policy. Completed Scene contrast uses the actual opaque host under the text sample point, expected to be the note box, and records its ground identity/color.
- The note box uses the existing `DECORATION` 1.10:1 floor over its completed host/canvas ground. The new effective-Theme validation and note-text paired-host check reject missing or non-opaque representative paint; generic `_ground_under` alone does not reject an absent fill and must not be relied upon for this contract.
- The representative-fill contract is independent of image-catalog pixels, crop/tile mechanics, and adapter target. Artwork variation does not change the declared contrast ground.
- `contrastTreatment` remains authoring data consumed before Scene. Scene transports the finite completed value; it does not re-resolve a Scheme or Theme.

## Normative specification changes

Specification 07 should state the note-text treatment, class ownership, opaque representative-fill requirement, and explicit unsupported cases at Theme/Scheme closure. Specification 08 should state that Scene contrast/perceptibility consume the note box's representative fill as the note text ground for rectangle, balloon, and image outlines, and that adapters do not inspect artwork. These clarify existing responsibility boundaries and #465 semantics; they introduce no new Scene schema, paint kind, or image sampling algorithm.

**Successor:** the C4 implementation plan must enumerate the six migration paths, `scene/capabilities.py`, semantic registry, generated contrast report, all affected public materializers, focused closure/ground tests, and visible SVG/PNG inspection. It must keep C3 fixture adoption conditional on published #467 L3 and remeasurement.
