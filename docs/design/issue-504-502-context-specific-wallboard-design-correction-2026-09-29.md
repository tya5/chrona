Copy the current wallboard composition and its declared top-level policy, then set the `table` node's `inlineSize` to `{minmax: {min: {fixed: 300}, max: {fr: 2}}}`. Keep profile identity `wallboard-programme-board`; do not use `extends` for this migration. Leave 04, 07, and 15 referencing `wallboard` at `layouts/wallboard.yaml`, revision `example-v1`; do not change their View, Theme, Layout, or generated output as part of this allocation correction.

This resource duplication is intentional and bounded: it makes the selected policy executable by today's Render Context path and avoids changing a shared profile. It does not declare that whole-profile duplication is the long-term reuse model.

## Why inheritance is deferred

The canonical Layout Profile format declares `extends` plus stable-node `overrides` (Specification 33, sections 2 and 8.1). The resolver implements base lookup and identity checks in `src/chrona/presentation/layout/profile.py` (`LayoutBase`, `_merge_base`, `resolve_layout_profile(..., bases=...)`). But this capability is not wired through production context resolution: `src/chrona/usecases/render_review.py:251` calls `resolve_layout_profile` without `bases`; `src/chrona/presentation/model/closure.py:_resolve_layout_context` loads the Context's single top-level Layout reference and no base closure; `src/chrona/usecases/materialize.py:_copy_reference` recursively copies derived Themes and snapshot Projects, but not Layout bases. A derived profile cannot therefore be resolved and materialized as a pinned Context resource today. Tests that explicitly pass `LayoutBase` prove the resolver unit only, not public materializer support.

Do not add a local `extends` workaround or special-case profile ID. A separate architecture/design slice must define the Layout dependency closure, pinned base loading, recursive materializer behavior, cycles and diagnostics, and Render Context integration before derived Layouts are used in public contexts. That mechanism is deferred; this correction needs no normative change to the Layout grammar.

## Migration and identity rules

The new profile is a full `chrona/layout-profile/v0.9` resource, not a partial override. Give it ID `wallboard-programme-board`, address `layouts/wallboard-programme-board.yaml`, and first revision token `example-v1`; retain the existing wallboard fields and node IDs. Each of the two Context references names `kind: layout-profile`, local store identity `halcyon-1-example`, that address, and that revision token. Context `contentIdentity` remains optional under Render Context v0.16 and follows the existing HALCYON convention (omitted); the materialized immutable closure must record/verify the canonical SHA-256 of exact resource bytes. Do not copy the old wallboard content identity onto the new resource. Regenerate materialized closure identities rather than hand-editing generated identity fields.

The existing wallboard source remains byte-identical. The only intended Layout-reference changes are contexts 02 and 12. Existing `table` and other stable node IDs, View membership, relation IDs/routes, and all other Context references stay intact. The 300px minimum is resource data, not renderer branching.
