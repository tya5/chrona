# Issue #554 — Lane presentation and diagnostic closure

**Base:** `c8bab542` (the published [design plan](../planning/active/issue-554-lane-followups-work-record-2026-09-29.md)). This design changes presentation semantics, not lane membership or Project identity.

## Use cases and decisions

1. A lane table names what a reader sees, not the generated lane key. This intentionally supersedes Spec 38's old `Lane <founder-id>` and explicit-key display rule. View owns the choice of `group` versus `lane` table presentation; the table-content projection resolves display text. For `lane`, use the sole member's Project title for a singleton, otherwise its group's title. If a group has several multi-member lanes, append the first member title to disambiguate them. An explicit lane key is an identity and is never presumed to be a human title. A genuinely declared human lane title can be added later as a separate View contract, not inferred from the key. Keep `Items` only where the View explicitly requests it; turn it off for the all-singleton 03 public View. A missing required Project title is a content diagnostic, not a fallback to an id.
2. Layout owns every member name's association to its own completed mark. Use the mark and completed text bounds, including leading visuals/chip, to measure the nearest edge-to-edge gap on both start and end sides. A direct name must be within 2em of its own mark. A farther legal candidate retains its name but gains a completed, source-keyed leader relation from label perimeter to mark perimeter. For full-band stagger, measure the two-dimensional nearest-point distance: displacement in either axis counts. Layout selects/places the leader with the label using the same obstacle inventory; it cannot cross required text or unrelated marks. If a legal leader cannot be completed, try the next label candidate, then use the existing source-keyed suppression outcome. `pack` and non-lane label policy do not acquire new displacement search. Scene projects the completed line and identity without routing; SVG only paints it. No new Project relation is created.
3. A successful render has one ordered warning ledger. Layout warnings, font fallback, perceptibility, scale collision, and attachment warning facts are collected once at the render-result boundary. CLI payloads and Scene diagnostic strings are projections of that ledger; both carry the same warning identity (code plus stable source/placement discriminator), with duplicates preserved in order. Scene-only informational diagnostics remain separate. The Scene must be finalized after draft perceptibility evaluation so its own findings appear there without a feedback loop; the evaluator reads the completed preliminary Scene, not the final diagnostic list. A test compares the multiset of warning identities in CLI and Scene, including `W_LAYOUT_LABEL_OVERFLOW` for attached milestones. This is a transport unification, not a change to Layout failure policy.
4. The bundled readable-default closed-day Theme uses one perceptible translucent fill token for both chart and legend. The starter gate measures composited luminance contrast against the actual underlying paint in Scene and confirms SVG paint equivalence; target minimum is 1.15:1 for both cue and key. The selected paint must remain translucent and later than row bands under the existing overlap rule. This is a Theme-resource change, not an adapter override. Legend truncation belongs to #497.

## Boundaries and migration

View selects lane table and count intent; table content resolves titles from selected Project facts. Layout measures and places labels, marks, and leaders. Scene projects completed primitives and records the canonical diagnostics; adapters serialize. Stable placement IDs preserve lane/member/source identity through the leader. No persistent schema version changes are required. The 03 View's declared count changes to false; generated Scene/SVG and preset byte identities must be regenerated. Diagnostic serialization gains complete warning identities; consumers treating `diagnostics` as a partial list must migrate to the complete list. The issue does not change the distinct `fitWarnings` detail payload or #497's legend text.

## Rejected options and failure behavior

Do not display `lane.explicit_key` as a title, impose a blanket row-count threshold, move labels in Scene/SVG, or silently draw an unvalidated leader. Do not cap all staggered names to 2em and reintroduce #504 suppression when a valid leader exists. Failed leader candidates participate in the existing finite candidate/suppression decision. Invalid title closure fails before adapter output; a valid fixed/capped profile still reports its ordinary visible fallback.

## Evidence

Focused View/table tests cover singleton, multi-member and duplicate-group titles; Scene/SVG tests pair every emitted member label with its mark or source-keyed leader and check both sides at 2em. The attached-milestones CLI/Scene warning multiset must match. Starter chart and legend must meet composited contrast and SVG equivalence; batch-check affected public materializers and bytes, then CI and literal acceptance review.
