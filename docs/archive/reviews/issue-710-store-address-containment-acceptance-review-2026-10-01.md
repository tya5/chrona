## Architecture and release conclusion

The security weakness is closed in the code (rows 2 to 4) and the schemas are tightened for the sites the owner named (row 1). The design findings are the record of what was wrong, and the issue's own framing, "defence in depth, not an open vulnerability", was incorrect for three items: a symlink inside a snapshot directory was followed out of the Store root (measured on POSIX), a `captureSnapshot` command with a `snapshotId` of `..\..\x` could write outside the registry on Windows, and a drive-letter address replaced the base path on Windows. `contentIdentity` was optional by default on this path, so it was not a containment control; making it required is [#723](https://github.com/tya5/chrona/issues/723).

Disclosures:

- **Row 1 is narrowed.** Three live address sites outside the owner's list and the removal of the five loose predecessors remain, with decisions in [#731](https://github.com/tya5/chrona/issues/731). `snapshot-ref` v0.2 is never retired for reads, because a committed baseline pinned by a Context stays on it.
- **A wrong statement in the S-A change.** The S-A pull request body, commit message and `schemas/README.md` said the frozen `vocabulary` part references `revision-store-resource-ref-v0.1`; it does not. S-D corrected the README, Spec 56 and the inventory comment. The merged S-A commit message still carries the old wording.
- **A design mechanic that did not work as written.** The inventory rejected two live entries of one kind, and a part cannot be `transitioning`; several live entries of one kind are now allowed only when all are `SCHEMA_PARTS` files, with a test.
- **One thing the design did not specify.** A result or baseline built from a v0.2 command could echo a legacy loose address and break the v0.2 to v0.3 contract, so `stamp_automation_result` and `snapshot_ref_resource` choose the newest version the content satisfies, else the predecessor.
- **Whether the bumps were needed.** After #719 the code already refuses every unsafe input, so Spec 56 §3.2's in-place clause for a refusal the consumer already makes could arguably have avoided them. The owner's row said bump and it was done; the question is in #731.
- **A Windows-only failure on the way.** The first three-OS run after the guard work failed on Windows in the directory-guard matrix because the materialization check asked only the host flavour whether `/tmp/out` was absolute; [#717](https://github.com/tya5/chrona/pull/717) fixed it and #719 replaced it with the shared function.
- **Derived effect.** S-B makes CI's derived-sync regenerate 29 `examples/*/generated/*.scene.json` files (one provenance line each) and four derived docs; S-C changes one.

Exact review-bearing-main three-OS CI and newest-Python materializer run must pass before closing #710; record that run in the issue closing comment.
