# Architecture Review — PR pytest speed and balance (#657)

**Reviews:** [design](../../design/issue-657-pr-pytest-speed-design-2026-09-30.md) against the [design plan](../planning/issue-657-pr-pytest-speed-design-plan-2026-09-30.md) and the published `main` (`400f323d`).
**Verdict:** the design may proceed to implementation planning, with the constraints below made binding on every slice. Two risks (2 and 9) cannot be designed away and are reported as open, not accepted.

## Findings

**1. Coverage can be lost by marking a test `corpus`. (High)** A marker is a one-word change that silently removes a test from every PR. The design's guard is procedural (the rule table and "the only PR-path test of a rule is never marked") because no tool can decide that a rule has another test. So the discipline is: synthetic test first, in the same PR or an earlier merged one; the PR body lists rule, synthetic PR-path test, remaining corpus test; a mutation check shows the synthetic test fails when the rule is broken. A candidate without a defensible synthetic test stays in the PR path and is reported. The reviewer of I657-3a checks the table against the diff, not the reverse.

**2. "Once per test session" is not "once per CI run". (High, materialized and remedied)** pytest-split assigns individual test items to three machines, so consumers of one combination landed in different shards and each shard rendered it again. Measured after I657-2 on CI (run 36737037428): 6 of 7 preset keys were rendered in two shards, `print-mono` in three; within a shard two workers asking for one key at once both spend a full render time (one renders, one waits). Acceptance row 2 is met as written (one pytest session, xdist workers included) but gave little wall-clock benefit. The recorded durations of cache consumers were also uneven (the first consumer carries the render). Remedy (I657-2b): one test item per (project, preset) render that runs every rule check on it, so deduplication no longer depends on where the splitter places items; each failing rule is still reported by name. The cost is that four test names became one per preset; the assertions are unchanged and moved verbatim.

**3. Cache correctness and isolation between tests. (Medium, designed)** A shared result is a shared mutable object unless prevented. The design prevents it: results are immutable bytes/strings, `scene` and `warnings` re-parse on every access, the key includes a digest of every input byte so a mutated input is a different key, and paths outside `examples/`, packaged resources and the cache's own starter are rejected. Residual risk: module-level state inside `chrona` (any `lru_cache`, font tables) is shared by all renders in a worker process; that is true today and the cache does not add to it, but it means a cached render does not prove a *fresh process* would render the same. `test_render_review_is_deterministic_for_one_closure` and the byte-for-byte reproduction test keep covering that.

**4. Duplicate renders were an accidental determinism check. (Low)** Rendering the same combination in two tests, in two workers, and comparing nothing was never a determinism test, but a nondeterministic layout would have made one of the tests flaky. With one render that signal disappears. It is replaced deliberately, not by hope: the I657-2 PR keeps one explicit test that renders one combination twice into separate directories in one process and compares bytes (cost about 30 s of worker time, well inside the saving), and the unchanged `reproduction-newest-python` job compares bytes against committed evidence on every code PR.

**5. Timing noise. (Low)** `.test_durations` from one unsharded session attributes render cost to whichever consumer ran first. Relative weights stay usable because the expensive tests remain expensive, and unknown or stale ids only cost balance. The file must never be treated as a gate or a spec; nothing may fail because of it.

**6. A PR can merge while main's corpus tests are red. (Medium, accepted with mitigation)** That is the point of the marker, and it moves corpus failures from the PR to the post-merge full matrix. Mitigations: `full-matrix` runs on every push to `main` (post-sync dispatch), nightly and on demand, so the failure is found within one run, not one day; `reproduction-newest-python` and `pr-conformance` (`conformance/run_conformance.py`) remain on every PR; and the derived-evidence snapshot (`derived-preview`, `derived-ready`) still regenerates and checks committed corpus evidence. The design does not change branch protection. A corpus failure on main is a normal red main to be fixed forward under the owning issue.

**7. Interaction with #575 and #573. (Medium, sequenced)** #575 restores the `avionics-bustest` lag (re-pinning all HALCYON contexts and regenerating evidence), freezes layout profiles, and adds `tests/support/synthetic_review.py`; #573 edits `surface_member_labels.py` and the layout-profile schema. This design keeps out of all of those files, puts its support code in `tests/support/render_cache.py` and `tests/support/axis_projects.py`, and depends on no #575 slice. If #575's builders land first, I657-3a uses them instead of `axis_projects.py`. A HALCYON data change that alters render output needs no cache work, since the cache keys by input bytes. Tests that #575 rewrites (`test_intent_engine`, the four core-rule tests) are not touched here; the rule table in I657-3a names the #575 tests it relies on and does not count a #575 test that has not merged.

**8. The product routing cost is out of scope but dominates. (High, reported)** A `--preset` render of HALCYON spends about 98% of its time in `route_orthogonal`/`obstacles.collisions` (665,000 all-obstacle scans). Every test-side saving in this issue is a workaround for that cost, and the acceptance figure would be reached far more surely by making routing faster. That is a product performance change with byte-identity as its proof, in a layer owned by other work; it needs its own issue and design. Recommended as a successor; no code here.

**9. Acceptance row 1 is borderline. (High, open)** Measured baseline: slowest shard 280 to 416 s. The estimate after all slices is 130 to 160 s (plan, finding 5). The design does not promise the figure; every slice PR reports measured shard times, and if the final figure is above 150 s the remaining cost is named test by test (candidates: the two `test_render` elevated tests, `test_attached_milestones`, the `gallery-editorial-lanes` closure test).

**10. Workflow blast radius. (Medium, designed)** Two workflow edits affect every PR. The shard `-m "not corpus"` edit is one line, guarded by a test that parses `conformance.yml`, and is validated by a `workflow_dispatch` full-matrix run on the branch. The refresh workflow is separate from `conformance.yml`, has narrowly scoped permissions, and cannot fail a PR. The token limitation (section 4 of the design) is disclosed rather than worked around. Both PRs stop for the lead's merge.

## What may not move out of the PR path

These remain in the `pr-pytest` shards (or another mandatory PR job) whatever their cost:

1. **Any test that is the only PR-path test of a rule.** Before a test is marked `corpus`, its synthetic replacement exists on `main` (or in the same PR) and is named in the rule table.
2. **Committed-evidence integrity**: the public-scene contrast and diagnostics tests, the packaged-resource mirror tests, and the schema and contract tests that read committed files. They are cheap (under 1 s each) and they are what makes a corpus edit visible.
3. **Public materializer reproduction** on Python 3.12. `reproduction-newest-python` stays, unchanged. Reproduction on Python 3.11 moves to the main/nightly matrix only if the lead accepts that (recorded as a decision in I657-3b; the default is to accept it, since 3.12 already reproduces every context).
4. **The render-counter test and the explicit determinism test** of the cache (findings 3 and 4).
5. **Every test of a rule with no synthetic replacement**, including tests that are slow. Slow-but-unique tests stay and are reported (finding 9).
6. **The guard test on `conformance.yml`** that keeps shard deselection and the full matrix consistent.

## Whole-architecture check

- Layer boundaries: nothing under `src/` changes. `tests/support/` is a new test-only package; it imports the public `chrona.app.cli.main` and `chrona.usecases.local_authoring.initialize_project`, the same entry points the tests use now.
- Adjacent designs: consistent with AGENTS.md ("corpus output is evidence, not an oracle"; core rules use synthetic fixtures) and with #575's design (synthetic builders, corpus as demonstration). It adds a mechanism (marker) that #575 did not have.
- Failure behaviour: a cache lock wait times out and fails the test loudly; a stale or missing `.test_durations` degrades balance only; a missing `DURATIONS_PR_TOKEN` degrades the refresh PR to "opened, needs a nudge".
- Intended incompatibilities: test ids change for the split monolith (8 new ids); corpus-marked tests are not run by PR shards.
