## Architecture and release conclusion

The performance problem #657 left is solved where it was: a render is about five times faster with identical output, and the PR-path shards take a median of 75 s. What remains is not in the code: the residual spread between shards is the variation between GitHub runner CPU classes. The refresh job now opens its own pull request.

Disclosures:

- **A criterion that cannot be met by the means the issue assumed.** The 20% spread target was set before the runner-speed effect was measured. The diagnosis says it cannot be reached by changing the split, and the honest target that replaces it is met only at its threshold.
- **The samples were not independent.** The eight post-change measurements were opened together, so the 24 shard jobs ran concurrently and may exaggerate how mixed the runner CPUs were; the CPU class was not recorded in these samples and the explanation for the 38 to 55% spreads is inferred from the earlier probe runs.
- **Only one preset was profiled.** The routing profile and timings cover `mission-light`; the other six catalogue presets were not measured.
- **The weakness the property test cannot show.** Removing only the rounding slack from the grid is caught by no generated case, so the slack is kept as defence in depth.
- **What is left in the routing cost.** About 646k `ObstacleSegment` constructions with validation, the per-call exemption checks and the A* bookkeeping. Cutting further means fewer `clear()` calls, which can change which equal-cost route A* picks, and needs its own design.
- **The refresh PR still needs its checks started by hand.** A pull request opened with the default token does not start the pull-request workflows, so each weekly PR must be closed and reopened (as #776 was) or given a `DURATIONS_PR_TOKEN` secret, which would also start the checks; the setting that was enabled lets the job open the PR but not start its checks.
- **A repository setting changed.** The setting "Allow GitHub Actions to create and approve pull requests" is now on, with the owner's say-so on 2026-10-01; it lets any workflow in this repository open a pull request with its own token, within the permissions the workflow declares.
- **This review was updated.** It was first published (PR #747) with item 3 deferred and the issue left open; item 3 is now met and the issue closes.
