## Design

**D1 (item 1). Scope of the "no inline copy" row.** The row is met in the D8 scope: no live inventory entry other than the parts carries an inline copy of a shared pattern (enforced by the live-entry copy test in `tests/unit/tools/test_schema_parts.py`).
The two frozen parts keep their own sha256 and path patterns (a parity test ties them to `common`). A `-v0.2` part is not worth its cascade: editing `presentation-resource` in place would retro-change 17 View versions, two icon-catalog versions and summary-profile, and
`revision-store-resource-ref` four kinds; a new part version would need every consumer re-pointed at its next bump for no accepted-set change. The non-live inline copies (`scene-v0.6`, `theme-v0.12`, `view-v0.26`, `view-v0.27`, `icon-catalog-v0.3`)
are historical and are removed with their own `transitioning` removal slices, never re-pointed (re-pointing would change what a published version accepts). The #662 row 1 stays `narrowed`; its successor note now points here and records the decision.
Revisit only if a part version is needed for another reason (the `common-v0.2` already named for dropping the unreferenced loose address defs): the frozen parts can then move at that time.

**D2 (item 2). Declared-vocabulary policy for the theme marker and the retirement of `theme-v0.8`.** The policy entries move to `schemas/theme-v0.13.schema.yaml` with these pointers (same three, one moved):
`.../allOf/1/then/properties/value/properties/shape` (accepted widens to `triangle, open-triangle, chevron, circle, open-circle`), `.../allOf/2/then/properties/value/oneOf/0/properties/kind` (`outline`),
`.../oneOf/1/properties/kind` (`diagonal-hatch`) and `.../allOf/3/then/properties/value/oneOf/0/properties/shape` (`diamond, circle, square, chevron`, same set as before).
The marker `shape` entry's owner becomes `chrona.presentation.layout.relation_terminals.marker_geometry`, the function that actually validates the five values; `ThemeTokenView` validates no shape, so naming it as the owner of that
acceptance was untrue. The other three entries keep `ThemeTokenView`, as before. A test ties the entry's `accepted` set to what `marker_geometry` accepts, so a later widening of either side fails.
Widening `accepted` is a change to a checked vocabulary, not a schema change: `theme-v0.13` already declared the five shapes and the renderer already drew them. Spec 56 §3.2 is not involved (no schema text changes), and the S0 gate's L1 and L2 are unchanged.
**Gate declarations (Spec 56 §3.2 and §7, the S0 equivalence gate):** only `theme-v0.8.schema.yaml` leaves `schemas/`, declared with one `expected-deltas` line of type `removed` pointing at `tests/unit/tools/test_schema_archive.py`, as the #662 S5 slices did.
Spec 56 needs no sentence: the archival rule and the retirement of a `transitioning` predecessor are already stated there. The derived `vocabulary-inventory.md` regenerates four schema paths, one owner and the widened `accepted` cell; it is not edited in the PR.
Archival follows the #662 S5 procedure: `git mv` to `docs/archive/schemas/`, delete the inventory entry in the same commit, update the archive README (it currently says theme v0.8 remains), run `tools.schema_inventory`, annotations, references, `tests/unit/tools`,
`tests/integration/test_packaged_resources.py` and the gate against `origin/main`. `tests/unit/tools/test_schema_archive.py` then enforces that no executable file names it.

**D3 (item 3). No shared envelope.** Each kind fixes its own `version` and `kind`, so a shared definition would save about four lines per schema while changing every schema's diagnostic shape (Spec 56 §3 reduces `allOf` branches) and adding an `allOf` to each. Recorded as decided against
in design D7 of #662; the eleven inline envelopes stay. The `presentation-resource` envelope that View, icon-catalog and summary-profile already reference is unchanged. Reopen only with a concrete diagnostic or maintenance failure.

**D4 (item 4). `store.provider` in corpus coverage.** `tools/corpus_coverage.py` follows every `urn:chrona:` shared part, like `presentation_coverage`, so the Snapshot Reference schema contributes `body.project.store.provider` (`content`, `git`, `local`, `package`) through the `revision-store` part.
The committed report then gains rows for whichever of the four values no committed corpus project uses (an uncovered row is non-gating information, as for the S4a `end` row). The test that pinned the omission is rewritten to pin the new behavior.
The report text that says which schemas it reads is amended if it implies vocabulary parts only. Following all parts is chosen over adding the one `revision-store` prefix because the part set is the repository's own closed list and the two coverage tools should not disagree; if another part adds rows, they are reviewed in the slice.
`docs/examples/corpus-coverage.md` changes only through derived-sync.

**D5 (item 5). `icon-catalog-v0.3` is kept for the bundled catalog.** The Material catalog (`material-symbols-outline-rounded-v2026-09-22`, 4,015 entries) is vector-only: no raster `address` exists in the data the loose v0.3 `address` pattern would check, it is trusted packaged data, and the v0.4 parse-time `storeAddress`
check already covers every v0.4 catalog. Migrating it would be a large packaged-data change and re-pinned manifest, notice and hash tests for no observable effect. The decision is stated in the inventory entry itself through an optional `reason` string
(non-empty when present; the loader validates it), and `icon-catalog-v0.3` stays `transitioning` with its removal slice unchanged. This closes the open question in #715 item 5; it is not a statement that v0.3's `address` is strict.

## Architecture review

- Layers: nothing here moves a responsibility. Items 2 and 5 touch conformance data and the inventory; item 4 touches a non-gating report tool; items 1 and 3 are decisions only.
- Item 2 corrects the policy's owner for the marker entry; it does not widen what the product draws (`theme-v0.13` and `marker_geometry` already agree). The policy remains a check that a schema declares nothing its owner does not accept; the new test keeps it truthful for the shape.
- Item 4 adds information to a derived report and no gate. Derived output stays bot-generated; the PR must not touch it (the PR check rejects it).
- Item 5's `reason` key is additive in the inventory format (a tool-owned file); it changes no schema document and no accepted set. The inventory loader's strictness is the only code change.
- Compatibility: no authored document changes verdict. L1, L2 and L3 of the S0 gate are expected equal apart from the one `removed` line in S1.
- Risks: a broadened `corpus_coverage` may surface other parts' enums (checked in S2); a policy owner change is visible only in the derived inventory table.
