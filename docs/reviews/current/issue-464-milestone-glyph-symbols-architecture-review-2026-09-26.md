# Architecture Review — Milestone Glyph Symbols (#464)

**Decision:** design approved for implementation planning, with the port-at-visual-edge limitation (below) named as an accepted risk, not a defect to fix in this slice. **Reviewed design:** [#464 contract](../../design/issue-464-milestone-glyph-symbols-design-2026-09-26.md). **Normative update:** Specification 07 §5.2, Specification 08 §5.3. This is a design review, not issue acceptance.

## Reviewed ambiguities and resolutions

1. **One primitive with a `parts` list, or several sibling primitives?** Considered both (Contract 4). Several sibling primitives wins: it reuses `_complete_primitive_paint` and the existing per-primitive `paint` field verbatim, needs no new nested Scene paint schema, and needs no adapter branch beyond looping primitives it already knows how to draw. The cost — several primitives per gate instead of one — is the same shape the Scene already accepts for a span.
2. **Is a new Theme token type needed for a glyph?** No. `shape: glyph` is an additive value under the existing `symbol` token type; the role property and resolution entry point are unchanged. A new type would duplicate plumbing that already exists.
3. **Do `milestoneSymbolActual`/`milestoneSymbolBaseline` need to exist as separate roles, or would a treatment suffice?** Pixel Quest's ghost-sprite baseline forces separate roles: it is a different *asset*, not a different treatment of one asset. Five of six targets never set the new roles and inherit `milestoneSymbol` unchanged.
4. **Does extending `_ground_under` to `Symbol` risk changing existing public evidence?** Reviewed against current usage: no existing `Symbol` primitive today has anything painted over it at the same bounds (one paint layer per built-in shape), so the candidate set only grows for the new multi-part case. This is asserted here from reading the code path, and is re-verified with the batch materializer diff in the implementation slice — a passing review here is not a substitute for that evidence.
5. **Port-at-visual-edge:** reviewed as a genuine, not cosmetic, gap (Contract 6). The alternative — Layout computing a glyph's painted horizontal extent from `parts`' path data during placement — was rejected for this slice because it requires Layout to parse and transform path data on every placement pass for a feature only six hand-authored glyphs currently need, and none of the six needs it (all are drawn full-bleed in their own `viewBox`, verified by reading each target's asset). Recorded as an accepted risk, not silently absorbed into "arrows end at the glyph's edge."

## Risks and gates

- **Port-at-visual-edge (accepted risk, named for the owner).** Holds only because every approved target's art is full-bleed. Nothing enforces this at Theme-load time; a future glyph with internal padding or a mismatched aspect ratio would have a dependency arrow visibly stop short of the artwork. Revisit if a seventh target's asset is not full-bleed, or move the constraint into a load-time check (comparing the glyph's `parts`' path bounds to its `viewBox`) as a small follow-up if this recurs.
- **Clip-source onto a multi-part glyph is not solved.** Only the first part is available as `outline` for the pre-existing `clipSourceId` mechanism. No committed slide exercises it; flagged for whoever first combines an icon overlay (spec 64) with a glyph-shaped gate.
- **Batch diff obligation.** The `_ground_under` widening and the two new optional roles are asserted here to be byte-identical on the other 22 public slides; the implementation slice must prove it with the batch materializer diff, not merely restate this review's reasoning.
- **Path-data grammar reuse.** The design commits to sharing the normalizer's SVG-path tokenizer rather than writing a second one; the implementation slice must actually extract it as a shared helper (not copy it), or this review's "exactly one grammar" claim is false by the time code lands.

No unresolved user choice remains for this design; the two scope exclusions (state-dependent glyphs, icon-catalog-backed parts) are named, not silently deferred, in the design plan.
