## Architecture and release conclusion

Layout and example YAML only: one declared viewport width, and a cache that cannot change a result. No schema, spec or Scene contract changed. The owner's rule held for item 1: the slide's look was fixed in its own YAML and no core priority knob was added.

Disclosures:

- **The speedup is 1.6x, not more.** Slide 16's CPU time fell from 18.3 to 11.5 s and slide 02's by 1.14x. The wall times flatter the change because the second measurement ran at a lower host load; CPU time is the steady figure. The remaining cost is the first rehearsal (about 6.6 s) and the second (about 4.3 s), which share no search because they place different member names; reusing a rehearsal's batch in place of the real pass would save more but changes the #592 phase contract, which the owner decision did not include.
- **The two items interact.** The 2400 viewport changes slide 16's size and so its render time; the memo timings above were taken on the 1600 slide before it landed, so the render time of the final 2400 slide was not measured separately.
- **The widest slide is large.** At 2400 by 2140 with unchanged 14 px text the timeline is much wider and the grey lane band at the left is mostly empty. It satisfies the owner's four conditions; it is a look the owner can still reverse by setting the width back to 1600, which restores the suppressed relation.
- **Another width could look better.** The result is not monotonic and only whole hundreds from 1600 to 2800 plus 2250 and 2350 were tried, so a width between them was not searched.
- **One merge on a stale base.** The docs PR #772 was merged on a base that had moved, docs-only, with `derived-ready` green.
