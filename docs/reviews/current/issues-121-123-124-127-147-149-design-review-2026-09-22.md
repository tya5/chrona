# Issues 121, 123, 124, 127, 147, and 149 — Design Review

**Design-plan authority:**
`docs/planning/active/issues-121-123-124-127-147-149-design-program-plan-2026-09-22.md`

## Decision summary

This review closes D1–D6 of the program plan.  The six changes are one
unidirectional product path:

```text
authored schema/document
  -> exact schema validation -> frozen closure contracts
  -> Core validation/scheduling -> View projection -> Layout placements
  -> Scene primitives -> SVG | PNG | PDF | Typst | TikZ artifact
```

The CLI may construct and materialize declared inputs, but it does not own a
second resolver, parser, scheduler, layout, or serializer policy.  Every arrow
is one-way; a renderer never feeds geometry or semantics back to an earlier
stage.

## D1 — #124: schema inventory and lifecycle

### Authoritative inventory rule

`schemas/` is an authored public-contract directory.  A schema is **live** only
if a current product route, a current conformance suite, or a current supported
tooling route names it in the generated schema inventory.  A historical example,
an unreachable module, or a deferred-roadmap document cannot make a schema live.
The inventory is a checked-in machine-readable manifest generated from explicit
registration roots, with a test that verifies both directions:

* every registered live schema exists, is packaged, and is named by one or more
  approved roots; and
* every schema file is registered exactly once as live or deliberately removed.

The README is rendered from that manifest and is an exact alphabetical index of
the live `(kind, version, owner, consumer)` set.  Search-based reference counts
remain a diagnostic, not semantic reachability: tests, package metadata, and
registry tables can be legitimate roots, whereas prose cannot.

### Version and deletion decisions

No compatibility parser is retained.  The final product path has one live
version per kind.  Implementations migrate all consumers and delete the
superseded schema in the same atomic publication.  Deferred capability schemas
(DateTime, capacity, collaboration, AI, release, and federation contracts
without a current product route) are removed together with their standalone
conformance-only fixtures, rather than advertised in the README.

The existing `timeline/v0.2` is a DateTime/recurrence successor belonging to
roadmap M10.  It is not the successor for #123 and must not be repurposed.  It
and its DateTime-only conformance route are removed from the current product
inventory.  #123 introduces `timeline/v0.3` as the Date-only replacement for
the currently live `timeline/v0.1`; it then atomically replaces v0.1.  This
preserves version meaning and avoids promoting M10 by accident.

`presentation-resource-v0.1` is a shared schema implementation detail only
while live resource schemas reference it.  The inventory records that dependency
explicitly; it is not an independently authorable kind.  Its final retention or
inlining is decided by whether the schema validator requires a packaged `$ref`;
the implementation may not leave an unregistered hidden schema.

### Acceptance

The schema inventory test, packaged-resource test, exact README test, and a
negative test for an unregistered schema all pass.  The final inventory contains
no concurrent live schema versions and no M10/deferred contract represented as
a current product input.

## D2 — #147: typed closure contracts

### Schema-first record model

Schemas remain the sole authored acceptance authority.  The closure resolver:

1. reads immutable bytes and decodes an untrusted document;
2. selects the exact registered schema from declared kind and version;
3. validates that document before any record is constructed; and
4. constructs one frozen, kind-specific record from the accepted document.

The record may reject only an invariant JSON Schema cannot represent, and that
case requires a named diagnostic plus an amendment to this review.  It may not
add defaults, accept an alternative envelope, or silently discard a schema
field.  The raw mapping is not available after the closure boundary.

`RenderClosure` contains immutable resource identity metadata and a tagged union
of `Project`, `View`, `Theme`, `ColorScheme`, `LayoutProfile`, `ActualSet`,
`SnapshotRef`, `SummaryProfile`, `ReviewDetailProfile`, and `RenderContext`
records.  Each record contains named immutable nested records where downstream
logic currently depends on shape: `TableColumn`, `LegendEntry`, `SummaryPanel`,
visibility policy, row policy, target declaration, and typed references.  Open
extension payloads remain explicitly named frozen mappings only where their
schema permits open content.

Derived values remain separate: `ResolvedTheme`, schedule results, View
projection, Layout Manifest, placements, and Scene are not persisted closure
records.  Date parsing remains owned by Core's Date-only domain; contract
construction does not introduce a second temporal parser.

### Completeness and ownership evidence

A schema-to-record conformance fixture enumerates the accepted fields and
asserts their record access path.  It fails when an authored field is not
represented, when a record exposes an undocumented synthetic field, or when a
closure consumer accepts `Mapping[str, Any]` for a resource.  Consumer modules
receive only records: Core receives Project facts through the Core adapter;
presentation receives View/theme/profile records; renderer adapters receive
only Scene and resolved renderer inputs.

## D3 — #123: Date-only Project v0.3

### Scope and version correction

The issue's proposed name “Project v0.2” predates the now-reserved DateTime
schema.  The current Date-only successor is **Project v0.3**, with
`version: timeline/v0.3`.  It does not add DateTime, recurrence, capacity,
cost, or automatic leveling.  The issue title/body will be corrected before its
implementation PR so the public tracker names the actual contract.

### Project semantics

Each object gains optional `parent: <object-id>` and optional authored
`wbsCode: <segment(.segment)*>`.  Parent references must resolve, cannot be
self-references, and form one acyclic forest.  Objects have at most one parent.
Root and sibling order is the canonical YAML mapping order after normalization;
if `wbsCode` is omitted, its display code is deterministically derived from that
tree order.  An explicit code is a stable author label, not a second containment
edge, and must be unique among the Project's objects.

An object with children is a **rollup** when its `schedule` is
`{mode: rollup}`.  Its planned span is the envelope of its direct and transitive
scheduled descendants; an empty rollup is invalid.  A parent with an explicit
fixed or scheduled schedule remains an ordinary scheduled object: it does not
silently constrain, move, or derive from children.  The former `children` field
and `derived: {from: children}` syntax are removed; the parent edge is the one
source of hierarchy truth.

`plannedProgress` is an optional decimal in `[0, 1]`, representing a declared
plan expectation only.  It never changes schedule, forecast, or Actual
selection.  Observed progress remains exclusively in ActualSet and View may
compare the two only as a declared facet in later projection vocabulary.

Relations retain endpoint-to-endpoint and calendar-qualified lag semantics.
Their `type` is initially the closed enum `[dependency]`.  No `constraint` or
`association` value is introduced until an owner defines scheduling behavior;
an enumerated single value is preferable to accepted-but-ignored semantics.

Named Snapshot comparison is already the baseline authority.  #123 does not
add a baseline field to Project or a renderer-specific comparison path; any
visual baseline output continues through View → Layout → Scene.

### Core invariants

Core validation names stable diagnostics for missing parent, self-parent, cycle,
duplicate explicit WBS code, rollup with no descendants, and illegal rollup
schedule.  Scheduling derives rollups only after descendants are scheduled and
does not reverse-infer child dates.  Dependencies on a rollup use its resulting
endpoints exactly as dependencies on another scheduled span.  A parent edge is
not itself a dependency.

## D4 — #127: WBS View and presentation projection

View v0.3 replaces the concurrent v0.1/v0.2 View shapes with one Date-only
resource contract.  Automatic rows may declare:

```yaml
grouping: {by: hierarchy, depth: 2, rollup: bar}
```

`depth` is a non-negative expansion limit; a subtree below it is not selected
implicitly.  `rollup` is `bar`, `header`, or `none`: it changes presentation of
an already selected semantic parent and cannot alter hierarchy or schedule.
Within each sibling set, existing declared ordering plus stable ID is used.
Explicit rows gain a required non-negative `depth` and an optional parent-row
reference validated against the selected Project tree; explicit rows cannot
invent a hierarchy edge.

The table vocabulary adds `wbsCode` and `path` sources.  Theme adds the semantic
token `table.indent.inlineSize`; it is resolved before Layout.  The primitive
registry adds `summaryBar`, a source-traceable parent-rollup mark.  A summary
metric may declare `scope: subtree`; its aggregation consumes selected View
projection members, never scene elements or table text.

Layout calculates indentation, code/title cell bounds, parent mark geometry,
text placement, and all table allocation from measured inputs.  Scene projects
the completed table-text and summary-bar placements.  Renderer adapters map
already selected primitive purposes to target drawing commands; none computes
codes, depth, rollups, or geometry.  Required labels and marks follow the
existing overflow policy and receive a diagnostic rather than silent removal.

## D5 — #121: local authoring workflow

### Commands and configuration

`chrona materialize <manifest>` becomes the public immutable Context builder.
It consumes the existing declarative manifest grammar through an application
service extracted from `tools/materialize_example.py`; the tool becomes a thin
compatibility-free developer wrapper or is deleted.  The service returns a
typed materialization result and writes only declared output files.

`chrona init [--example halcyon-1] [directory]` creates a new explicit project
layout, `.chrona/store.yaml`, and a complete working resource/manifest set.
It refuses a non-empty target unless an explicit future overwrite policy is
designed; this issue never overwrites authored files.  Generated examples are
fixtures of the same live schemas and are immediately materializable.

Store selection has exactly this precedence: explicit CLI options; an explicit
store configuration argument; `.chrona/store.yaml` at the project root; then a
named current-directory project root discovered by walking upward.  No home
directory, mutable branch, or arbitrary directory scan is a fallback.  Failure
to find or validate a store yields one stable diagnostic before any input read.
The selected store identity/root is used to resolve addresses but remains
explicit in the materialized immutable Context.

`render`, `render-review`, and `materialize` call one closure resolver and
share the same store-selection service.  The CLI owns only parsing, diagnostics,
and output paths.  Documentation is updated to the live Render Context version
as part of the same schema-index publication.

## D6 — #149: Typst and TikZ adapters

### Target contract

Add `typst` and `tikz` to the next Render Context version, replacing v0.7
atomically.  Each has a declared `target.kind`, a target capability set, and a
`typesetter` environment identity containing engine name, exact version, and
adapter grammar version.  Unlike PNG/PDF it has no rasterizer.  The artifact is
UTF-8 source with media types `application/x-typst` and `application/x-tex`.

The renderer registry gains exactly one adapter per kind.  Both receive a
completed `SceneSurface`, viewport, and resolved tokens, and emit native vector
drawing commands.  They do not import resource schemas, projects, Views, font
metrics, Layout, routing, or scheduling.

### Text and evidence policy

This issue ships only `textMode: positioned`: Chrona supplies the measured
baseline, bounds, font asset identity, and font size from the immutable Context;
the adapter emits those coordinates and an explicit target font declaration.
The source artifact is byte-reproducible under a declared adapter identity.
Rendering it with a host's unconstrained typesetter is not immutable visual
evidence and must be labeled as such.  Native typesetter-reflow text is deferred
to a separately designed draft-only feature; it is not silently selected here.

Both targets declare only capabilities they can preserve.  Required SVG-only
metadata/accessibility/table semantics are rejected by the existing capability
gate rather than approximated.  Target tests parse emitted source, prove stable
ordering and source identifiers, and compile with the declared engine only when
that exact toolchain is available in the pinned verification environment.

## Whole-architecture consistency result

The program conforms to the roadmap's single-semantic-path and adapter-only
replacement gates, Specification 08's `Layout → Scene → renderer` seam,
Specification 09's resolver/CLI ownership, Specification 13's immutable closure
rules, ADR-0029's View-owned rows, and ADR-0031's completed-placement rule.

It intentionally rejects the following alternatives: reuse of the DateTime
v0.2 schema for current Date-only data; a parser that validates independently
of schemas; View/renderer-derived containment; WBS code computed by multiple
layers; implicit local-store discovery; raw YAML consumed past closure; native
typesetter reflow presented as immutable evidence; and any compatibility parser
for superseded schemas or contexts.

## Design completion gate

Before implementation planning, reviewers must verify that the final source
inventory, specification amendments, diagnostics, and migration boundaries are
consistent with these decisions.  An implementation discovery that requires a
new invariant, changes a boundary, or exposes a schema mismatch pauses that
slice and returns to this design review for an amendment and renewed whole-system
review.
