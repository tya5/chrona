## Mark-class completeness and ownership

The design's mark matrix covers planned span/point, snapshot/scenario facets, closed/open Actual, missing Actual, progress, attached point, selected vector/raster member icons, and point legend swatches. It distinguishes `Rect`, `Symbol` paths, multi-part glyph siblings, clipped hosted fill, normalized vector icon paths, and raster viewports. Each primitive is represented once: `ObstacleSegment` carries centerline plus stroke width; `ObstacleRect` carries already expanded bounds; clearance remains a separate collision input. This is consistent with `SurfaceObstacleIndex` and prevents double expansion.

The role boundary is consistent after the structural migration: Theme metrics provide geometry-bearing numbers, while the completed paint resolver controls Scene paint. A Theme color/Scheme change therefore cannot move a lane; a Theme geometry metric or icon-size change may move it. The design does not add paint to View or alter Scene schema. It does require an internal Layout placement value for completed symbol/icon paths and an internal typed paint-part intent accepted by the resolver. Compatibility checks must preserve glyph contain-center transform, `paint: none`, ordered per-part identities and paint order, close-point conversion, float arithmetic, the built-in diamond outline override/glyph exception, point legend geometry, and material-icon vector path transformations.

## Open evidence gate and risks

1. **Renderer miter limit:** current `ScenePaint` carries line cap/join but not miter limit; the current SVG path serialization relies on the SVG default of four. The design uses a conservative `2 × stroke_width` envelope for paths, which is safe only when emitted joins are limited to four half-width radii. Before implementation acceptance, inspect every admitted materializer/renderer and prove its effective miter limit is no greater than four, or amend the design/specification to bound the actual supported output. Do not infer cross-adapter equivalence from the Scene type alone.
2. **Conservative false collisions:** path-control-point and miter envelopes may be larger than the painted path and increase lane count. The 02 ≤12 and chain criteria must be rerun with current data after implementation; prior feasibility counts are not evidence for this geometry change.
3. **Icon path topology:** normalized vector paths may be curved; their control-point hull is conservative, not exact. Raster alpha is intentionally not inspected. If that bound makes the accepted domain infeasible, return to design with measured evidence rather than under-reserving.
4. **Role availability:** each supported lane mark class must have its canonical role and geometry metrics before mapper closure. Existing Theme diagnostics remain authoritative for invalid values; unsupported or missing mapper geometry must fail before allocation with the typed Layout error in the correction.
5. **Compatibility of moved path construction:** current automatic/explicit Scene and SVG outputs, point legend swatches, and material-icon SVGs must be byte-characterized across the structural move. If preserving their existing geometry bytes requires renderer inference, implementation returns to design rather than recreating that inference in Scene.

## Review disposition

The architecture keeps Project/View semantics, Theme appearance, Layout geometry, Scene projection, and adapter serialization in their declared layers after the required structural migration. The correction is consistent with Specifications 38, 46, and 50 and the #375/#459/#466/#480/#486 contracts. The miter-limit gate is unresolved evidence, not permission to assume all outputs behave like SVG. B1b-2 implementation planning may proceed only with exact ownership of completed paths and resolver responsibilities plus an explicit inventory/test for the miter gate; implementation acceptance and public lane activation remain deferred. No #467 or #494 acceptance row is met by this review.
