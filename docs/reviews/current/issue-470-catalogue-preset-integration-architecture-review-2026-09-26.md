# Architecture Review — Five Catalogue Preset Integrations (#470)

**Design:** [integration contract](../../design/issue-470-catalogue-preset-integration-design-2026-09-26.md). **Decision:** approve serial integration after #466 C1 CI and an implementation plan, subject to current-main rendering and per-PR gates; this is not the final issue acceptance.

The design preserves [Specification 55](../../specification/55-presentation-design-space.md)'s exact preset-member identity and [Specification 51](../../specification/51-progressive-authoring.md)'s declarative package boundary. It also preserves [#378 genericity correction](../../design/issue-378-builtin-preset-genericity-correction-2026-09-26.md): neither HALCYON object IDs nor the bare default View can become a copied catalogue member. View, Theme, Layout and Scene ownership remains as in Specifications 06/07/08/33. Specification 50 permits natural canvas growth, so the 1600 × 900 acceptance names requested viewport, with actual output dimensions reported. The five PRs do not authorize mechanism or schema changes.

Risks: shared library and packaged-resource test hunks may conflict despite per-preset bundles; old PR screenshots may no longer match after #466 shared-obstacle routing; an output can be warning-free while still visually weak; and a green old-base PR check is not a current-main gate. The implementation plan must require serial merge, refreshed CI, actual copied-preset renders on HALCYON and starter, batch image inspection, all warning IDs, and an explicit 19-item/three-observation gap-to-issue audit. If a PR needs a non-YAML mechanism to meet the issue's present acceptance, leave it open and return to its owning design; do not slip the mechanism into a preset merge.
