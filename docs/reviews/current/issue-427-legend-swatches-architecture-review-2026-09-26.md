## Reviewed ambiguities and resolutions

1. **Why a Theme role for `swatchInlineSize` rather than a Layout Profile field.** A span/line entry's legend length is a visual size decision with no chart equivalent (unlike block size, which literally is the chart's own `markHeight × timeline.mark.blockSize`), so it belongs with the other size/appearance tokens (`markCornerRadius`, `markHeight`) that already live in Theme, not with placement fields in Layout Profile. This keeps the split clean: Theme answers "how big/what does it look like", Layout Profile answers "where, and how are entries arranged".
2. **Why block size is *not* a new Theme token.** Making it one would let a Theme's legend disagree with its own chart (an author could set a swatch block size larger than any real mark on the same document), which reopens exactly the defect #427 reports for a different value. Reusing `timeline.mark.blockSize` is a Layout metric already resolved once per document and already the sole authority for every real mark's height; reading it again for the legend cannot drift from the chart, by construction.
3. **Why `theme-v0.13` and not `theme-v0.12`.** `theme-v0.12.schema.yaml` already exists for the unrelated `derived-theme` kind (`schemas/schema-inventory-v0.1.yaml`). Filenames are unique across kinds, so the next authored-Theme (`kind: theme`) version is v0.13. This is a naming detail, not a design risk; it is a fresh file either way.
4. **Why the v0.9→v0.10 Layout Profile bump requires `direction`/`gap` on a v0.10 legend slot rather than defaulting them.** A silent default would leave one more legend dimension decided by a constant a document cannot reach — the exact defect acceptance item 4 names. Requiring them on the new version, while leaving v0.9 exactly as it behaves today until migrated, satisfies the criterion for every document that adopts the fix without breaking the unmigrated corpus. This mirrors how every prior Layout Profile bump handled a newly-required field.
5. **Migration cost.** 14 public Themes declare roles today; only Themes that also declare a `legend` slot (`wallboard.yaml` today, plus the two examples the implementation plan adds a legend to) need a `legend-swatch` role added. No Theme without a `legend` slot is affected. The existing `E_THEME_ROLE_REQUIRED` diagnostic already covers a Theme that declares `legend` without the new role, so this is enforced without a new diagnostic identifier.

## Risks and gates

- **Milestone shape/size regression.** `02-programme-board`'s legend must show the exact diamond and exact height any milestone on that slide has; the implementation slice's test asserts bit-for-bit equality between a real milestone's `path_commands`/bounds construction inputs and the legend swatch's, not merely "looks like a diamond".
- **Relation-legend paint isolation.** Tagging a legend relation `source_kind="legend"` must not let it fall into the `scale_paints` override meant for object-level relations (there are none today, but the hook exists generically); the implementation review must show the override only ever fires for `scale:`-prefixed source refs, as today.
- **Byte batch discipline.** Only `02-programme-board` (shape/size of existing swatches) and `03-launch-campaign` (a new `legend` slot) are expected to change. Any other public SVG diff in the regeneration batch is a defect, not an accepted side effect, and must be attributed before the implementation slice is accepted.
- **Schema-inventory bookkeeping.** Both bumps (`theme-v0.11`→transitioning/`theme-v0.13`→live, `layout-profile-v0.9`→transitioning/`layout-profile-v0.10`→live) must land in `schemas/schema-inventory-v0.1.yaml` in the same commit as the schema files, per repository convention, with `removalSlice` left for a later cleanup slice, not this one.

No unresolved user choice remains for phase 1. The one open question for the implementation slice is exactly which existing example's Layout Profile (`wallboard.yaml`) is migrated to v0.10 versus left on v0.9 for one release cycle; the design plan already resolves this ("migrate `wallboard.yaml`; add a new legend to `print-portrait.yaml` for `03-launch-campaign`"), so it is a scheduling note, not a design gap.
