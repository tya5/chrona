## Architecture and release conclusion

One engine behind every front end: the command line and the tool core call the same two functions (`operational.store_commands.run_store_command` and `open_store_reader`), the engine itself is unchanged, the tool core reaches `operational` through that one named module (`tools/check_import_direction.py` rule, with tests that every other `operational` import from a tool and any from the binding still fails), and the SDK is still imported by the binding module only. The registry is one stable document: both tools are listed whatever the flag is, `chrona mcp --list-tools` needs no SDK, and the four older tools are byte-identical in it. Tool set `chrona/agent-tools/v0.3`. Rows 2, 13 are `narrowed` and rows 3, 18 are `deferred`, each with an open successor: [#902](https://github.com/tya5/chrona/issues/902) (resolve, guided authoring, revert tool, inline commands, a multi-process lock) and [#812](https://github.com/tya5/chrona/issues/812) (Store reading tools).

Findings of the architecture review that changed the design before code ([work record](../../planning/active/issue-813-mcp-mutating-tools.md) section 4): Spec 10 section 9.1 contradicted the shipped tool and now has a scope note (R1); the Store configuration was an unguarded write surface and every configured root must now lie inside the workspace (R2). One later change was recorded with the code: #829 landed `message` on every Automation Result row, so the tool reuses the engine's messages instead of owning a second text (section 3.5).

Disclosures:

- **No real agent-host session was run.** The write path is exercised through the SDK client, an in-process client and the real server over stdio, not a host application; the host-transcript issue [#814](https://github.com/tya5/chrona/issues/814) is still open and is unchanged by this work.
- **Cross-process writes to one Store are not guaranteed.** The server serializes its own calls; a command line and a server writing one Store at once can interleave the ledger and tip read-check-write. A lost race on a revision directory fails and never overwrites. A planted symlink inside the Store at one of the engine's temporary file names would be followed; both are outside the threat model of a local process the user started and are recorded for [#902](https://github.com/tya5/chrona/issues/902).
- **`destructiveHint: true` does not mean something is overwritten.** It is the owner's instruction that the metadata not understate a write; nothing is overwritten.
- **The default is read-only.** A deployment that wants writes must pass `--allow-write`; whether the host asks the user before calling the tool is the host's setting.
- **Windows and macOS evidence is the exact-main three-OS run named in the closing comment.** The binding and stdio tests skip without the extra and the link tests skip only where the OS cannot create a symlink; the run's job logs decide whether they ran there.
- **A mutation check was run in [PR #928](https://github.com/tya5/chrona/pull/928)** (14 guards weakened or deleted, 14 killed after one binding-default survivor was closed with a test), not in CI.

Exact review-bearing-main three-OS CI and newest-Python materializer run must pass before closing #813; record that run in the issue closing comment.
