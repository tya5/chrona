## Reviewed ambiguities and resolutions

1. **Is a stride ever legitimate within a colliding run?** No: self-fit (`axis_label_fits`) is computed once per candidate from that candidate's own clipped interval and does not depend on any other candidate's disposition. A stride applied to a run of already-failing candidates cannot make any of them fit; it can only retain a subset that still does not fit, which the issue's own wording ("removes only labels that collide") forbids. The design's "drop exactly the non-fitting set" is therefore the loosest rule the issue's stated bound ("at most... a stride to the colliding run") permits — reviewed and confirmed, not merely asserted.
2. **Does removing the self-containment check's role as sole collision evidence need a real two-label geometry check instead?** No, reviewed against the reproduction evidence: `axis_intervals` produces contiguous, half-open, non-overlapping buckets, so a label inside its own bucket cannot reach a neighbour's. The `visible-overflow` control render in the evidence confirms the converse (a self-non-fitting label produces a real `W_SCENE_TEXT_INTERSECTION` with its neighbour) and that suppressing exactly that label removes the intersection. Adding a second, geometry-based collision detector would duplicate this without changing any outcome, so it is not part of this design.
3. **`AxisThinningSchedule.stride`/`.phase` removal — public contract risk?** None: the dataclass is Layout-internal (`axis.py`, consumed only by `surface_composer.py` and directly by `test_axis_placement.py`); it is not serialized to any schema, Scene, or public resource. The one direct test of the function is corrected in the same slice, not preserved as dead compatibility surface (AGENTS.md: do not retain compatibility behavior that defeats the approved design).
4. **`W_LAYOUT_AXIS_DENSITY` payload change — diagnostic-vocabulary risk?** Checked against `conformance/declared-vocabulary-policy-v0.1.yaml` and `docs/diagnostics/inventory.md`: neither registers `W_LAYOUT_AXIS_DENSITY` or `W_LAYOUT_AXIS_LABEL_THINNED` (they are tier-local strings appended directly, not `FitWarning` instances the inventory tool scans), so the payload correction has no conformance-fixture or inventory-regeneration dependency beyond the two test-suite assertions named in the design.
5. **Public evidence: is losing the `stride=2:phase=1` assertions in `test_materialize_example.py` an acceptable, intended change?** Yes: both fixtures (`examples/orion-asic` `gates`, `examples/halcyon-1` `07-replan-baseline`) exercise exactly the defect this issue reports (a clipped edge bucket under `thin-with-record` dropping otherwise-fitting labels), reproduced and quoted in the evidence document. Showing more of their own axis labels is the fix working as designed, not a regression; the implementation plan must attribute every changed byte in both fixtures to this rule, not treat it as incidental corpus drift.

## Risks and gates

- **Batch attribution:** the 21-materializer regeneration must show that only `gates` and `07-replan-baseline` (and any other fixture the batch newly discovers with a clipped `thin-with-record` edge) change, and that the change is exactly "more labels placed, same geometry, same non-thinned label positions." Any other change is a defect to report before acceptance.
- **`AxisTierOutcome` invariant migration:** the `surface_quality.py` change and the `axis.py`/`surface_composer.py` change must land in the same slice; landing the invariant tightening first would make the still-buggy code raise `E_LAYOUT_AXIS_OUTCOME_INVALID` on any real `thinning-stride` outcome, and landing it after would let a manifest accept a value the corrected code never produces (harmless, but redundant and quickly stale — implementation plan orders it with the code change).
- **ja-JP reproduction gap:** the exact CJK case from the comment was not re-rendered through a locale-specific fixture (the mechanism is instead confirmed via the existing English `07-replan-baseline` quarter case, which fails the same way). If the owner wants a direct ja-JP regression test, it needs a `Noto Sans JP`-backed fixture; this is named as an open decision in the implementation plan rather than silently added or dropped.

No unresolved user choice remains beyond the ja-JP fixture question above, which does not block implementation planning.
