# Architecture Review — Preset Catalogue (#429) and the Editorial Preset (#383)

**Design:** [design](../../design/issue-429-383-preset-catalogue-design-2026-09-27.md). **Plan:** [design plan](../../planning/active/issue-429-383-preset-catalogue-design-plan-2026-09-27.md). **Reviewed against:** `presentation-preset-v0.1`/`preset-library-v0.1` (unversioned by any living spec), Specification 62 (`Proposed`), Specification 39 (axis tier appearance, §1.2, #426), Specification 55/59 (design space, prefer-ladders), the layer-ownership rule in `AGENTS.md`, and the boundaries owned by #479/#466/#467/#490.

## 1. Contract and schema impact

No schema version changes anywhere. `presentation-preset-v0.1` and `preset-library-v0.1` are extended only with data (four new `library.yaml` entries; `default.yaml`'s `body.resources` addresses change value, not shape). `render-context-v0.16`'s `store`/`revision` fields are already untyped provider-specific objects — using `{provider: package, identity: chrona.resources}` for a `view`/`theme`/`colorScheme`/`layout` reference is a new *use* of an existing field, not a new field. This is the additive-property precedent the project already applies to Theme (`progressInset` in #430, `chipPadding` in #428) extended correctly to a resource-reference shape rather than a Theme role. No version bump is warranted or proposed.

**Finding, not a defect:** the render-context schema's `store`/`revision` being untyped objects means nothing in the schema itself distinguishes a legitimate `package`/`chrona.resources` locator from an attempt to reference an arbitrary absolute path. `_package_resource` (`materialize.py:57-65`) already guards this at the code level (rejects absolute, escaping, or non-`chrona.resources`-package paths), so the design does not introduce a new escape surface — it exercises an existing guarded path for a new reference kind. Confirmed by reading the guard, not assumed.

## 2. Layer ownership

Checked against the declared boundaries (View = intent; Theme = tokens; Layout = measurement/placement/geometry; Scene = completed primitives; adapters serialize only):

- The four directions' distinguishing content is View decisions (grouping, table columns, row-mark composition, axis tiers) and Theme values (paint, typography, dash, inset, swatch sizing). Neither crosses into Layout, Scene, or adapter territory; both are declarative resources of an already-supported kind.
- `chrona preset list`/`render --preset <name>` and `resolve_named_preset_members` are CLI/usecases resolution code — turning a name into a resource identity — which is exactly the CLI's existing role (`_run_render` already turns a path into resource identities the same way). No policy is added; the resolver does not choose *which* preset, only *where its bytes are*.
- Repointing `default.yaml` and retiring `default_preset_root()` removes a bespoke resolution path in favor of reusing the general one — a reduction in special-casing, which the project's stated preference ("prefer a structural refactor when it removes mixed ownership," `AGENTS.md` §5) favors over keeping two parallel default-resolution mechanisms.
- The corpus-evidence mechanism (§5 of the design) adds no code. It is worth stating precisely what layer owns the finding: `materialize.py`'s `_copy_reference`/`_reference_payload` already treat "how to fetch member bytes" as orthogonal to "which reference kind this is" — that separation is what makes the new use free. This is good evidence the existing design already drew the boundary correctly; nothing needed to be reopened to reach it.

**No layer-boundary violation found.**

## 3. Consistency with adjacent designs and specifications

- **Spec 62.** The design's only change to Spec 62 is a status/predecessor note in §1.1, explicitly not claiming any of the deferred resolver's authority (no `chrona package *` command, no lock, no registry, no candidate/acquisition flow). Re-read against §1 ("non-authority... cannot introduce a Project/domain field, scheduling rule, semantic registry entry, Scene primitive... or host default" for a *Presentation Package*) — irrelevant here, since nothing built is a Presentation Package; it is the existing finite `presentation-preset-v0.1` bundle the specification itself calls its predecessor. Consistent.
- **Spec 39 §1.2 (#426).** Editorial's two-tier band (navy quarter/grey month, reversed label colour) is exactly the case #426 built View v0.24 for; the design cites the acceptance review rather than re-deriving the capability. Consistent, and it correctly does not depend on the still-open non-literal fold-in (#490), which only Wallboard needs.
- **#398 (mark height/offset/paint-order).** Technical print's outline-planned-with-inset-actual and Muted executive's offset dashed baseline are both restatements of the container/inner pattern #398 already shipped; the design does not propose extending #398, consistent with #425's own finding ("the bar vocabulary is finished").
- **#427 legend miniatures.** The design's Editorial legend (six entries: capsule outline, coral capsule, diamond, elbow+arrowhead, dashed segment, grey rect) maps onto `swatch_geometry`'s existing dispatch buckets (`point`, `mark`, `line`, `legacy`) read in `surface_composer.py:1867-1908` — `MARK_GEOMETRY_ROLES` covers the capsule/coral-capsule pair, `milestone` covers the diamond, `("asOf","dependency","dependency-critical")` covers the dashed segment and the elbow-with-arrowhead (a `RelationPlacement` with `marker_end`). The grey weekend rectangle is the `legacy` bucket's plain square, which is a faithful primitive for a rectangle swatch — no gap there, contrary to what a shallow reading of #425's "three of them are squares" could suggest for *this* direction; Wallboard's seven filled circles are the case that bucket table does not yet have a name for (`milestone`-shaped is one, but a plain filled circle swatch for a category key is not one of the four dispatch buckets). **New finding, not previously named**: a `point`/circle-shaped category swatch with no on-chart mark counterpart is not one of `swatch_geometry`'s buckets. This only matters for Wallboard, which is already blocked and last in sequence; naming it now so the Wallboard slice's design step does not have to rediscover it.
- **#467 (lane rows, other session).** None of the four Views declare `rowDecoration`/lane packing; the design correctly treats this as "nothing to reconcile today" rather than "safe forever." Flagging a **process risk**, not a design defect: if #467 changes default row-block-extent computation before Technical print/Muted executive/Wallboard land, their bundle Theme values (row pitch, mark height ratio) authored against today's `required_row_block_extents` may need re-tuning. The implementation plan must re-check byte identity against `main` at each slice's start, not just at this review's time.
- **#479 (other issue, group order/palette-by-appearance/legend preference).** Muted executive's scoped, fixture-only `grouping.order` is consistent with #479's own listed scope ("project-generic presets cannot order groups by data") — this design does not claim to solve the project-generic case, and says so in both the design and here. Acceptable as a named, bounded exception, not a workaround, because the gap is recorded against #479 rather than silently generalized.

## 4. Risks

1. **Public-visible default change.** Repointing the bundled default is the single highest-blast-radius change in this design: every render that omits `--preset` changes appearance. Already flagged in the design plan's open decisions; restated here as an architecture-level risk because it is the kind of change AGENTS.md's publication discipline exists for — the implementation plan must diff every changed public artifact and attribute each change, not assume "expected" excuses inspection.
2. **Id rename touches seven files.** Listed in the design plan; mechanical but must be done in the same slice as the resource repoint, not split, or a stale id could resolve to new content, which is exactly the identity-mismatch class of bug the preset contract's own validation (`copy_builtin_preset`'s `value.get("id") != member.get("id")` check) exists to catch. The rename should be exercised by that existing validation, not bypass it.
3. **Corpus-evidence path is exercised for a new reference kind for the first time.** The design's claim that `materialize.py` needs no code change is based on static reading, not a run. The implementation plan's first Editorial slice must prove it by actually materializing a context with a `view`/`theme`/`layout` `package`-provider reference before relying on it for four presets' worth of evidence — if it fails in some untested corner (e.g. the theme-inheritance branch at `materialize.py:93-109` assumes `address` is meaningful as a *within-example* relative path for cycle detection, which may behave oddly for a `presets/bundles/...` address if Editorial's Theme ever declares inheritance), the fallback is copying the bundle's bytes into the example project's own directory instead — cheaper to fall back to if discovered early than if discovered on the fourth preset.
4. **Wallboard's circle-swatch gap (§3 above) is new and unfiled.** Should be recorded on #427-adjacent ground or as its own small issue before Wallboard's slice, not rediscovered mid-implementation. Implementation plan names this explicitly.

## 5. Decision

**Approved to proceed to the implementation plan**, with the four open decisions in the design plan (default id rename, milestone-in-capsule as a named gap, Muted executive's group-order scoping, HALCYON-1 as the shared fixture) left for the lead/owner's explicit confirmation before slice 3 (default repoint) and slice 5 (Muted executive) start — nothing earlier in the sequence depends on those answers. No layer-boundary violation, no unauthorized Spec 62 authority claim, no schema version bump required. The one new finding (§3, Wallboard's circle-swatch gap) is recorded here and carried into the implementation plan rather than opened as a separate issue prematurely, since Wallboard is already blocked on #490 and not scheduled.
