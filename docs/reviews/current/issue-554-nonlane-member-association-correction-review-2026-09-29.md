# Architecture Review — Non-Lane Member Association Correction (#554)

**Decision:** approve the [correction](../../design/issue-554-nonlane-member-association-correction-2026-09-29.md) before any further #554 product edit. Public default HALCYON evidence at `daffc65f` shows the original lane-only contract did not meet the literal both-side association criterion.

Specs 08 and 50's Layout/Scene/adapter seam remains intact: Layout resolves the own mark, measured distance, bounded route, and suppression/failure; Scene projects the completed Path and exact host identity; SVG only serializes. Spec 38's lane membership and exact obstacle inventory remain lane-only, so a non-lane leader must not acquire synthetic lane identity or a lane obstacle facet. The existing `memberLabelLeader` semantic and Theme dependency stroke are reused without conflating presentation association with a Project dependency. Spec 50's general visible-overflow fallback is explicitly narrowed for member names with an own mark: a required name may overflow its slot only if bounded to or routed back to that mark; otherwise the named Layout error is required. Other label families retain their current fallback. The existing finite non-lane candidate search remains finite; this correction adds association validation, not a new search policy.

The completed ReviewRow band is carried as explicit internal route bounds, distinct from chip-expanded candidate bounds. Endpoint-only route exemptions prevent a leader crossing unrelated required text or marks. Route failure must be tested against the declared next candidate, and every emitted label with an own mark must pass the Scene/SVG association check through exact `hostPlacementId`, never a nearest-mark guess. No public schema migration is needed; affected generated evidence may change. #554 acceptance stays pending until the correction, materializers, main CI, and release review are published.
