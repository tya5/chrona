# Issues 259, 278, and 279 Design Plan

## Scope and order

This plan addresses contributor-install reproducibility (#259), semantic rounded
geometry (#279), and automatic milestone folding (#278). The order is #259, #279,
then #278. #259 is an isolated contributor-contract correction; #279 establishes a
Theme/Layout/Scene/renderer pattern that #278 must not bypass; #278 changes automatic
Review projection and therefore requires the most extensive design review.

## Investigation and design questions

### #259 — Contributor environment contract

Confirm the dependency set actually required by the documented `pytest` command,
the optional-renderer policy, and CI's wheel-install coverage. Design must select one
truthful contributor command and ensure documentation, package extras, and tests use
the same contract.

### #279 — Rounded semantic geometry

Determine separately how Theme declares corner treatment for span marks, point/diamond
marks, and relation paths. `ScenePrimitive.corner_radius` is not sufficient for a
diamond or an orthogonal path by itself. The design must define a typed renderer-neutral
corner-treatment handoff, prevent non-mark rectangles from inheriting it, and retain
Layout ownership of mark geometry. It must account for the existing SVG and typeset
renderers, Theme metric resolution, semantic registry uniqueness, and public examples.

### #278 — Automatic point folding

Define an automatic row-membership policy rather than extending explicit-row syntax.
The design must state eligibility, deterministic predecessor tie-breaking, group-header
semantics, table-subject and label behavior, comparison-facet handling, row/track
allocation, relation routing, and the behavior when a declared fold target is absent.
It must preserve the current `own-row` result by default and keep Project relation truth
out of Scene.

## Required design review

Before implementation, review each design against the Project → Scheduler → View
projection → Layout placement → Scene projection → renderer pipeline. In particular,
neither Theme nor Scene may infer schedule structure, and renderer-specific syntax may
not become a persisted View or Project decision.

## Publication and verification gates

Publish the completed English design and its architecture review before implementation.
Then publish a separate implementation plan naming atomic PRs, target files, acceptance
tests, full-suite gate, public materializer checks, and generated-SVG evidence. Each
implementation slice is independently reviewed, tested, and merged serially.
