# M27 Presentation Product-Path Recovery Design Plan — 2026-09-21

**Status:** Active design plan; no M27 implementation is authorized.
**Owns:** Resolution of Issues #29, #30, #31, and #33. Issue #28 is verified as a
closed regression only after its stale report is reconciled with the v0.5 test evidence.

## 1. Outcome

Restore the declared Chrona review-presentation vocabulary on the sole
`render-review` product path: typography, title/subtitle, calendar axis bands, table
missing-value presentation, groups, plan-versus-Actual marks, variance and
missing-Actual cues, milestones, routed dependencies, legend, annotations, and the
declared detail/summary families. The product output MUST be reproducible from an
immutable Render Context and its resolved resources.

The outcome is not a compatibility restoration or a Python-coded example theme.
View, Detail, Layout Profile, Theme, and Color Scheme remain the user-editable
declarative authorities. Runtime code may implement only their generic resolution,
composition, routing, and serialization mechanisms.

## 2. Fixed invariants

1. Project, Schedule, Actual, and View selection remain semantic authorities; Scene
   and SVG never reschedule, invent Actuals, infer title matches, or mutate inputs.
2. Layout Profile resolves physical regions and the Layout Manifest. Scene consumes
   that resolved result and never restores a superseded layout grammar or hard-coded
   example geometry.
3. `ResolvedPresentationInput` and `SurfaceContentInput` from Specification 30 are
   the only derived content boundary. SVG receives a completed renderer-neutral
   `SceneSurface`, never unresolved View/Theme/Profile documents.
4. Theme owns typography, paints, strokes, markers, patterns, opacity, and corner
   treatment; Color Scheme supplies only its declared color values. No renderer-local
   palette, font size, missing-value text, or marker default is permitted.
5. Every rendered primitive retains stable scene identity, source provenance, semantic
   facet, visual role, bounds, and accessibility text. A renderer serializes those
   values and validates output bounds; it does not reinterpret presentation policy.
6. Example artifacts are generated by a manifest-driven materializer and checked for
   byte-identical reproduction from declared immutable inputs.

No implementation may start before D27-5 is published. Discovery that requires a new
semantic authority, resource type, or output target pauses the gate and amends this
plan before any code change.

## 4. Required design decisions

### 4.1 Single product composition path

Decide and document whether the existing `SceneSurface`/`scene_svg` serializer becomes
the product serializer, or whether the current review Scene is expanded to the same
complete contract. In either case, `render-review` has exactly one composition path;
the selected path must consume the Layout Manifest and must not retain a parallel
legacy fallback. The design must list modules that become reachable, migrated, or
retired.

### 4.2 Declarative display policy

Define the owning fields and diagnostics for:

- heading/subtitle and role-specific typography;
- calendar-aligned axis bands, density selection, label formatting, and measured
  clipping/overflow;
- `tableColumns[].missing` values (`blank`, `em-dash`, `unknown`) as presentation
  values rather than literal enum text;
- group surfaces/headers/row shading and group-plus-facet Theme paint precedence;
- planned/baseline/Actual/milestone marks, variance, and missing-Actual pattern/text;
- legend, coverage, annotations, summary, detail, observation, and milestone-digest
  slot families;
- finite routing and marker policy for dependencies, leaders, and explanatory arrows.

### 4.3 Example reproduction

Define one generic materializer that resolves each example manifest into a temporary
immutable Store closure, invokes the public CLI, and checks the declared SVG artifact.
It must not import source modules to bypass CLI composition, depend on Git `HEAD`, or
make ASTER-specific decisions. Checked-in artifacts are regenerated only after the
semantic output contract is accepted.

## 5. Design evidence required before implementation

- positive and negative schemas/fixtures for every new or clarified declarative field;
- a traceability matrix from every lost #33 capability to its owning resource,
  Scene primitive, SVG serialization, and acceptance assertion;
- at least one generic and one existing-product fixture with multiple groups,
  planned/Actual variance, missing Actual, milestone, dependency, annotation, and
  summary/detail content;
- measured axis collision and output-boundary fixtures, including a rejected required
  label rather than silent clipping;
- no-raw-fallback proof: a malformed or absent required resolved input is diagnosed
  before Scene/SVG construction;
- a whole-design review that explicitly rejects renderer-local policy and
  source-ID/example-specific branches.

## 6. Planned implementation ordering (not yet authorized)

After D27-5, prepare a separate implementation plan with bounded slices for shared
input normalization, complete Scene primitives, SVG serialization, declarative policy
resolution, materialization/reproduction, and final regression acceptance. Each slice
will add failing evidence first, pass full inherited conformance, receive a
design-conformance review, and be published to `main` before the next slice.
