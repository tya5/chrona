# Design Plan — Group Bands and Headers (#481)

**Public base:** `bf98f9b0` on `main`. **Source of truth:** [Issue #481](https://github.com/tya5/chrona/issues/481), Specification 45 (§ Group headers), Specification 50 §3.4 (Groups and legend), Specification 49 (semantic registry: `groupHeader`, `groupBand`, `rowBand`, `groupHeaderBand`). **Related:** #470 (the `control-room-dark` tuning that found all three defects, PR #472); this issue does not touch #466/#467 (annotation placement, lane rows, owned by the other dev session) or #478 (closed/near-closed).

## Published baseline, inference, and unverified facts

Reproduced on `bf98f9b0` with a copied `control-room-dark` preset (`.venv/bin/chrona preset copy control-room-dark --output work/crd`) and HALCYON-1 (`--actual`), editing `work/crd/layout.yaml` (`reviewSurface.backgroundExtents`) and `work/crd/view.yaml` (`body.backgroundDecoration`).

1. **Row stripes and group bands exclude each other.** `src/chrona/presentation/layout/surface_composer.py::compose_surface_layout` emits row-stripe shapes (`rowBand`) first, then group-body shapes (`groupBand`), into the same `shapes` list (lines ~910–925 on the base commit). `renderers/v05_svg.py:139` paints primitives sorted by `(paint_order, original_list_index)`. All five shipped presets bind `group-band` and `row-band` to the **same** `backgroundPaintOrder` (`10`) in Theme, so ties resolve by list order and the group band always paints last, fully hiding the (opaque) row stripe wherever both extents overlap. Emitted-scene evidence with `rowBand: both, groupBand: both, groups: all`: `group:ait` bounds `{block: 157.1, blockSize: 150.0}` painted after `row-band:integration` `{block: 157.1, blockSize: 30.0}` at the same `paintOrder: 10` — the row stripe primitive exists in the Scene but is fully covered in the SVG. This is why 4 of 5 presets restrict `groupBand` to `table` (so it never reaches the timeline where stripes run) and `elevated-light` uses no stripes at all — the summary's framing ("forces every preset to choose") is accurate, not a documentation gap.
   - Confirmed by prototype: reordering emission (groups appended before rows, so a same-order row stripe is the later/topmost primitive) makes an alternating row stripe visibly paint over an opaque group band while an unstriped row still shows the group's own tint — i.e., both decorations are visible "across the whole surface" simultaneously. PNG crop inspected at 130–340px band of the HALCYON‑1 render.
   - A `groupBand` with Theme `backgroundTreatment: outline` (stroke only, no fill) already composes with a `rowBand: both` stripe today, without any code change — confirmed by rendering (`Assembly, integration and test` group boundary as a stroked rect over visible alternating stripes). This is the "group bands as outlines" technique from the acceptance text; it needs no additional design correction, only that presets/docs demonstrate it (Theme authoring: `role.stroke` and `strokeWidth` must be set, which today none of the five presets do for `group-band`).
   - `groupHeaderBand` already paints unconditionally whenever a group has a header (`group.header_bounds is not None`), independent of `backgroundDecoration.groups`, and at a higher `backgroundPaintOrder` (`11`). This is the existing "header-only" technique (`groups: none` + `rows.presentation: header`); it is unaffected by the row/group reorder.
2. **A group's own band excludes its own header.** `GroupPlacement.content_bounds` is built from `row.bounds` only (`surface_composer.py` group-building loop, ~lines 746–761); the header block is carved out *before* the first row but never folded into `content_bounds`. Confirmed: with `presentation: header` and `groups: alternate`, `group:ait` (selected, index 0) has `block: 157.1` while `group-header-band:ait` (always painted) has `block: 137.1, blockSize: 20.0` — the header sits directly above and outside `ait`'s own band. Under `alternate`, the unconditional `groupHeaderBand` shape is painted for **every** group regardless of the body-band selection: `group-header-band:bus` (`bus` is index 1, *not* selected for a body band) is painted at `block: 307.1`, flush against the end of `ait`'s band (`block 157.1 + 150.0 = 307.1`). Because `group-header-band` and `group-band` are bound to the same fill color (`surfaceRaised`) in the shipped presets, `bus`'s header visually reads as the last striped row of `ait`, not as the start of `bus` — this is the literal defect narrative.
3. **`group-header:*` text ignores the Theme's `groupHeader` role.** `surface_composer.py` places group-header text with `typography_role="text"` (not `"groupHeader"`), confirmed emitted-scene `textLayout.weight: 400` for `control-room-dark`, whose Theme declares `groupHeader.fontWeight: weight.bold`. The semantic registry already declares a `groupHeader` binding (`theme_role: "groupHeader"`, `docs/specification/49-semantic-presentation-contract.md` line 57), and `groupHeader` is already a required Theme typography role (`fontFamily/fontWeight/fontSize/…`) plus a `groupHeader.fill` color binding — declared in `control-room-dark`, `mission-light`, `print-mono`, but **absent** from `elevated-light`, `executive-light`, and five `examples/*/themes/*.yaml` files (`aster-ssd` ×2, `controller-z-ja`, `orion-asic`, `controller-z` ×3). Switching the placement call to `typography_role="groupHeader"` in a throwaway prototype reproduces `E_THEME_ROLE_REQUIRED: /body/roles/groupHeader/fontFamily` for every Theme lacking the role — confirmed against `elevated-light`/`executive-light` presets and a broad focused-test run (`tests/unit/chrona/presentation`, `tests/integration`, `tests/cli`): 76 failures, all traced to one of the 9 Theme files above (no inline test-fixture theme dicts are affected; every failure loads one of those files by path).

## Literal issue acceptance ledger

1. "Row stripes and group bands can be combined across the whole surface: stripes above group bands, or group bands as outlines or header-only."
2. "A group's band includes its own header row, under both `all` and `alternate`."
3. "`group-header:*` text uses the Theme's `groupHeader` role; a test asserts the declared weight."

## Use cases and decisions to close

1. **Combine stripes and group bands.** A reader wants both a group boundary and a full-width row stripe. Decide the default z-order contract: should Layout *guarantee* row stripes paint above group bands (independent of Theme `backgroundPaintOrder` ties), or is it sufficient that the outline/header-only techniques already work and the paint-order tie is a preset-authoring gap? The prototype shows a minimal, purely structural fix (emit group shapes before row shapes) makes the stripe-over-band combination work out of the box under the *default* (tied) paint order every shipped preset currently uses, without any Theme change — this is the smaller contract and is preferred.
2. **A group's band includes its own header.** Decide whether "the group's band" means (a) `content_bounds` used by the `groupBand` semantic grows to include the header rows, with the `groupHeaderBand` accent painted only when that group is selected for banding (`all`, or its `alternate` turn) — while remaining fully unconditional under `groups: none` (preserving the "header-only" technique) — or (b) some other geometric reconciliation. (a) is the minimal fix that removes the "orphan header" illusion (a non-selected group's header no longer paints at all under `alternate`) while leaving every other documented technique intact.
3. **`groupHeader` role reaches text.** Switch the placement call's `typography_role`/`semantic_id` to `"groupHeader"`. This requires adding the already-declared-but-unused `groupHeader` typography role (and a `groupHeader.fill` paint binding) to the two preset bundles and seven example Theme files that currently omit it — sized precisely by the reproduction above, not open-ended. Preset/example authors choose the declared weight per Theme (e.g. `weight.bold` where already available, `weight.regular` for `elevated-light`/`executive-light`, which use group cards and did not intend bold headers), so no public visual regression is silently introduced.

## Responsibility and architecture review questions

- Layer ownership (AGENTS.md, Specification 49): the fix is entirely inside Layout (`surface_composer.py`, one function). View's `backgroundDecoration` (rows/groups selection) and Layout's `backgroundExtents` (table/timeline/both per role) keep their existing schemas and meanings; Theme keeps `backgroundTreatment`/`backgroundPaintOrder`/`groupHeader` typography as tokens. No schema or adapter changes are anticipated.
- Does reordering shape emission change any other consumer of paint order (e.g., `_validate_background_shapes`, which only inspects translucent `fill` shapes pairwise and is order-independent)? No — confirmed by reading; the overlap check is symmetric over the collected list, not position-sensitive.
- Does extending `content_bounds` to include the header block affect other `content_bounds` consumers (`_completed_canvas` viewport union at line ~2278, the folded-milestone header-expansion replacement at line ~1257)? No — `_completed_canvas` already unions `header_bounds` separately (extending `content_bounds` only grows an already-included region); the folded-header replacement preserves whatever `content_bounds` it is given unchanged.
- Does gating `groupHeaderBand` by the same `banded` selection under `all`/`alternate` (while remaining unconditional under `none`) change any existing public preset's rendered output? All five presets use `presentation: header` with `groups: all` (never `alternate` or `none`) today, and under `all` every group is already selected, so `banded` is always true — no observed preset output changes for defect #2's shape-gating alone. The `content_bounds` extension (header now included in the `groupBand` rectangle) can move the painted group-band's top edge upward by `timeline.groupHeader.blockSize`, which is a public byte change for every preset that combines `groups: all|alternate` with `presentation: header` and a non-`none` `groupBand` treatment — i.e., every shipped preset except `elevated-light`'s stripe-free card. This must be attributed, not silently accepted.
- Does the `groupHeader` typography-role switch require a Specification 45/49/50 update? Yes — Specification 45's "Group headers" paragraph currently says only "Scene emits group-header text" without naming a role; it must name the `groupHeader` Theme role explicitly, matching Specification 49's existing (already-published, currently unused) registry entry. Specification 50 §3.4 needs one sentence stating that a group's header participates in its own band's decoration selection.
- Nine Theme files (2 shipped presets, 7 `examples/*` themes) must gain a `groupHeader` typography role and a `groupHeader.fill` binding before this ships, or every render/CLI/materializer path touching them breaks with `E_THEME_ROLE_REQUIRED`. This is a real, bounded implementation cost that must be an explicit slice, not incidental cleanup.

## Ordered design slices and acceptance evidence

1. **D481-1: design and architecture review.** Select the three fixes above (emission order; header-inclusive `content_bounds` with `banded`-gated `groupHeaderBand`; `groupHeader` typography role), specify the exact geometry and gating rules, and the Specification 45/50 amendments. Publish `docs/design/issue-481-group-bands-and-headers-design-2026-09-26.md` and the architecture review.
2. **D481-2: implementation plan.** Slice by defect: (I481-1) stripe/band layering — reorder shape emission, add a combined-surface test and a PNG-crop-inspected preset variant; (I481-2) header-inclusive group band — extend `content_bounds`, gate `groupHeaderBand`, add `all`/`alternate` containment tests; (I481-3) `groupHeader` typography role — switch the placement call, add the role + fill binding to the 9 Theme files, add a weight-assertion test; each slice regenerates and attributes public evidence for every preset it can change.

Issue acceptance needs a separate review with one row per literal criterion, direct test and rendered-output evidence, the batch materializer diff (attributing every changed primitive to one of the three fixes), and the green CI run.
