# Design Plan: Evidence closure, mark composition, and relation semantics (#392, #393, #401, #398, #396, #397, #399, #394, #395)

## Purpose

Complete the remaining presentation gaps as three coherent programs rather
than independent renderer patches. The programs preserve the authority chain:

```text
Project / Actual / Relation facts
        → View projection and selection
        → Theme treatment / Layout geometry
        → completed portable Scene
        → target adapter serialization
```

## Public facts and corrections

* #392's schema-derived coverage currently descends through Theme token types
  but not their finite value structures.
* #393's `annotationText` binding is bypassed. Its `iconMark` reachability
  claim is corrected by the Issue comment: mark-icon placement is live but
  lacks corpus evidence; that work belongs to #396 and #392.
* #401 accepts `en-US` and `ja-JP` but declares an unbounded locale string.
* #398, #396, #397, and #399 all require completed mark geometry and must not
  move clipping, inset, offset, or actual-state interpretation into an adapter.
* #394 and #395 both expose relation meaning lost between Project and Scene;
  source/target terminals and relation labels must share one relation fact
  projection instead of adding unrelated line branches.

## Program A — Contract evidence closure (#392, #393, #401)

### A1 — Schema-driven coverage depth (#392)

Replace contract-specific vocabulary traversal depth with schema-derived paths
for finite values in every live presentation schema. A schema enum/const added
below a Theme token value must appear without an extractor edit. Corpus
evidence continues to state only whether a declared value is realized; it does
not make unreached values invalid user input.

### A2 — Registry honesty (#393)

Use `annotationText` where annotation text is constructed, so a text primitive
has its own text purpose. Add a structural registry-reachability check across
Layout and Scene lookup sites. It distinguishes an unused binding from a
binding that is reachable but lacks corpus evidence; `iconMark` is the latter.

### A3 — Locale contract closure (#401)

The present product contract is explicitly finite: `en-US` and `ja-JP` only.
Narrow every public locale schema/guide surface to this set and retain explicit
rejection before rendering. Do not introduce host locale lookup or a partial
locale-table architecture without a third supported locale use case.

## Program B — Mark composition (#398, #396, #397, #399)

### B1 — Role geometry foundation (#398)

Theme supplies finite per-role lane-relative height, offset, corner treatment,
and paint-order intent; Layout resolves them against each assigned stack slot
and derives track extent from the maximum occupied geometry. Scene receives
only the completed bounds and its semantic reading order remains source-stable
even when paint z-order differs. Invalid role geometry diagnoses with the
semantic role and requested extent.

### B2 — Badge composition (#396)

A mark-targeted icon decorates, never replaces, its host mark. `iconMark` gains
its own Scene and Theme role, and its `iconScale` is measured against host mark
height rather than label typography. Layout insets the completed icon bounds;
the host remains the badge container. The first corpus evidence uses a circle
container and contrasting icon paint.

### B3 — Contained progress fill (#397)

Progress remains a fraction applied to a selected host mark. A completed Scene
primitive may name a completed host outline as a clipping boundary. Layout
creates that explicit containment; the adapter serializes it without inferring
rounded geometry. A partial fill clipped to a rounded host has a rounded leading
edge and square trailing edge.

### B4 — Open actual spans (#399)

An Actual observation may opt in to `openUntil: asOf`. View/projection preserves
this as a distinct open-ended actual fact, rather than fabricating `finish`.
Layout resolves the end against Actual Set `asOf`; a missing as-of produces a
task-specific warning and no invented mark. Scene uses a completed open-end
treatment that cannot be confused with the square trailing edge of progress
fill. `missingActual` remains exclusively the no-observation state.

## Program C — Relation semantics (#394, #395)

### C1 — Relation fact projection

Project relation endpoint kinds, signed/calendar-qualified lag, and semantic
class become typed View projection facts. Layout consumes only those completed
facts to select ports, route, terminal treatment, and label candidates.

### C2 — Independent terminals (#394)

Scene paths carry independent source and target marker geometry. Theme binds
the two terminal roles independently; `circle` is an admitted finite
non-directional terminal. Adapters serialize terminal geometry only, never
endpoint policy.

### C3 — Relation labels (#395)

View's relations policy gains a closed content selector. Initial content is
non-zero lag and endpoint pair. Layout measures, places, and suppresses labels
under the existing relation overflow policy, emitting a diagnostic only for
declared `diagnose`. Zero lag is omitted by policy, not represented as an empty
label.

## Required design reviews

Each program design must review Specification 32 (ownership), Specification 50
(label fallback/overflow), Specification 63 (finite capability ceiling),
Specification 64 (icon closure), accessibility/source ordering, schema
learnability, package/wheel closure, and current gallery/corpus evidence.

## Implementation sequence and publication units

1. Publish A design, architecture review, and implementation plan; complete
   and release #392, #393, #401.
2. Publish B design, architecture review, and implementation plan; implement
   B1 then B2/B3/B4 in independently reviewable commits, followed by one
   corpus/materializer evidence release closing #398, #396, #397, #399.
3. Publish C design, architecture review, and implementation plan; implement
   projection, terminals, labels, then corpus/materializer evidence and close
   #394 and #395.

Every unit runs focused tests; every program release runs full pytest,
conformance, structural checks, public materializer bytes, generated coverage
and gallery checks, wheel smoke, visual acceptance review, and three-platform
CI before Issue closure.
