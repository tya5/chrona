# Issues 121, 123, 124, 127, 147, and 149 — Design Program Plan

**Status:** Active design plan.  **Baseline:** `main` at `85982c2`, after the
merged output-target boundary of #122.  This plan authorizes design work only;
it does not authorize production-code, schema, fixture, or generated-artifact
changes.

## Outcome

The six issues form one contract-and-product-surface program.  Its outcome is
an author-facing schema inventory with one live contract per kind, a typed
validated closure boundary, an explicit Project hierarchy that can be
projected as WBS review content, an operable local authoring workflow, and
native Typst/TikZ output adapters.  The program must retain one semantic path:
Project and scheduling own planning truth; View owns selection and presentation
policy; Layout owns geometry; Scene owns primitive projection; renderer
adapters own serialization; and CLI owns invocation and filesystem I/O.

## Confirmed starting facts

* #119 and #122 are merged, so every closure resource is schema-validated and
  a typed renderer/artifact registry exists.
* `schemas/` still contains concurrent versions and its README is not an exact
  live index.  In particular, Project v0.1 and v0.2 coexist while the current
  core validation path remains v0.1.
* The closure currently has immutable envelopes but retains resource bodies as
  generic YAML-shaped mappings.  Thus #147 cannot be treated as a cosmetic
  annotation change.
* #123's hierarchy is domain truth, while #127's tree rows and rollup marks are
  View and presentation projections.  Neither may make scheduling semantics in
  a renderer or a View.
* The current materializer is a tool-only route and the guide contains an
  obsolete Render Context version statement.  #121 is an operational adapter
  change, not an alternate closure resolver.
* #149 is unblocked by #122, but a typesetter may not become a second geometry
  engine or an implicit evidence mode.

## Cross-design decisions that must be closed

1. **Schema authority and lifecycle.** Schemas remain authored acceptance
   contracts.  A schema is live only when a current product, conformance, or
   declared tooling path names it; examples alone do not make a superseded
   schema live.  The final design must distinguish schemas retained for a
   current operational path from staged/deferred designs, which must be removed
   rather than presented as available product contracts.
2. **One migration closure.** A kind may have only one live version after the
   program.  Version replacement may not leave a half-migrated materializable
   context.  When #123 changes Project acceptance, every current consumer,
   fixture, sample, closure contract, and context referring to Project moves in
   the same implementation publication.  #124's deletion gate follows that
   migration; it does not pre-delete the only schema still used by Core.
3. **Schema first, records second.** #147 records are immutable runtime forms
   built only after exact schema validation.  They narrow neither acceptance nor
   semantics.  A generated/conformance check must make an accepted schema field
   unrepresentable as an omitted record field.  Raw document mappings stop at
   the closure boundary.
4. **Hierarchy is semantic; WBS is projection.** A parent relation and its
   rollup rules belong to Project and are validated before scheduling.  View
   decides which parts of that tree become rows; Layout derives indentation,
   table allocation, label placement, and rollup geometry; Scene emits only
   completed primitives.  WBS codes must have a single declared source and must
   not be independently recomputed by renderer adapters.
5. **One closure and one CLI route.** `materialize`, `init`, `render`, and
   `render-review` use the same resource resolution and validation path.  Store
   discovery is CLI/application configuration, never a hidden resolver fallback
   or a mutation of immutable Context identity.
6. **Target adapters preserve the geometry seam.** Typst and TikZ consume only
   completed Scene/placement-derived primitives plus resolved tokens.  Native
   typesetter measurement, if offered, must be a separately declared,
   non-evidence draft mode; immutable evidence uses declared Chrona font assets
   and placements.  Unsupported target fidelity is rejected, never silently
   degraded.

## Implementation-planning prerequisites

No implementation plan may be written until D1–D7 are published and merged.
The ensuing plan must:

* identify an atomic migration unit whenever a versioned schema and its
  consumers change together;
* give each mergeable slice its files, diagnostics, focused tests, inherited
  suite, conformance, public materializer, and generated-output evidence;
* order implementation so #123 completes before #127, and typed closure and
  schema retirement do not expose mixed resource versions;
* require a design amendment and renewed D7 consistency review when
  implementation discovers an omitted invariant, ownership conflict, or schema
  limitation; and
* prohibit compatibility shims, renderer-local semantic policy, duplicate
  parsers, or force-pushing `main`.

## Publication gates

1. Publish and merge this design-program plan.
2. Publish and merge all D1–D6 design documents and D7 review as one complete
   design phase; no implementation planning or code begins before that merge.
3. Publish and merge the implementation program plan.
4. Implement only its approved slices.  Before every merge, fetch current
   `origin/main`, verify the target diff and PR state, run the slice evidence,
   and require the full inherited suite and public materializer checks where
   applicable.  Merge and publish serially; do not force-push `main`.

## Completion criteria for this planning phase

This phase is complete only when this document is merged and its baseline is
recorded.  It intentionally does not claim any of the six issues implemented
or closed.
