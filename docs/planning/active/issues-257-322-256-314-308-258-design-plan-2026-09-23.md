# Design Plan: Public Analysis, Example Roles, Presentation Intent, and Honest Draft Targets

## Scope and authoritative order

This programme addresses #257, #322, #256, #314, #308, and #258 in the
following order.  Each issue receives its own completed design, whole-
architecture review, implementation plan, implementation slices, acceptance
review, and serial publication before its successor begins.

1. **#257 — public schedule analysis.** Expose already-computed critical-path
   and total-float facts through the stable CLI JSON boundary.
2. **#322 — example role separation.** Re-inventory the current v0.6 contracts
   and split regression evidence, curriculum material, and design-gallery
   responsibilities without treating stale v0.5 observations as facts.
3. **#256 — deterministic presentation prefer-ladders.** Define typed View
   intent, Layout-owned rung selection, diagnostics, and a bounded extension
   registry before adding any new placement behavior.
4. **#314 — declared semantic colour scales.** Design a typed data-to-paint
   encoding with explicit domain coverage, Scheme-owned literals, derived
   legends, and no revival of the deleted projection rule engine.
5. **#308 — bar vocabulary disposition.** Reconcile the issue against current
   main: inside labels are delivered by #310 and state paint is owned by #314.
   Decide and document the remaining progress-fill scope as its own bounded
   successor rather than mixing it with scale work.
6. **#258 — honest draft targets.** Define the exact draft-render target
   contract and deterministic typesetter requirements, preserving immutable
   Context rendering as the reproducible evidence path.

## Programme constraints

Project, Temporal, Scheduling, Actual, and dependency semantics remain
independent of every presentation choice.  View owns authored selection and
intent; Theme/Scheme owns visual policy and literals; Layout owns measurement,
placement, collision, and rung selection; Scene owns renderer-neutral completed
primitives; adapters serialize or explicitly reject completed capability.

No compatibility parser, legacy `style` rule path, renderer fallback, raw SVG
authority, or second example/package registry may be introduced.  If an issue
reveals a boundary conflict, implementation stops and a published design
correction resolves it before work resumes.

## Per-issue design questions and evidence

### #257

Specify a versioned, deterministic CLI analysis payload; establish its relation
to scheduler diagnostics and placements; prove that public JSON exposes no
presentation policy.  Acceptance evidence includes CLI/use-case tests and a
HALCYON analysis fixture.

### #322

Measure the live schema and example corpus afresh.  Define separate ownership,
paths, commands, and gates for regression fixtures, teaching curriculum, and
gallery evidence.  Explain how public materializer byte evidence remains
authoritative without forcing teaching examples to be exhaustive.

### #256

Define a finite presentation-extension vocabulary, eligibility, ordered
prefer-ladders, selected-rung record, and diagnostic surface.  Establish that
an extension cannot select coordinates, bypass Layout quality checks, or make a
renderer decision.

### #314

Define encoding source, typed domain, explicit Theme mapping, Scheme range,
unmatched-value policy, legend derivation, and the ordering of semantic
projection versus appearance completion.  Inventory all existing role paths and
remove no code until a replacement contract is accepted.

### #308

Record delivered and superseded parts on the Issue.  For progress fill, decide
whether it is a semantic mark subpart, which layer owns its completed geometry,
and how it interacts with #256 labels and #314 paint without conflating their
contracts.  Create a successor only after that design is accepted.

### #258

Inventory draft and immutable render target capabilities.  Decide whether
draft rendering omits typeset targets or accepts a complete explicit
environment descriptor; define stable diagnostics and help text.  No draft path
may infer a host typesetter or weaken the Context closure.

## Publication and verification

Every design and review is published before its implementation plan.  Each code
slice has focused tests; each issue's acceptance runs the full parallel suite,
conformance, relevant structural gates, affected public materializers, generated
SVG comparison where applicable, and wheel plus isolated installed-wheel smoke
when package/public CLI behavior changes.  Before every push, fetch `main`,
inspect the exact range and diff, and push fast-forward only.
