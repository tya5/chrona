# Issues #353, #351, #352, and #358 — Design Plan

## Objective

Close the remaining visual-output correctness and portability findings before
the next gallery expansion: tested visual-capability diagnostics (#353),
declared multilingual font closure across Layout/PNG/PDF (#351/#352), and
portable Layout spacing requirements (#358).

## Order

1. Inventory current diagnostics, Context font declarations, package data,
   materializer closure copying, renderer factories, and Layout token
   resolution.  Confirm a legally redistributable font can be used by both
   resvg and ReportLab before selecting it.
2. Publish one cross-layer design that assigns font closure, glyph coverage,
   line breaking, renderer identity, and Layout token ownership without
   reopening Scene policy or accepting host fallback.
3. Publish an atomic implementation plan.  Implement #353 independently,
   then the shared #351/#352 font closure, then #358 and its composition
   evidence.  Each slice is independently testable and publishable.
4. Run focused tests per slice; at the release boundary run full pytest,
   materialize every declared corpus slide, regenerate/inspect evidence,
   conformance/structural checks, and GitHub CI.  Close Issues only after the
   corresponding public evidence and review are published.

## Required design questions

- Define one immutable font asset record that binds metrics and actual font
  bytes, including source identities, and is resolvable from a Context or the
  packaged default.
- Choose whether missing glyphs diagnose or silently substitute; decide the
  bounded CJK breaking rule and its punctuation policy.
- Ensure PNG and PDF receive declared font files without acquiring host font
  directories, and include font identities in their adapter identities.
- Decide the precise Layout-to-Theme requirement contract and its validation,
  migration, diagnostics, and separation from feasibility/overflow policy.
- Check every choice against View → Layout → Scene → renderer ownership, the
  Context closure boundary, public materializer behavior, and target
  capability truthfulness.

## Acceptance evidence

The final design must name source files, schema/context migration, public CLI
and materializer paths, test fixtures, generated examples, diagnostics, and
the release gate for every issue.  No implementation begins until this design
and its whole-architecture review are accepted and published.
