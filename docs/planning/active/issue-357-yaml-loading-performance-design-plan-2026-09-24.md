# Issue #357 — YAML Loading Performance Design Plan

## Trigger

The corrected bundled Material catalog makes the cost of repeated pure-Python
YAML parsing observable in normal public materialization.  Profiling identifies
two independent causes: runtime resources are decoded through `yaml.safe_load`,
and immutable schemas are decoded repeatedly during one process lifetime.

## Objective

Reduce parsing cost without changing YAML safety, decoded values, resource
freshness, validation semantics, generated bytes, or package-boundary
authority.

## Architectural decision

Introduce one dependency-neutral `chrona.yaml_codec` module.  Its public
`safe_load` selects `yaml.CSafeLoader` when libyaml is available and otherwise
uses `yaml.SafeLoader`.  It remains safe-load-only: no unsafe tags, custom
constructors, or serialization policy are introduced.

All production YAML ingress uses this codec.  It is deliberately above neither
Core nor Storage: Core, Storage, Presentation, Operational, and Usecases may
depend on it; it depends only on PyYAML.  Tests and authoring-only tools are
out of the runtime migration unless they establish release evidence.

Package schemas are a distinct authority from runtime resources.  A cached
schema loader may cache only resources returned by `chrona.resources`; Context,
snapshot, revision-store, manifest, extension, and user-authored files remain
decoded for each read.  This prevents stale external state from being mistaken
for an immutable packaged contract.

The contract registry and schema-by-name accessors cache their package-derived
results for a process lifetime.  Cache ownership stays in the module that owns
the validator; no mutable cross-layer schema registry is introduced.

## Design gates

| Gate | Required result |
| --- | --- |
| D357-1 | One safe codec has C-loader fallback and preserves SafeLoader semantics. |
| D357-2 | Every production YAML decode uses the codec; no layer imports a lower-layer loader. |
| D357-3 | Only packaged schemas/registries are cached; mutable resource reads remain uncached. |
| D357-4 | Cache behavior has timing-free tests, including a repeated materialization path. |
| D357-5 | Public corpus bytes, validation diagnostics, wheel resources, full suite, and CI remain stable. |

## Non-goals

- Lazy CLI imports and startup performance are separate work.
- Caching external YAML, catalog closure results, render products, or schema
  validation results is out of scope.
- Changing YAML syntax, schema versions, content identities, or output bytes is
  prohibited.

## Acceptance

The timing-free acceptance evidence proves schema parse/registry construction
is once per process where package schemas are reused, while external reads are
not cached.  Release evidence additionally records a local performance sample:
Controller Z in-process materialization under 0.7 s and the Material-catalog
Draft path under 2 s on the recorded development environment.  Timings inform
the release review but are not CI assertions.
