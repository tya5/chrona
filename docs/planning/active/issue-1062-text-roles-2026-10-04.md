## 1. Published baseline

Read on `4d97eccd` from code, specifications and the mock `docs/research/presentation/halcyon-1-target-design-2026-09-21/board/02-programme-board.png`:

1. **Mock.** The Phase column is muted grey and smaller than the Work package column; the legend labels are muted grey; the legend swatches and every other table cell stay at full ink.
2. **Table cells today.** `cell_typography_role(column)` (`review/v05_content.py`) returns `numeric` for `signedDays` and `signedNumber`, else `text`. That role is carried by each `TableCellContent.typography_role` and read by every Layout consumer: column measurement (`measure_table_columns`), row line block (`table_text_line_block`, in `render_review.py`, `surface_base.py`, `surface_lanes.py`), ellipsis, alignment and the centred baseline (`surface_table.py`). Scene paints a cell by its semantic: `tableCell` is binding scene role `text`; the variance and missing-actual cells are state text with their own roles. So size, spacing and weight already follow the cell's typography role; only the selection of the role per column, and a cell colour other than the `text` fill, are missing.
3. **Header precedent (#991 item 13).** `tableColumnLabel` is a Theme text role; Layout resolves it with a fallback to `text` (`ThemeTokenView.table_header_role`), and Scene paints the headers with it only when the Theme binds a `tableColumnLabel` fill (`v05_builder.py`). Registered in `capabilities.py` with text measurement and text paint.
4. **Legend label today.** Layout measures and places legend labels in the typography role `legend` (`surface_legend.py`, `legend_source_input`); `legend` is already a declarable Theme role with its own size, so the size of a legend label is already a Theme choice. Scene paints them as `legendLabel`, binding scene role `text`, theme role `legend`, purpose `legend-label`, contrast class ground text. `legend` is registered in `capabilities.py` as a measurement-only role, so `legend.fill` is rejected at Theme resolution as unsupported (the issue's "`legend.fill` is rejected").
5. **Admission of an unknown role name.** `theme_role_property_consumer` admits, for a role name with no registered contract, text measurement and axis measurement properties and the rect paint properties (the latter for the Detail Profile fixed-square legend fallback). An author-named role such as `table-cell-secondary` with `fontSize` and `fill` is therefore admitted today under consumer descriptions that name only axis tiers and legend squares.
6. **Contrast gate gap (found while reading, a defect of the precedent).** `contrast_binding_for(scene_role, purpose)` classifies a Text primitive by its role, else by purpose **only when the role is `text` or the binding's own scene role**. A header painted in `tableColumnLabel` (visual role `tableColumnLabel`, purpose `table-column-label`) therefore falls through: it is **not contrast-checked** (confirmed: `contrast_binding_for("tableColumnLabel", "table-column-label")` is `None`). A muted header ink below 4.5 would not be reported. The same would hold for any new text role these knobs introduce, which breaks the acceptance row "a label under the role that fails text contrast is reported as it is today". This slice closes it for the new roles and for the header.
7. **Schema.** `view-v0.28.schema.yaml` `tableColumns[]` is closed (`additionalProperties: false`); the axis tier `typographyRole` (a non-empty string naming a Theme role) is the existing precedent for a View naming a Theme text role.

Unverified (checked per slice): corpus bytes after the slice; Typst and TikZ output for the new colour and size; whether the existing Controller Z `table-header` slide still passes the contrast gate once its headers are classified (item 6).

## 5. Design (decisions; reverse = delete the optional property or role admission and its consumer branch)

- **D1 View knob (table).** `tableColumns[].textRole`: optional non-empty string naming a Theme text role (the form of the axis `typographyRole`). Absent: today's role (`numeric` for `signedDays` and `signedNumber`, else `text`). Present: the cells of that column are measured and placed in that role (size, weight, letter spacing, transform, line height), through the one existing channel `TableCellContent.typography_role`; nothing new is added to Layout geometry code. The header keeps its own role (`tableColumnLabel` or `text`): a column's role is for its cells. An explicit `text` or `numeric` is equivalent to the default.
- **D2 colour (table).** The role colours the cell as a text paint: when the named role is neither `text` nor `numeric` and the Theme binds `<role>.fill`, a plain `tableCell` primitive carries visual role `<role>` and resolves that fill (the mechanism of the header). Without a `fill` binding it keeps the `text` ink and takes only the typography. State-text cells (variance, missing actual) keep their own state role and ink; the column role gives them only typography. This keeps the state colour gate (`required` or `deemphasized`) authoritative.
- **D3 Theme knob (legend).** The existing Theme text role `legend` may bind `fill` (and `opacity`, as `text` does). When the Theme binds `legend.fill`, legend labels carry visual role `legend` and resolve it; otherwise they stay `text`. No new role name: `legend` already owns the label size, and "its own colour and size" is `legend.fill` plus the existing `legend.fontSize`. Swatches are separate (`legend-swatch`, entry roles) and unchanged.
- **D4 admission.** Registry and admission, in one place (`capabilities.py`): `legend` moves from the measurement-only group to a text role with fill and opacity (consumer "Layout legend measurement and Scene Text"); the consumer description of an unknown role's measurement and fill is extended to name "View-named table column text" so that role-admission reports tell the truth. A role named by a View still needs the Theme to declare it (D6). Scene paint roles are otherwise a closed vocabulary (`test_every_public_theme_declaration_and_scene_paint_role_has_a_consumer` requires a registered contract for every `visualRole` in the committed Scenes); a View-named role is the one admitted exception, bounded to a Text primitive of purpose `table-cell` whose role the capability table admits for `fill`, and the test states that exception instead of silently skipping unknown roles. A View-named role declares text measurement properties and `fill`; the `iconScale` and `iconGap` of `text` are not admitted for an open name, and a table cell needs neither. No new role is registered by name, because a View-named role is author-chosen.
- **D5 contrast by purpose.** `contrast_binding_for` gains one rule: a Text primitive whose visual role is **not any registered scene role** (so it is a Theme text paint role: `tableColumnLabel`, `legend`, or a View-named role) is classified by its purpose like free ink on `text`. Result: header, table cell and legend label in a named role are ground text, blocking at the fixed `required` floor of 4.5 against their ground, exactly as under `text`. A role of its own never borrows another purpose's class (unchanged: `axis-label2` with `member-label` stays unclassified). This also closes item 6 of the baseline for the headers. Alternatives rejected: a closed list of table text roles (a View cannot then name its own role); checking contrast at Theme resolution (the ground is a Scene fact, #884/#980).
- **D6 unknown role.** A `textRole` that names a role the resolved Theme does not declare is `E_THEME_ROLE_REQUIRED` raised before any measurement, with the pointer of the View property, `/body/tableColumns/<index>/textRole`, and a detail naming the missing `/body/roles/<name>`. A role without text measurement properties fails at its missing property by the existing Theme token path. Rationale: the View input is what the author must change; the existing Theme-side pointer stays in the detail. Reverse: change the pointer argument.
- **D7 adapters.** SVG, PNG and PDF (from the SVG), Typst and TikZ serialise completed Scene Text: `text_layout` (size, spacing, family, weight) and resolved `paint`. No adapter reads a visual role name or a Theme role, so none changes; the evidence checks size and colour in the SVG, the Typst source and the TikZ source of the slide. Role names are not emitted into any format that a third party parses beyond the existing Scene `visualRole` string.
- **D8 owner-level choices.** (a) Open role names (chosen) against a closed set of table roles: open lets a Theme declare any number of treatments and matches `typographyRole`; cost: contrast by D5 rather than by a registered role. (b) Reuse `legend` (chosen) against a new `legendLabel` role: smaller surface, the size is already there, absent declaration is byte identical because `legend.fill` is rejected today so no Theme binds it. (c) Per-column role (chosen) against a table-wide secondary role: the mock colours one column. (d) State text keeps its ink (chosen): a column role must not defeat variance colours.

**Schema (Spec 56 section 3.2; S0 gate).** `view-v0.28`: one optional property `textRole` under `tableColumns.items.properties`; additive, no version bump, no expected-delta entry (an optional property, as `missingBy` was in #1020). `python -m tools.schema_equivalence --base-rev origin/main` runs in the code PR and its result is recorded there. On the base of the code PR the gate passes without pruning (the entries of other merges are still inside their one-merge window and are not mine to retire). No Theme schema change: `roles` is open and `colorBindings` targets are validated by the capability table. Living specifications updated in the code PR: Specification 24 (table columns), Specification 07 (text roles, beside the header role), Specification 49 (the `legendLabel` row). Migration impact: none; omission keeps output.

## 6. Architecture review

- **Layers.** View selects a role name (intent only); Theme declares size and colour; Layout measures and places in the selected role (existing channel); Scene picks the paint role and carries completed Text; adapters serialise it. No paint decision in Layout, no geometry in Scene.
- **Defaults.** Absent `textRole` and absent `legend.fill` change no byte; `regenerate_public_examples --check` shows the corpus unchanged except where the contrast reclassification changes a result (D5 is a gate, not paint; a header that failed would be a new error, so the corpus is checked for this before the PR, see risks).
- **Adjacent designs.** Same mechanism as `tableColumnLabel` (#991), generalised from one fixed name to a View-named one; lane tables take no `tableColumns` and are unaffected; the legend slot sizing (#497) already measures in `legend`, so a size change reflows the slot with no new code.
- **Failure behaviour.** Unknown role: error at the View pointer (D6). Failing contrast: the existing blocking `E_SCENE_STATE_TEXT_CONTRAST` with the primitive id, ratio and role (`render_review` already names the role).
- **Residual risks.** D5 newly gates headers in `tableColumnLabel`; if the committed Controller Z `table-header` slide fails 4.5 it is reported and handled as a finding (fix that evidence Theme in the same PR and say so), not hidden. A View-named role that collides with a registered scene role name (for example `planned`) is classified by that role's own class by the existing rule and would fail at its missing text properties first.
