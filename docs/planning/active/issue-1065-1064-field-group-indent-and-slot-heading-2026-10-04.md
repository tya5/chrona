## 1. Published baseline

Read on `86f85498` (re-checked on `b866e6b8`) from code, specifications, both issues (no comments before this work) and the mock.

**Mock.** Group header bands ("Spacecraft bus", ...) carry their label about half a step in from the band edge; each child row label sits one further step to the right of its header label (header label at x 55, child labels at x 65 in the 2000 px view, band edge at 45). Above the notes rail, the caption "NOTES" (small, muted, letter-spaced capitals) shares the vertical band of the axis header; the first note starts lower, at its own row.

**#1065 today.**

1. The View already names the indented column: `hierarchyColumn`. `_validate_view_table_intent` (`contracts/resources.py`) rejects it with `E_VIEW_HIERARCHY_COLUMN_UNEXPECTED` unless the View uses hierarchy grouping, a row `depth` or a `parentRow`; it requires it (`E_VIEW_HIERARCHY_COLUMN_REQUIRED`) when the View does nest. Verified on `86f85498` with a synthetic Project grouped by field with `presentation: header`: without `hierarchyColumn` the cells start at the table start (x 24.0) and the headers at x 24.0; with it, the render fails with that error.
2. The offset of a cell in the hierarchy column is one Layout rule, `table_cell_indent(grouped, depth, inset, indent)` (`layout/presentation.py`): `inset` (the body size) when the row belongs to a group, plus `table.indent.inlineSize * depth`. The Theme metric is already a required one (`sources.REQUIRED_METRICS`), so a Theme without it fails before Layout (`E_LAYOUT_METRIC_REQUIRED`); the helper keeps `E_PRESENTATION_MEASUREMENTS_REQUIRED` as its own backstop. The same helper feeds measurement (`sources._table_content_inline`, `measure_table_columns`: a cell's extent includes its indent, so a content-sized table slot is as wide as its widest indented cell, Specification 24 section 2.1) and placement (`surface_table.compose_table`: the cell is placed at the column start plus the indent and its text is fitted to column width minus indent minus inset, with the `table.overflow` ladder `ellipsize-with-source`).
3. Where a row's depth comes from: hierarchy grouping and explicit `rows` entries (`TableRowLevel(keys, grouped, depth)` built in `review/v05_content.py`). Field-grouped automatic rows are `TableRowLevel(keys, grouped)` with depth 0.
4. The header label starts at the header's start edge, which is the table slot's start (`surface_base`, group header rect), pushed right by a start-position group tab plus its gap (`surface_groups.compose_group_presentation`, #882). With a vertical `groupHeader` writing mode there is no header row at all: a tag column is carved from the table start (#585, `group_tags.py`).
5. Tints and bands (#583) are geometry of the group and header rows; the table text indent changes only where the cell text starts.

**#1064 today.**

1. A Layout Profile slot (`layout-profile-v0.10` `slot`) has `id`, `source`, sizes, `place`, `priority`, `overflow`, `cell`, and optional per-slot declarations for a legend (`direction`, `gap`, `itemMinInlineSize`, #427) and a region `frame` (#889). It has no caption. `override` can replace such properties in a derived profile (`extends` plus `overrides`), which is how a Context already changes a Layout Profile's declared copy without editing the base.
2. The rail is the `annotations` slot (and the `notes` slot for project notes). The engine records one `LayoutDecision` per arranged slot; an absent optional slot (no content) has none and its siblings close over it (`engine._active_children`). Annotation boxes, their leaders and fallback use the slot's bounds as the rail viewport (`surface_annotations.place_annotations`); notes and legend place their lines from the slot's bounds (`surface_content.place_notes`, `surface_legend.place_legend`). A slot is also a Scene slot: a text outside its slot gets `W_SCENE_TEXT_SLOT_ESCAPE`.
3. The axis header is the `timeline-axis` slot, a sibling above the timeline in the target-B profile; the rail slot starts at the same block position (the `review` row).
4. Text roles: the title uses typography role `heading` and the subtitle `subtitle` through the closed semantic registry (`titleText`, `subtitleText`, #991); a Theme text role carries font family, weight, size, line height, letter spacing, text transform and numeric spacing; paint comes from `colorBindings` of the Scene role. Ground text (#884, #980) is classified by purpose in `semantic_registry.contrast_binding_for`, and the contrast gate judges it against the ground under it. `tableColumnLabel` (#991) is the precedent for an optional text role: used when the Theme declares it, `text` otherwise.
5. Text fitting: `text.ellipsize_text` keeps the source and the cut is reported as `W_LAYOUT_TEXT_ELLIPSIZED` (the group header beside a tab, #882, is the precedent).
6. Adapters: a heading is a `Text` primitive. SVG and PNG draw it; Typst and TikZ draw Text with the same letter-spacing and text-transform handling as any other label (the existing text ladder), so no adapter change is planned.

Inferred (confirmed by the slice that touches it): that no Scene schema change is needed (a heading is an ordinary Text with a registered purpose); that the presentation-coverage tool accepts the new purpose when it is registered with the other text purposes.

Unverified: the rendered look and the contrast gate on the evidence slides (read as images in each slice); the Windows run (no Windows host here; the three-OS CI is the check).

## 4. Design plan

Use cases (synthetic Projects; target B is a comparison, never the oracle):

- **U1** a table-timeline grouped by a field with header bands and a hierarchy column: child labels one declared step inside the header label. **U2** the same with a group tab at the start of the header: the child still sits one step inside the header label, not inside the tab. **U3** a narrow flexible column: the indented label is cut with its source kept. **U4** hierarchy grouping and explicit row depth: unchanged. **U5** field grouping with `presentation: band`, or no grouping, and a declared `hierarchyColumn`: the error as specified.
- **U6** a note rail headed "NOTES" in the axis header band, notes starting below it. **U7** the heading at the top of the slot (no axis beside it). **U8** a rail with no notes: absent slot, no heading. **U9** a slot too small for its heading. **U10** a derived Layout Profile that overrides only the heading text. **U11** a heading wider than its slot. **U12** a legend slot with a heading.
- Every knob is optional; absent means today's output byte for byte. Spec 56 section 3.2 applies to the one schema change (the slot `heading`): an additive optional property goes in place with no version bump, schema `default` annotations implement nothing, and the consumer supplies and tests the omission behaviour.

Responsibility boundaries: View names the indented column (existing property); Theme declares the step (existing metric `table.indent.inlineSize`) and the heading's typography and paint (a text role); Layout Profile declares the heading's text and placement; Layout owns the indent arithmetic, the heading band, the reserved block, fitting and omission; Scene carries completed Text primitives; adapters serialize them.

Order of design slices: this record, then I1065, I1064, then the acceptance reviews.

## 5. Design (decisions; reverse = delete the optional value or property and its consumer branch)

### #1065, indent under field-grouping headers

- **D1 (owner-level) where the knob lives.** Options: (A) allow `hierarchyColumn` when the View groups by a non-hierarchy dimension with `presentation: header`, and reuse the Theme step `table.indent.inlineSize`; (B) a separate View knob (`grouping.childIndent`) in px or em; (C) always indent the children of every header group by a Theme metric, no declaration. Choice: **A**. Reason: a group header is a parent row in reading order whatever produced the grouping; the View already names the column that carries nesting and the Theme already owns the step, so one vocabulary covers both, the measurement already includes the indent (a content-sized table widens exactly as for hierarchy), and no schema changes. B adds a second indent concept next to `table.indent` and a second place where a unit is chosen (em or px); C changes every existing header-grouped slide and violates the default rule. The unit stays the Theme's: `table.indent.inlineSize` is a px number the Theme author may derive from a font size, so an em step is a Theme value, not a new unit. Reverse: restore the single `E_VIEW_HIERARCHY_COLUMN_UNEXPECTED` condition and remove the `under_header` row-level flag.
- **D2 the rule.** When `hierarchyColumn` is declared, the View groups by field (any non-hierarchy dimension) with `presentation: header`, and no other nesting is declared (no row `depth` or `parentRow`), every grouped row is depth 1 below its header (depth 0). Its cell in the hierarchy column starts at the column start plus `lead + table.indent.inlineSize`, where `lead` is the distance of the header's label from the table start: the group tab and its gap when the Theme draws a start-position tab (#882), otherwise 0. So the child label starts exactly `indent` after its header's label start (A1), also beside a tab. The grouped-row `inset` of the hierarchy rule is not added: that term belongs to hierarchy grouping, whose output must not change. The header label is not touched (A2).
- **D3 flat case (A4).** Without header groups the declaration stays an error, as today: field grouping with `presentation: band` (or none), or no grouping, plus `hierarchyColumn` is `E_VIEW_HIERARCHY_COLUMN_UNEXPECTED`, with the message now naming "field grouping with presentation header". Options: error (chosen) or accepted as a no-op with a warning. Reason: a declared knob that cannot act hides a mistake and it keeps the existing contract; a View that wants an indent when headers are on and none when they are off declares both. Reverse: replace the raise with a warning code.
- **D4 interactions.** Hierarchy grouping, a row `depth` or a `parentRow` keep their rule (`inset` plus step times depth) and win over D2 when present, so every existing fixture stays byte identical (A3). A Theme whose `groupHeader` role is vertical (#585) draws no header row; there the View is still valid (a View cannot know the Theme) and the indent is not applied (rows are not below a header; the tag column already marks them). Tints and bands (#583) and the tab are geometry of the group and header rows and do not move; only cell text starts later. The step needs no new requirement: `table.indent.inlineSize` is already one of the required Theme metrics (`REQUIRED_METRICS`), so a Theme without it already fails with the existing required-metric error.
- **D5 text fit.** Unchanged ladder: the cell's available inline size is the column width minus the indent minus the cell inset; a cut label ends with an ellipsis, keeps its source and is reported (`overflow: ellipsized`, `W_LAYOUT_TEXT_ELLIPSIZED`). A content-sized or `minmax(content, ...)` table is measured with the indent included, so the widest indented label never cuts it.
- **Schema.** None: `hierarchyColumn` and the metric exist; the change is the View contract check and the Layout offset. No expected-delta entry; the schema equivalence gate is run on the PR and its result recorded.
- **Specifications.** 24 section 2.1 (the hierarchy column rule) and 45 (group headers indent member labels), each with the migration impact (none: the previously rejected combination becomes valid; accepted documents give byte-identical output).

### #1064, slot heading

- **D6 (owner-level) declaration and where.** An optional `heading` on a Layout Profile `slot` and on `override` (replacing the whole declaration), shape `{text, align, block}`:
  - `text`: literal presentation copy, 1 to 80 characters, no control character. Copy is presentation, not Project fact. The Theme's `textTransform` (uppercase) is applied by the text role, so the profile holds "Notes" and the Theme makes it "NOTES".
  - `align`: `start | center | end` within the slot's inline extent, default `start`.
  - `block`: `top | header-row`, default `top`.
  Options for the declaration site: (A) on the slot (chosen: node-local, `extends`/`overrides` merge it, like `frame`); (B) a top-level list naming slots (duplicates ids, reference validation); (C) a new `caption` slot kind (a second node that must be sized and ordered). Reverse: remove the property.
- **D7 override of the text.** The issue says a Context or View may override the copy. A Context pins a Layout Profile and may pin a derived profile (`extends` plus `overrides: {<slot id>: {heading: {...}}}`); that is the Context-level override and needs no new schema. A View-level override would add a second site that must be validated against the profile's slot ids and the Layout source set; it is deferred to a successor if wanted (no row of the issue needs it). Recorded on the issue.
- **D8 role.** The heading is typography role `slot-heading` (Theme text role: colour from the `slot-heading.fill` colour binding, size, weight, letter spacing, text transform). It is a registered semantic (`slotHeading`, purpose `slot-heading`) classified **ground text**: the existing contrast gate judges it against the ground under it, so a muted heading that is too faint fails like any other ground text (B4). A Theme that does not declare the role renders the heading in the `text` role (the `tableColumnLabel` precedent: copy is never silently dropped). `role` is not a per-heading choice in this design (the issue's example names the one value `slot-heading`); a second role is additive later. Options: an error when the Theme lacks the role (rejected: a Theme written before this feature would fail on a profile that gained a heading); `groupHeader` reuse (rejected: it is bound to group semantics and the vertical tag).
- **D9 placement and reservation (Layout).** For a slot with a declared heading and positive area, Layout completes one Text placement `slot-heading:<node id>` with `slot_id` the slot. The heading's line box is `font size * line height` of its role. Let `gap = 0.5 * font size`.
  - `block: top`: the line box starts at the slot's block start; the slot's content starts at `top + line + gap`.
  - `block: header-row`: when a `timeline-axis` slot's block extent intersects the slot's (it is beside the axis band), the line box is centred in that band (clamped to the slot) and the content starts at the larger of the band's bottom and `top + line + gap`. When no axis band is beside the slot, `header-row` behaves as `top` and Layout records `I_LAYOUT_SLOT_HEADING_NO_HEADER_ROW:<node id>`. Centring in the band is a decision: the mock puts NOTES at the baseline of the upper axis tier, while the table header labels sit on the lower tier; the band is the one rule that does not depend on how many tiers the View draws. A tier-aligned variant is additive later.
  - The reserved block is `content start - slot top`. The content of the slot is placed in the remainder: a **content viewport** equal to the slot bounds with the reserve removed from the top. The Scene slot keeps its full bounds, so the heading is inside its slot (B1) and no content can lie above the content start (B3). Consumers: annotations (rail), notes, legend and summary. Group-details, milestones, observations, title, table, timeline, timeline-axis and network reject a heading (`E_LAYOUT_SLOT_HEADING_SOURCE` at `/root/.../heading`): their blocks are measured and aligned by other rules (a table heading would break the row alignment with the timeline), and each is a successor if wanted.
  - Fit: a heading wider than the slot is cut with its source kept and reported (`W_LAYOUT_TEXT_ELLIPSIZED`); `align` positions the cut text.
  - Omission: an absent optional slot has no decision and so no heading (nothing is drawn, nothing moves; a rail with no notes shows no caption); a slot of no area, or a slot too short for `line + gap`, draws no heading and reserves nothing (`I_LAYOUT_SLOT_HEADING_OMITTED:<node id>:too-small`). A heading never moves other slots (it is taken from its own slot), so the surface size and every other bound are unchanged by it.
  - The profile's content-sized extent is unchanged: a rail beside the timeline does not set the surface height. A content-sized slot (`blockSize: content`) is measured from its content only, so its heading is taken from its allocation and the slot completes larger by the existing growth rule where its content needs more (legend, notes). Recorded as a limit; a measured reservation is a successor if a use needs it.
- **D10 diagnostics and identity.** `placement_id` is `slot-heading:<node id>` (stable, from the profile). The manifest bytes gain a `heading` entry per declaring node only when declared, so absent declarations leave the canonical manifest byte identical (B5).
- **Schema (Spec 56 section 3.2, S0 gate).** `layout-profile-v0.10`: optional `heading` in `slot.properties` and in `override.properties`, a shared `$defs/slotHeading` (`additionalProperties: false`, required `text`; `align` and `block` enums). Additive: accepted documents only grow, with one expected-delta entry per new pointer and a covering test; `python -m tools.schema_equivalence --base-rev origin/main` runs on the PR and the result is recorded; stale entries older than one schema merge are retired with `--prune-stale`. Theme and View schemas: no change (a role name is open in `roles`; the registry in `capabilities.py` declares which properties the role admits). `layout/profile.py` checks the heading's shape first and names the exact pointer (the `frame` precedent), then the source rule.
- **Specifications.** 33 (Layout Profile: slot heading), 07 (the `slot-heading` text role), 49 (semantic `slotHeading`), each with the migration impact (none: omitted keeps output).
- **Adapters.** SVG and PNG draw the Text primitive; Typst and TikZ draw it as any other Text with its letter spacing and text transform (the existing text ladder); no adapter change. Verified on the evidence slide through the four adapters in the slice.

## 6. Architecture review

- **Layers.** View names a column (existing); Theme declares the step and the heading role (paint and typography only); Layout Profile declares copy and placement intent; Layout owns the offsets, the heading band, the reserved block, the cut and the omissions; Scene carries completed Text; adapters serialize. No geometry in Scene, no paint in Layout, no corpus name in core.
- **Defaults.** Both slices are byte identical when the declaration is absent: #1065 changes only a combination that is rejected today; #1064 changes nothing without a `heading` (the manifest bytes, the slot list and every primitive are as before). `tools/regenerate_public_examples.py --check` shows no corpus diff; no corpus datum is edited.
- **Adjacent designs.** The indent reuses the #437/#480 hierarchy rule and its measurement, so a content-sized table cannot cut an indented label; the tab lead reuses #882's resolved tab; hierarchy grouping and explicit depth are untouched. The heading reuses the `frame` (#889) pattern for a node-local profile declaration and the ground-text classification (#884, #980); text fitting reuses `ellipsize_text` with its warning. The content viewport keeps every consumer's arithmetic (annotation routing, note lines, legend flow) as is by passing it the reduced slot, and restores the full bounds on the completed slot.
- **Failure behaviour.** Bad indent combination: the View contract error with its pointer. Missing metric: the existing required-metric error. Bad heading shape or source: `E_LAYOUT_SCHEMA` / `E_LAYOUT_SLOT_HEADING_SOURCE` at the exact pointer. No room, no axis band, too long: omission or cut plus a recorded diagnostic, never a failure.
- **Residual risks.** The tab lead in the table measurement (`sources.py` and `surface_table.py` must use one helper); a content-sized rail slot (heading taken from its allocation); the rail's annotation search regions now start lower (fewer candidate positions at the rail top, observed on the evidence slide); contrast of a muted heading on a tinted ground (gated, evidence slide).
- **Intended incompatibilities.** None for accepted documents.
