# Issue #1031: baseline ghosts are not relation endpoints (work record)

Living record for [#1031](https://github.com/tya5/chrona/issues/1031), a plain bug fix confined to one owner (Layout relation routing, plus one Scene check). Steps 1 to 4 of the sequence are combined here; the literal acceptance review follows the merge.

## 1. Baseline (read on `094c4df9`, rebased on `14892b4e`)

- `layout/surface_routes.py: compose_surface_routes` loops every (source instance x target instance) of a relation. `instance_anchors` holds one entry per row member, and since #1000 a member can be a comparison mark (`source_kind` `snapshot` for `comparison.baselineMarks: ghost`, `scenario` for a scenario baseline). One relation therefore became up to four paths (`relation:<id>:<src>:<dst>` with `snapshot:`/`scenario:` ids).
- Reproduced on synthetic fixtures in every row mode (automatic, field-grouped, lanes, explicit): 4 paths for 1 relation.
- Corpus sweep of all 53 committed Scenes (relation `Path` primitives per `sourceRef`): four slides duplicate, not only target B. `halcyon-1/target-b` (24 relations x 4 = 96 paths, 72 with a `snapshot` id; the 97th path is the legend swatch), `halcyon-1/tvac-slip` and `halcyon-1/flight-readiness` (scenario ghosts, same cause) and `controller-z/baseline-ghosts` (7 relations x 4). Every other slide already had one path per relation.
- Unverified before: whether an explicit row that lists an object only as a snapshot item still needs its relation.

## 2. Literal acceptance (copied from #1031)

1. With baseline ghosts shown (any row mode), relations connect only primary (current plan) marks; ghosts are never endpoints. A synthetic test with ghosts plus two related items asserts exactly one relation path per relation.
2. The committed `21-target-b` Scene has 24 relation paths, one per relation, no relation id containing `snapshot`.
3. Every other committed slide keeps one path per relation. A corpus check fails if any relation produces more than one path; duplication is never silent.

## 3. Design and architecture review

- **Rule (Layout, project independent).** Relation endpoints are the current-plan instances of an object. Row members of kind `snapshot` or `scenario` are comparison marks and are skipped as endpoints. Ghosts still draw, still carry their own marks and ports for egress clearance (`comparison_clusters` is unchanged).
- **Fallback (decision, reverse = delete the `or entries`).** An object with no plan instance at all (an explicit row holding only a snapshot item) keeps its comparison instances, so a deliberate snapshot-only row does not silently lose its relation. Not an endpoint of a ghost when any plan instance exists.
- **Not changed.** Explicit rows that list one object as both `primary` and `actual` items are still two instances; no committed slide does that, and the corpus sweep shows no duplicate, so it is left as declared by the author.
- **Check (Scene, not Layout).** New error `E_SCENE_RELATION_PATH_DUPLICATE` in `scene/perceptibility.py`: two `relation:` Path primitives with one `sourceRef` in a surface. It runs in the existing `scene-perceptibility` conformance check over every manifest Scene and in draft feedback, so a duplication fails conformance instead of being drawn silently. The legend swatch shares the source kind and is excluded by the `relation:` id prefix.
- **Layers.** Layout owns the routes; Scene only observes completed facts; no schema, View, Theme or Project change; no corpus datum edited.
- **Migration.** Four committed slides change (regenerated by derived-sync, not edited): fewer paths, no overlapping arrowheads.
