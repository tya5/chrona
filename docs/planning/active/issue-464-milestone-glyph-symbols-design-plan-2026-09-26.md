# Design Plan — Milestone Glyph Symbols (#464)

**Public base:** `908f9d69` on `main`. **Source of truth:** [Issue #464](https://github.com/tya5/chrona/issues/464), Specifications 07 (§5.2 tokens), 08 (§5.2/5.3 primitives), 64 (portable icon catalogs, for reusable normalization). **Related:** #453 (target B gap map), #429 (preset catalogue), #462 and PR #461 (the six design targets), #446/#459 (perceptibility and contrast gates this design must keep meaningful).

## Published baseline, inference, and unverified facts

Reproduced on `908f9d69` with HALCYON-1 `02-programme-board`: setting `wallboard.yaml`'s `milestone-symbol` value to `{shape: pin}` and running `python -m tools.materialize_example examples/halcyon-1/manifest.yaml --slide programme-board --output /tmp/repro-464` fails closure with `chrona.presentation.model.closure.ClosureError: E_THEME_SCHEMA`, raised from `_collect_presentation_resources` (`src/chrona/presentation/model/closure.py:537`), because `schemas/theme-v0.11.schema.yaml`'s `symbol` token value schema closes `shape` to `enum: [diamond, circle, square, chevron]` (line 73). The change was reverted after the repro. A second, independent guard exists downstream: `symbol_geometry` in `src/chrona/presentation/scene/mark_geometry.py` raises `E_THEME_TOKEN_TYPE` for any shape outside the same four names — reachable only if a caller bypasses schema validation, so it stays as defense in depth, not the only fix point.

**What exists today, verified by reading the code (not only the issue body):**

1. `ThemeTokenView.symbol(role="milestoneSymbol")` (`model/theme_tokens.py:112`) always resolves the *one* role name `milestoneSymbol`, regardless of planned/actual/baseline. `scene/v05_builder.py` calls `value.theme_tokens.symbol()` with no role argument at every one of its five call sites (planned, actual open-span, actual point, and the two folded-group variants). There is **no** `milestoneSymbolActual` or `milestoneSymbolBaseline` role today, although the issue's first acceptance bullet names them as if they should exist. Baseline/planned/actual are today distinguished only by each purpose's own resolved `ScenePaint` (colour, and optionally `pattern: outline` + `dash` for a stroke-only ghost), never by shape.
2. `SymbolGeometry` (`scene/model.py:118`) carries exactly one field, `outline: tuple[PathCommand, ...]`, and `PathCommand.kind` is one of `move`/`line`/`quadratic` only (`layout/surface_quality.py`); the SVG adapter's `commands_data()` (`renderers/v05_svg.py`) raises `E_PRESENTATION_PRIMITIVE_INVALID` on anything else — **no cubic Bézier**. A `Symbol` primitive carries exactly one `paint: ScenePaint`, so exactly one fill-or-stroke pair paints the whole shape.
3. The **icon** capability (spec 64) already solves an adjacent but different problem well: `NormalizedVectorIcon.paths: tuple[NormalizedIconPath, ...]` (`icons/normalizer.py`) and its Scene counterpart `SceneIconPath` (`scene/model.py:79`) already carry *several* paths, **each with its own `fill`/`stroke`/`stroke_width`/`opacity`**, parsed from arbitrary SVG `d` data including cubic curves (`icons/normalizer.py::_path`, tokens `M/L/H/V/Q/C/Z`). This is materially the multi-part painted-glyph primitive #464 needs, but it is wired to `PrimitiveKind.ICON` with `purpose: icon-mark` (an overlay drawn *inside* an existing host mark's bounds, per `surface_composer.py::resolve_mark_visual_requests`), not to the milestone's own semantic purpose (`planned`/`actual`/`snapshot`). Reusing `Icon` verbatim for the gate shape itself would blur "the glyph replaces the shape" with "the icon decorates the shape," and would leave the milestone's own primitive kind as `Rect`/`Symbol` with nothing drawn — contradicting "the Scene still says milestone, planned."
4. Relation ports already terminate at a mark's **bounding-box** edge, never at a shape's visual silhouette: `layout/ports.py::connector_boundary_ports` and `connector_egress_candidates` read `mark.bounds` only. Today's diamond/circle/square/chevron shapes all touch their own bounding box on all four sides by construction, so this is invisible. A glyph whose artwork does not fill its declared aspect ratio on both axes (e.g. a tall pin in a wide box) would produce a port that lands on empty canvas beside the glyph, not on its edge — a real gap against literal acceptance bullet 5, not merely a documentation nit.
5. Contrast checking (`scene/contrast_policy.py::_ground_under`) treats only `kind == "Rect"` primitives as a possible "ground" a later primitive is painted over; a `Symbol` is never considered ground. Today this is harmless (one paint layer per symbol). A multi-part glyph painted as several stacked `Symbol` primitives (see Contract 1 below) would make every part's contrast checked against the **canvas**, not against the part beneath it — silently wrong for exactly the case the issue asks to keep meaningful ("the perceptibility and contrast gates measure the glyph's effective paint against the surface beneath it").
6. Perceptibility's `_occlusion_findings` (`scene/perceptibility.py`) only compares `Text` against `Rect`; it never flags `Symbol`-vs-`Symbol` overlap, so several same-bounds `Symbol` primitives for one glyph do not trip spurious occlusion errors. `ScenePrimitive.__post_init__` requires `symbol is None` unless `kind == "Symbol"`, and does not currently forbid two primitives with the same `purpose`/`sourceRef` — that pattern is already legal (a span already emits several primitives per object).
7. Theme's `pattern` role property, resolved through `_paint_family`/`resolve_scene_paint` in `scene/v05_builder.py`, already turns **any** primitive kind's paint into stroke-only + dash when the role declares `pattern: {kind: outline}` — this is not restricted to `Rect`. (The *scene-level* `ScenePrimitive.pattern: PatternGeometry` field, which is Rect-hatch-tile geometry, is a different thing and stays Rect-only; `pattern_geometry({kind: outline})` already returns `None`, so it never touches Symbol's invariant.) This means the "existing role treatments distinguish variants" direction from the issue is not aspirational — the paint-family machinery already generalizes; only the *shape* side needs multi-part support.
8. All six approved targets were read from `docs/research/presentation/{tenthframe,yuya,titlecard,sunday,rpg,flatpack}-target-2026-09-26/README.md`. Five (Tenth Frame, Yuya, Title Card, Sunday Strip, Pixel Quest) fit "one glyph, painted differently per variant, distinguished by fill/outline/dash." Pixel Quest is sharper: its baseline is a **different sprite** (a ghost), not an outline of the same sprite, so a Theme must be able to bind an entirely different glyph asset per variant, not just a treatment. Flat Pack adds gate-glyph selection **by as-of state** (ticked vs. open); this is explicitly out of scope here — see "Not in scope."

## Literal issue acceptance ledger (copied verbatim)

1. A Theme can bind `milestoneSymbol` (and its actual and baseline counterparts) to a glyph asset instead of a built-in shape, and every milestone renders with it.
2. A glyph with at least two painted parts renders both, with paints from the Theme or from the asset, and the choice is documented.
3. Planned, actual and baseline variants of one glyph can be distinguished without colour alone.
4. One committed slide renders HALCYON-1 `02-programme-board` with a non-built-in gate glyph, and its evidence is reproducible.
5. Dependency arrows still end at the glyph's edge, and the perceptibility gate passes on that slide.

## Not in scope (name, do not fold in)

- **State-dependent glyphs** (Flat Pack: ticked/open by as-of) — a real, related requirement the issue's own comments raise, but not one of the five acceptance bullets above. Filed against #464 as a comment only; left for a follow-up issue once this shape/paint contract exists, because it needs a new selector axis (as-of vs. gate date), not more glyph geometry.
- **Icon-catalog-backed glyphs** ("It can be a vector path or a catalogue icon" in the issue body). The design below accepts an inline vector path per Theme value, matching all six targets' hand-authored art; wiring spec 64's catalogue lookup as an alternative *source* for the same `parts` shape is additive and left for a follow-up once the shape/paint contract is proven, per the design-minimal rule.
- **#466/#467** (annotation placement, lane rows) — untouched; this design does not change row/lane geometry, only the point-mark's fill.
- Clipping a *host* to a multi-part glyph's silhouette (`clipSourceId` pointing at a Symbol with `parts`) is flagged as a known gap in the design, not solved, because no committed slide exercises it.

## Use cases and decisions to close

1. **A Theme author replaces a gate's shape.** Decide: does a glyph replace the *value* bound to the existing `symbol` token type (extend the enum), or does it need a new token type? Direction: extend `symbol`'s value schema with `shape: glyph` plus `viewBox`/`parts`, because the role property (`roles.<role>.symbol`) and the resolution path (`ThemeTokenView.symbol`) do not need to change shape, only the value's internal shape.
2. **A Theme author paints a glyph part.** Decide the per-part paint source: role-derived (`fill`/`stroke` from the *same* semantic role that already colours planned/actual/baseline) vs. a literal colour baked into the asset (`color: "#RRGGBB"`), and what happens when a role in stroke-only/outline mode meets a part that declares a literal fill colour. Direction below: outline-mode always wins and ignores literal part colours, so baseline stays colour-independent by construction.
3. **Three variants, one glyph or three.** Decide whether `milestoneSymbol`/`milestoneSymbolActual`/`milestoneSymbolBaseline` are three independently bindable roles (each defaulting to `milestoneSymbol` when unset) or one role read three times with a hard-coded treatment. Direction: three independently bindable roles, because Pixel Quest's ghost baseline cannot be expressed as a treatment of the same asset.
4. **Multi-part rendering unit.** Decide whether one glyph becomes one `ScenePrimitive` with a new nested paint list, or several sibling `Symbol` primitives (one per part) sharing bounds/purpose/role. Direction: several sibling primitives, because it reuses the existing per-primitive `paint` field, the existing `_complete_primitive_paint`/`resolve_scene_paint` pipeline, and needs no new Scene paint-nesting concept — at the cost of extending contrast's `_ground_under` to also treat a prior `Symbol` as ground (item 5 below).
5. **Port position.** Decide whether Layout computes a glyph's *visual* horizontal extent (post contain-fit) for the port, or keeps using the milestone's bounding box and documents an authoring constraint instead. Direction below keeps `layout/ports.py` unchanged and states the constraint explicitly, because every approved target's glyph is drawn full-bleed in its own viewBox (checked against the six READMEs' art), and a Layout-side visual-extent computation would need to walk `parts`' path data for every layout pass, not just Scene build — disproportionate for six targets that don't need it. This is the one place the plan risks not meeting the letter of a criterion without a larger change; called out explicitly for the lead/owner rather than silently narrowed.

## Responsibility and architecture review questions

- Does moving multi-part paint composition into `scene/v05_builder.py`/`scene/mark_geometry.py` keep Theme = tokens, Scene = completed primitives? Yes if the *decision* of which colour paints which part is resolved once, in Scene construction, from Theme tokens already exposed by `ThemeTokenView` — no new Layout responsibility, and Layout keeps owning only the shared bounding box.
- Does extending `contrast_policy.py::_ground_under` to accept `Symbol` grounds change any existing public evidence? It only adds candidates; today no Symbol has other primitives painted over it in the same bounds, so the existing 22 slides' contrast rows are expected to be byte-identical. Verified in the implementation slice, not asserted here.
- Does adding two new Theme roles (`milestoneSymbolActual`, `milestoneSymbolBaseline`) with default-to-`milestoneSymbol` fallback threaten the "unknown role rejected" contract in spec 07 §5.2 (`E_THEME_ROLE_PROPERTY_UNSUPPORTED`)? No — they are new *registered* roles, not unregistered properties; the registry gains two entries, and every existing Theme that only declares `milestoneSymbol` is unaffected because both new roles are optional with an explicit fallback, not a required token.
- Is a Scene version bump needed? No, by precedent: `schemas/scene-v0.6.schema.yaml`'s primitive schema has taken many additive fields since it was introduced (`endTreatment`, `contrastTreatment`, `hostPlacementId`, the table fields) without changing `"chrona/scene/v0.6"`. Adding an optional `parts` array to the `symbol` schema definition follows the same precedent. Confirmed by `git log --oneline -- schemas/scene-v0.6.schema.yaml` showing repeated additive commits under the one version string.
